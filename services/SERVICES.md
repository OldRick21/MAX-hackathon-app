# Исходники сервисов

- `administration/` — backend и клиент сервиса администрирования.
- `schedule/` — сервис расписания: учебные группы и занятия, собственное хранилище, без HTML-клиента (экраны рисует оболочка).
- `user-profile/` — сервис «Люди»: анкеты участников вуза, собственное хранилище, без HTML-клиента (экраны рисует оболочка).
- `demo-service/` — прежний статический клиент демо-расписания; больше не используется, экземпляр заглушки ядро превращает в настоящее расписание.
- Новые сервисы, разрабатываемые в этом репозитории, размещаются в `services/<имя>/`.

`backend/services/` — внутренняя бизнес-логика ядра, а не исходники отдельных сервисов.

При добавлении, изменении или удалении сервиса через админку настройки автоматически синхронизируются в `services/connected/<service_uuid>.json` на сервере. Файл содержит вуз, тип сервиса, адреса, профили и манифест, без credentials, JWT и персональных данных участников. БД — источник истины; ручное редактирование JSON не изменяет сервис. При следующем экспорте изменения файла будут заменены данными БД.

Экспорт выполняется после успешной транзакции. Если диск недоступен, операция в БД сохраняется, ошибка пишется в лог; файлы можно восстановить командой `sudo docker compose exec backend python manage.py export-services`. При запуске также выполняется полная синхронизация. Отключённый сервис сохраняется с `enabled: false`, физически удалённая запись исчезает из экспорта. Файлы не коммитятся в Git.

Исходники собственных сервисов хранятся в этой папке, но подключение экземпляра не загружает код и не запускает контейнер. Облачный экземпляр использует развёрнутый процесс, локальный работает у вуза.

Перед первым запуском обновлённого Compose подготовьте директорию для UID backend (10001):

```bash
mkdir -p services/connected
sudo chown 10001:10001 services/connected
sudo chmod 750 services/connected
sudo docker compose up -d --build backend administration user-profile schedule web
```

Сервис «Люди» хранит анкеты в volume `profile-data` и работает под UID 10003; каталог в томе создаёт сам образ, отдельной подготовки не требуется. Экземпляр подключается вузу в админке или командой `manage.py install-people INSTITUTION_UUID` — подробности в [корневом README](../README.md#сервис-люди).


## Первый администратор

Сначала пользователь входит через MAX и получает UUID платформы. Оператор один раз назначает первого сотрудника поддержки:

```bash
sudo docker compose exec backend python manage.py grant-platform-role USER_UUID
```

Для нового вуза другой пользователь отправляет заявку через оболочку; поддержка одобряет её. Заявитель становится владельцем вуза (профиль `admin`, роль `owner` сервиса администрации). Самостоятельно одобрять свою заявку нельзя.

Для уже существующего вуза без владельца оператор выполняет:

```bash
sudo docker compose exec backend python manage.py list-institutions
sudo docker compose exec backend python manage.py assign-owner INSTITUTION_UUID USER_UUID
```

После назначения заново откройте приложение и выберите профиль администратора. Следующих администраторов владелец добавляет через интерфейс, назначая профиль и необходимые роли. Поддержка платформы и администратор вуза — разные полномочия.
