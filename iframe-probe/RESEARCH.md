# Проверка встраивания клиентов сервисов

## Вывод на 22 сентября 2026

В документации MAX мини-приложение описано как HTML/CSS/JavaScript. В изученных разделах подключения и Bridge нет явной гарантии работы вложенных iframe. Поддержку внутри MAX необходимо проверить на реальных клиентах Android, iOS и Web/Desktop. Обычный Chromium не подтверждает совместимость со всеми браузерами MAX.

Для первого прототипа выбран iframe: он изолирует документ и стили сервиса. Каталог может содержать произвольное число записей, но одновременно открытые iframe расходуют память и процессор. «Без ограничений» по ресурсам обещать нельзя.

## Что реализовано

1. Ядро-клиент запрашивает `GET /api/demo/services` у ядра-backend.
2. Backend возвращает каталог из двух демонстрационных сервисов: расписание и профиль, с URL их клиентов.
3. По кнопке «Открыть» ядро создаёт iframe и браузер загружает HTML с `/api/demo/clients/<id>`.
4. JS сервиса отправляет `service:ready`, ядро отвечает `core:ping`, сервис возвращает `service:pong`.
5. Кнопка внутри клиента передаёт `service:action` в ядро.
6. «Выгрузить» удаляет iframe и таймер. Карточка остаётся, клиент можно открыть заново.

Это динамическая загрузка веб-клиента, а не скачивание файла на устройство пользователя. Клиенты отдаются отдельными запросами: не нужно включать все HTML/JS в начальный ответ каталога.

Карточки создаются без iframe; число экземпляров не зашито в коде. Сейчас они чередуют два демо-клиента, а не регистрируют новые реальные сервисы. Реестр вузов, сервисов и их API остаётся отдельной задачей.

## Как проверить внутри MAX

Развёртывание теста выполняется отдельно по инструкции в README.md этой папки.

1. Открыть тестовое мини-приложение кнопкой отдельного бота внутри MAX.
2. На его главной странице находится проверка iframe.
3. Дождаться сообщения о получении каталога. Нажать «Открыть».
4. Проверить, что виден интерфейс клиента, а ядро показывает «Связь в обе стороны работает».
5. Нажать кнопку внутри iframe и убедиться, что увеличился счётчик действий в ядре.
6. Добавить ещё 5 клиентов и открыть их. Повторить с 10–20 экземплярами, оценить отзывчивость и прокрутку на целевом устройстве.
7. Проверить «Выгрузить», повторное открытие и «Удалить все».
8. Нажать «Показать отчёт», скопировать текст и приложить ОС, версию MAX и наблюдения об интерфейсе.

Отчёт содержит User-Agent, состояния, время установления связи и счётчики действий, но не персональные данные MAX. Время включает загрузку документа и обмен сообщениями; это не измерение памяти и не отдельный замер сетевой задержки. Сам `load` iframe не считается успешной проверкой. Таймаут не доказывает отсутствие поддержки: причиной может быть сеть или конфигурация сервера.

| Среда | Результат |
| --- | --- |
| Chromium 144, Linux, окно 390×844 | Проверены 6 iframe, двусторонние сообщения, действие кнопки, выгрузка/повторное открытие, удаление и отчёт; Flask обслуживал HTTP напрямую, без Docker/Nginx |
| MAX Android | Требуется проверка на устройстве |
| MAX iOS | Требуется проверка на устройстве |
| MAX Web/Desktop | Требуется проверка внутри MAX |

Локальная команда `python -m http.server` не обслуживает API: для полного теста нужен backend за тем же origin, что и страница.

## Изоляция и дальнейшая интеграция

Демонстрационные iframe используют `sandbox="allow-scripts"`, без `allow-same-origin`. Родитель проверяет `event.source`, opaque origin `null` и идентификатор конкретного запуска. Клиент проверяет источник и origin ядра. MAX Bridge остаётся ответственностью ядра; токен бота и `initData` в дочерний документ не передаются.

Эта проверка подтверждает только загрузку HTML, выполнение JS и сообщения. Она не проверяет cookies, авторизацию, загрузку ES-модулей или запросы к API из sandbox: opaque origin потребует отдельного решения для этих возможностей. В прототипе нет реальных пользовательских данных и нет загрузки произвольного URL от пользователя.

Для внешнего сервиса его CSP `frame-ancestors` и X-Frame-Options должны разрешать встраивание; CSP оболочки должна разрешать его через `frame-src`. В MAX Web учитывать всю цепочку родителей. Ошибка на конкретном внешнем сайте не означает, что iframe вообще не поддерживаются. Клиент локального сервиса должен быть доступен устройству пользователя либо безопасно опубликован через платформу; произвольный proxy URL не реализован.

Для MVP предпочтительно держать открытым один выбранный клиент; остальные хранить как записи каталога. При переключении можно выгружать предыдущий клиент, учитывая потерю его несохранённого состояния.

## Запасной вариант, если iframe не пройдёт проверку в MAX

Для доверенных и проверенных клиентов платформы: загружать ES-модуль через `import(url)`, вызывать `mount(container, context)` и `unmount()`, отображать интерфейс в Shadow DOM. Каталог backend возвращает URL версии модуля. Это позволяет обойтись без отдельного документа на сервис.

Shadow DOM изолирует оформление, но не является границей безопасности JavaScript: модуль работает с полномочиями ядра. Поэтому этот вариант подходит только для доверенного кода, а не произвольных клиентов вузов. Поддержку dynamic import и Shadow DOM также следует проверить в целевых MAX-клиентах. Пока iframe не признан неработающим, второй загрузчик не добавлен.
