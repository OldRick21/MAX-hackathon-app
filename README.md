# Вузы России — мини-приложение MAX

Платформа объединяет сервисы вузов в одном мини-приложении MAX. Пользователь выбирает вуз и свой профиль, затем получает доступ к сервисам этого вуза: администрированию, расписанию и анкетам пользователей. Локальный сервис курсовых работ предусмотрен как демонстрация расширения платформы.

Проект находится в разработке. В репозитории есть работающая стартовая страница, бот, минимальный backend для Docker и отдельный прототип системы авторизации. Полный пользовательский сценарий пока не собран.

## Текущее состояние

| Компонент | Что есть в коде | Как запускается |
| --- | --- | --- |
| `bot/` | JS-бот с кнопкой открытия привязанного мини-приложения | Сервис `bot` в Compose |
| `frontend/` | Приветствие, имя из MAX Bridge, светлая и тёмная темы | Nginx или локальный HTTP-сервер |
| `backend/` | FastAPI-приложение с `GET /api/v1/health`; заготовки роутеров | Сервис `backend`, Uvicorn |
| `auth_system/` | Пользователи, членства в вузах, профили, сессии, роли, манифесты и часть администрирования | Отдельно, локально; в Compose не включён |
| `docs/core/` | Целевой контракт и спецификация API ядра | Документация |
| `docs/services/` | Контракты Service SDK и четырёх сервисов | Документация; реализации сервисов и SDK ещё нет |

**`backend/` и `auth_system/` — разные приложения.** Команда `docker compose up` не запускает систему авторизации. Основной frontend пока не отправляет `initData` на backend и не получает пользовательскую сессию.

## Модель платформы

- **Пользователь** имеет внутренний ID и может состоять в нескольких вузах.
- **Членство** связывает пользователя с вузом и хранит его профили.
- **Профиль** — статус внутри вуза: `student`, `teacher` или `admin`. У человека может быть несколько профилей одновременно.
- **Экземпляр сервиса** принадлежит одному вузу. Облачные сервисы размещаются у платформы, локальные — в инфраструктуре вуза.
- **Роль** относится к пользователю, выбранному профилю и конкретному экземпляру сервиса. Роли определяют разрешения (`permissions`).

Профиль отвечает на вопрос «кто я в этом вузе», роль — «что мне можно в этом сервисе». Анкета пользователя в сервисе `user-profile` — отдельная сущность, не замена профиля доступа.

По целевой архитектуре ядро хранит пользователей, членства, профили, роли и сессии; сервисы — собственные предметные данные. Один процесс облачного сервиса должен обслуживать несколько логических экземпляров с изоляцией вузов. Подробности — в [манифесте](docs/SPEC_MANIFEST.md) и [спецификации облачного размещения](docs/services/CLOUD_RUNTIME_SPEC.md).

## Локальная работа с интерфейсом

Для изменения дизайна достаточно файлов в `frontend/`. HTML, CSS и JavaScript разделены; сборщик не используется. Шаблоны пока отдаются как статические файлы.

Из корня репозитория:

```bash
python3 -m http.server 8080 --bind 127.0.0.1 --directory frontend
```

Откройте [страницу приветствия](http://127.0.0.1:8080/templates/index.html). Для остановки нажмите `Ctrl+C`.

В обычном браузере страница предлагает открыть приложение в MAX. Если библиотека Bridge недоступна, отображается ошибка её загрузки. Имя из `initDataUnsafe` используется только для отображения, а не как доказательство аутентификации.

## Локальный запуск минимального backend

Из корня репозитория:

```bash
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r backend/requirements.txt
python -m uvicorn backend.app:app --host 127.0.0.1 --port 8000 --reload
```

В другом терминале:

```bash
curl http://127.0.0.1:8000/api/v1/health
```

Ответ:

```json
{"status":"ok"}
```

Автоматическая документация этого приложения: [Swagger UI](http://127.0.0.1:8000/docs). Она содержит фактически подключённые маршруты, а не весь целевой контракт из `docs/`.

В `backend/routers/auth.py` есть проверка HMAC и времени `initData`, но выдача сессии не завершена. Роутеры не подключены через `include_router`; Dockerfile сейчас копирует только `app.py`, без каталога `routers/`.

## Локальный запуск системы авторизации

`auth_system/` — отдельный прототип для разработки и проверки API. Запускайте его вместо минимального backend на порту 8000 либо выберите другой порт. Встроенные тесты ожидают именно `127.0.0.1:8000`.

Из корня репозитория:

```bash
cd auth_system
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

export DATABASE_URL='sqlite:///./dev.db'
export JWT_SECRET_KEY="$(python -c 'import secrets; print(secrets.token_hex(32))')"

python -m uvicorn main:app --host 127.0.0.1 --port 8000 --reload
```

Команды задают настройки для текущего терминала. Вместо переменных окружения можно использовать локальный `auth_system/.env`: настройки читаются относительно текущей рабочей директории. Сохраняйте один и тот же секрет, если нужно проверять ранее выданные токены после перезапуска.

| Переменная | Назначение | Значение по умолчанию |
| --- | --- | --- |
| `DATABASE_URL` | Подключение SQLAlchemy | Обязательна |
| `JWT_SECRET_KEY` | Ключ подписи JWT | Обязательна |
| `JWT_ALGORITHM` | Алгоритм JWT | `HS256` |
| `REDIS_HOST` | Адрес Redis | `localhost` |
| `REDIS_PORT` | Порт Redis | `6379` |

Для текущего прототипа используйте SQLite: обработчик подключения безусловно выполняет SQLite-команду `PRAGMA foreign_keys=ON`. Подключение PostgreSQL потребует изменения кода, одного другого `DATABASE_URL` недостаточно.

При старте создаются таблицы. Если вузов ещё нет, создаётся демонстрационный вуз с записями сервисов и тестовыми machine credentials. Адреса этих сервисов — примеры, а не развёрнутые приложения.

Если Redis недоступен, код переключается на FakeRedis в памяти процесса. Для локального запуска используйте один worker; такой fallback не обеспечивает общее состояние между процессами и теряет данные после перезапуска.

### Возможности и ограничения прототипа

В `auth_system/routes/auth.py` подключены маршруты входа, refresh/logout, текущего пользователя, вузов и профилей, выдачи и отзыва сервисных сессий, machine-токенов, introspection, манифестов, ролей и части управления вузом. `/institution` и `/institution/{institution_id}` пока возвращают HTML-заглушки.

Перед интеграцией с реальными пользователями остаются существенные задачи:

- Dev-вход по `username` или `max_user_id` работает без подтверждения личности. Для существующего username пароль проверяется только при его передаче. Пользователи с префиксом `ivan_` автоматически получают демонстрационное членство, а имя с `admin` — также профиль администратора.
- Вход через `initData` ищет `MAX_BOT_TOKEN`, но это поле не объявлено в `Settings`; используется тестовое значение по умолчанию. Простого добавления переменной в `.env` при текущем коде недостаточно. Корневой `BOT_TOKEN` сейчас передаётся Compose только боту.
- JWKS возвращает демонстрационный RSA-ключ, тогда как фактическая подпись JWT по умолчанию использует HS256. Это не готовая реализация публичной проверки ключей.
- Private admin-маршруты находятся в том же приложении. Отдельный закрытый listener и сетевые ограничения из спецификации ещё не настроены.
- Frontend, основной backend и `auth_system` ещё не объединены. Проверка телефона, полный процесс регистрации и ручного одобрения вузов, интерфейсы сервисов и загрузка их клиентов не завершены.

Наличие обработчика не означает полного соответствия OpenAPI. Список недостающих проверок нужно сверять с целевыми контрактами; исследовательские документы не заменяют аудит реализации.

### Проверка auth_system

При запущенном локальном `auth_system` откройте второй терминал:

```bash
cd auth_system
source .venv/bin/activate
python run_all_tests.py
```

Путь `cd auth_system` здесь указан относительно корня репозитория. Runner вызывает четыре набора сценариев: core auth, service RBAC, private administration и lifecycle/compliance. Они создают пользователей, роли, членства и записи сервисов — используйте отдельную тестовую БД.

Runner не запускает сервер самостоятельно. При неудаче набора он выводит ошибку, но не выставляет ненулевой exit code; проверяйте итоговый отчёт, а не только код завершения процесса. Эти тесты не подтверждают безопасность production-конфигурации или полное соответствие контрактам.

## Запуск на настроенном сервере через Docker

Текущая конфигурация рассчитана на сервер `195.133.197.144` с уже выпущенным сертификатом. Обычный Compose запускает:

| Сервис | Назначение |
| --- | --- |
| `bot` | Node.js 24, long polling MAX, кнопка открытия мини-приложения |
| `backend` | Python 3.13, FastAPI и Uvicorn с двумя workers; внутренний порт 8000 |
| `web` | Nginx, внешние порты 80 и 443; ожидает успешный healthcheck backend |
| `certbot` | Инструмент выпуска/продления сертификата в профиле `tools`; не работает постоянно |

Маршрутизация Nginx:

- HTTP перенаправляется на HTTPS, кроме пути ACME-проверки.
- `/` отдаёт `frontend/templates/index.html`.
- `/static/` отдаёт CSS и JavaScript из `frontend/static/`.
- `/api/` проксируется в `backend:8000` с сохранением пути.

`auth_system`, SQL-база и Redis в основном Compose отсутствуют. Порт backend наружу не опубликован. Автоматическая страница FastAPI `/docs` также не проксируется текущим Nginx.

### Подготовка

Нужны Docker Engine, Docker Compose, доступ к MAX API и свободные порты 80/443. В конфигурации используется существующее хранилище сертификатов:

```text
/var/lib/max-miniapp/acme/
/var/lib/max-miniapp/letsencrypt/
└── live/max-miniapp/
    ├── fullchain.pem
    └── privkey.pem
```

Сохраняйте весь каталог `letsencrypt`, включая файлы, на которые ссылается `live/`. На новом сервере без этих данных текущий Nginx не запустится: первичный выпуск сертификата требует отдельной настройки. При другом адресе измените `server_name`, редирект и настройки сертификата в `web/configs/docker-nginx.conf`.

При первом запуске из корня репозитория создайте `.env`, если его ещё нет:

```bash
cp .env.example .env
chmod 600 .env
```

Укажите свой токен в файле:

```dotenv
BOT_TOKEN=YOUR_BOT_TOKEN
```

Существующий `.env` при обновлении не перезаписывайте. Корневой файл предназначен для бота и не является конфигурацией `auth_system`.

### Запуск и проверка

Остановите другие экземпляры того же бота, затем из корня репозитория:

```bash
sudo docker compose config --quiet
sudo docker compose up -d --build
sudo docker compose ps
sudo docker compose logs --tail=50 bot backend web
curl https://195.133.197.144/api/v1/health
```

Сайт: [https://195.133.197.144/](https://195.133.197.144/). В настройках мини-приложения бота MAX должен быть привязан этот адрес.

Бот получает свой username из MAX API и использует `Keyboard.button.openApp` для открытия связанного мини-приложения. URL сайта в `bot.mjs` не задаётся. Файл `russian_trusted_root_ca_pem.crt` используется Node.js как дополнительный корневой сертификат через `NODE_EXTRA_CA_CERTS`; это не HTTPS-сертификат сайта.

## Обновление и обслуживание

Обычное обновление на сервере при чистом рабочем дереве:

```bash
git pull --ff-only
sudo docker compose up -d --build
```

После изменения HTML/CSS/JS пересборка образа не нужна: frontend подключён через bind mount. Обновите страницу, при необходимости очистите кеш браузера или заново откройте мини-приложение.

После изменения Python-кода:

```bash
sudo docker compose up -d --build backend
```

После изменения кода бота:

```bash
sudo docker compose up -d --build bot
```

После изменения файла конфигурации Nginx:

```bash
sudo docker compose up -d --force-recreate web
sudo docker compose exec web nginx -t
sudo docker compose logs --tail=50 web
```

Общие команды:

```bash
sudo docker compose ps
sudo docker compose logs -f --tail=100
sudo docker compose stop
sudo docker compose down
```

`down` удаляет контейнеры и сеть проекта; файлы репозитория и внешнее хранилище сертификатов сохраняются.

Проверка продления существующего сертификата:

```bash
sudo docker compose run --rm certbot renew --dry-run
```

Реальное продление и применение сертификата:

```bash
sudo docker compose run --rm certbot renew
sudo docker compose exec web nginx -t && sudo docker compose exec web nginx -s reload
```

Планировщик продления не входит в репозиторий. Если на сервере настроен systemd timer, его конфигурация хранится отдельно от Compose.
