# Вузы России — мини-приложение MAX

## Интерфейс из макета

Основной интерфейс перенесён из `vuzy-frontend.tar.gz`: React, TypeScript, Vite, адаптивная навигация, локальные шрифты. Исходники оформления находятся в `frontend/src/`; CSS — в `styles/` и CSS Modules рядом с компонентами.

`web` теперь собирается из `frontend/Dockerfile`: Node собирает интерфейс, Nginx отдаёт результат. После изменения оформления на сервере выполните:

```bash
sudo docker compose up -d --build web
```

Для локального просмотра дизайна:

```bash
cd frontend
npm ci
npm run dev
```

Локальная разработка использует демонстрационные данные. `npm run build` и Docker используют реальный API и вход через MAX; обычный браузер показывает заглушку. Проверка сборки: `npm run build`. Проверка нового интерфейса: `npm run test:design` (требуются Playwright и Chromium).

Сохранены заявки на подключение вуза и поддержка платформы. Администрирование и дополнительные сервисы открываются через iframe. Демо-расписание с меню `home` также открывается через iframe. Встроенные экраны «Профиль» и «Люди» работают против сервиса анкет (`services/user-profile`): оболочка рисует их сама, без iframe. Встроенный экран расписания по-прежнему требует реализации API — оформление его не создаёт.

Старые `frontend/templates`, `frontend/static` и тесты старой оболочки пока сохранены для сравнения, в образ нового веб-клиента они не попадают. Старый `version:assets` для React не нужен: Vite добавляет хеши к именам ресурсов.

Органайзер сервисов вузов с единым входом через MAX. Пользователь выбирает вуз и профиль, затем открывает доступный сервис внутри приложения. Один пользователь может состоять в нескольких вузах и иметь несколько профилей в каждом.

Основной backend — Python/FastAPI, frontend — React/TypeScript, бот — Node.js. Приложения запускаются через Docker Compose, внешние запросы принимает Nginx.

## Что реализовано

- Вход по подписанным данным MAX, внутренний UUID пользователя, core/service-сессии, обновление и отзыв токенов. В обычном браузере без данных MAX показывается заглушка.
- Выбор вуза, профиля и сервиса; динамическая загрузка клиента сервиса в iframe по протоколу SDK.
- Заявки на подключение вузов и раздел поддержки платформы.
- Сервис администрирования: участники, профили, роли, подключённые сервисы и журнал операций.
- Сервис «Люди» (`user-profile`): отдельный контейнер со своим хранилищем анкет. В оболочке — пункты «Профиль» и «Люди»: своё имя и описание правит сам участник, должность и учёную степень — администратор с правом `profiles.manage`, список содержит только заполненные анкеты своего вуза.
- Тестовый вуз и статическая заглушка расписания с вымышленными занятиями.
- Автоматическое сохранение настроек подключённых сервисов в JSON-файлы.

Вход проверен пользователем на iPhone и в MAX Web через Firefox. Новые административные сценарии проверены локальными тестами; это не заменяет проверку развёрнутой версии в MAX. Полноценные сервисы расписания и курсовых пока не реализованы. Сервис анкет реализован, и его сквозной путь (сессия ядра → service access → анкеты) проверен тестом против живого ядра в одном процессе; на развёрнутом стенде в MAX он ещё не проверялся.

│   ├── Dockerfile               # Сборка Vite → Nginx

│   ├── scripts/                 # Версионирование ресурсов
│   └── tests/
├── backend/
│   ├── main.py                  # FastAPI-приложение ядра
│   ├── auth/                    # MAX, JWT, сессии и проверки доступа
│   ├── database/                # Общая metadata, модели и создание таблиц

│   ├── settings/                # Настройки deployment
│   ├── user_operations/         # Схемы запросов управления
│   ├── manage.py                # Первоначальная настройка платформы
│   ├── seed_demo.py             # Добавление тестового вуза и расписания
│   └── tests/

│   ├── demo-service/            # Заглушка расписания

`backend/services/` содержит функции ядра. Корневая папка `services/` содержит отдельные приложения. Аутентификация выделена в `backend/auth/`: маршруты и схемы входа, проверка MAX, JWT, отзывы, модели пользователей и сессий, зависимости проверки доступа. Все модели используют общую metadata из `backend/database/base.py`.

## Пользователи и права

MAX ID связывается с внутренним UUID после серверной проверки `initData`. Для назначения прав используется UUID платформы, отображаемый в приложении, а не MAX ID.

- Членство связывает пользователя с вузом.
- Профиль (`student`, `teacher`, `admin`) определяет статус пользователя в этом вузе.
- Роль определяет разрешения в конкретном сервисе и выбранном профиле. Профиля `admin` самого по себе недостаточно для административных полномочий.
- Поддержка платформы рассматривает заявки и управляет статусами вузов. Администратор вуза управляет своим вузом через сервис администрации.

Секреты сервисов остаются на сервере. Клиент сервиса получает только service access token; ядро-клиент хранит свои токены в памяти.

## Запуск на сервере

Текущий Nginx настроен на IP `195.133.197.144` и уже выпущенный сертификат в `/var/lib/max-miniapp/letsencrypt`. Для другого адреса нужно согласованно изменить Nginx, адрес мини-приложения в MAX и настройки сервисов. Демо также содержит этот адрес в коде.

Нужны Docker Engine и Docker Compose. Внешние порты: 80/443 для оболочки, 8443 для демо, 8444 для администрации. Backend, administration, user-profile и Redis не публикуют свои внутренние порты напрямую. Сервису «Люди» отдельный порт не нужен: его экраны рисует сама оболочка, iframe с отдельным origin здесь не участвует, поэтому Nginx проксирует префикс `/people/api/` на origin оболочки в контейнер `user-profile`.

### Настройки

При первом запуске из корня проекта:

```bash
cp .env.example .env
chmod 600 .env
nano .env
```

При обновлении существующий `.env` не перезаписывайте — добавьте недостающие переменные:

```dotenv
BOT_TOKEN=актуальный_токен_бота
CURSOR_SECRET_KEY=постоянный_случайный_секрет
JWT_ISSUER=https://195.133.197.144
CLOUD_BINDING_KEY=отдельный_постоянный_случайный_секрет
ADMINISTRATION_PROVISIONING_TOKEN=ещё_один_случайный_секрет
SHELL_ORIGIN=https://195.133.197.144
ADMINISTRATION_PUBLIC_ORIGIN=https://195.133.197.144:8444
USER_PROFILE_PROVISIONING_TOKEN=отдельный_секрет_сервиса_Люди
```

Для каждого из четырёх секретов отдельно выполните `openssl rand -hex 32`. Сохраните значения между перезапусками. `.env` не добавляется в Git. Compose передаёт `BOT_TOKEN` боту и как `MAX_BOT_TOKEN` ядру. Dev-вход, демо-наполнение и FakeRedis в основном Compose выключены.

`USER_PROFILE_PROVISIONING_TOKEN` обязателен: без него Compose не запустится, потому что этим токеном контейнер «Людей» читает свой binding у ядра. Токен администрации для этого не подходит и наоборот — каждый тип сервиса получает только свои bindings.

Подготовьте папку экспорта для пользователя backend (UID 10001):

```bash
mkdir -p services/connected
sudo chown 10001:10001 services/connected
sudo chmod 750 services/connected
```

### Запуск и диагностика

```bash
sudo docker compose config --quiet
sudo docker compose up -d --build
sudo docker compose ps
curl --fail https://195.133.197.144/api/v1/health
sudo docker compose logs --tail=80 backend administration web
```

Ожидаемый ответ healthcheck: `{"status":"ok"}`. Затем откройте мини-приложение кнопкой бота MAX. К боту должен быть привязан адрес оболочки; URL сайта не задаётся напрямую в коде кнопки бота.

SQLite ядра хранится в volume `core-data`, анкеты сервиса «Люди» — в `profile-data`, Redis — в `redis-data`. Обе базы работают в режиме WAL: прерванная запись откатывается при следующем открытии файла, поэтому перезапуск или падение контейнера не оставляет БД повреждённой, а параллельные запросы ждут освобождения записи вместо ошибки. Перед обновлениями схемы сохраняйте резервную копию БД. Не используйте `docker compose down -v` для обычного обновления: это удаляет volumes. При запуске создаются дополнительные таблицы и защищённые экземпляры администрации для существующих вузов; права владельца автоматически не назначаются.

## Первый администратор

### Поддержка платформы

Пользователь сначала входит через MAX. Оператор однократно назначает сотрудника поддержки:

```bash
sudo docker compose exec backend python manage.py grant-platform-role USER_UUID
```

Замените `USER_UUID` на его внутренний UUID. После повторного открытия мини-приложения становится доступен раздел поддержки платформы.

### Владелец нового вуза

1. Другой пользователь отправляет заявку через «Подключить свой вуз».
2. Поддержка рассматривает и одобряет заявку. Одобрять собственную заявку нельзя.
3. Заявитель получает профиль `admin` и роль `owner` в сервисе администрации созданного вуза.
4. Владелец добавляет следующих администраторов через интерфейс, назначая профили и необходимые роли.

### Владелец уже существующего вуза

Если у вуза ещё нет владельца:

```bash
sudo docker compose exec backend python manage.py list-institutions
sudo docker compose exec backend python manage.py assign-owner INSTITUTION_UUID USER_UUID
```

Команда не заменяет существующего владельца. После назначения заново откройте приложение, выберите вуз и профиль администратора. Поддержка платформы и владелец вуза — отдельные назначения.

## Подключение сервисов и общая папка

Собственные реализации размещаются в `services/<имя>/`. Подключение через админку создаёт экземпляр сервиса в БД, связанный с вузом. Облачный экземпляр использует уже развёрнутый процесс платформы; локальный сервис работает в инфраструктуре вуза по одобренным адресам.

После успешного добавления, изменения или удаления настройки синхронизируются в:

```text
services/connected/<service_uuid>.json
```

Файл содержит UUID сервиса и вуза, тип, способ размещения, адреса API/клиента, профили, манифест и состояние `enabled`. Credentials и JWT в него не выгружаются. БД остаётся источником истины: ручная правка JSON не меняет сервис и будет перезаписана.

Файлы исключены из Git. Отключённый сервис сохраняется с `enabled: false`; физически удалённая запись удаляется из экспорта. При ошибке записи на диск транзакция БД сохраняется, ошибка попадает в лог. Восстановление файлов:

```bash
sudo docker compose exec backend python manage.py export-services
```

Полная синхронизация также выполняется при запуске ядра. Добавление сервиса через админку не загружает его исходники и не запускает новые контейнеры. Новый тип сервиса требует реализации, настройки размещения и добавления в каталог разрешённых типов. Подробности: [services/SERVICES.md](services/SERVICES.md).

## Сервис «Люди»

Анкеты участников вынесены в отдельный сервис: контейнер `user-profile`, собственная SQLite в volume `profile-data`, свой provisioning-токен. Ядро остаётся источником пользователей, членств и профилей — сервис хранит только анкету и на каждый запрос спрашивает у ядра, кто пришёл и что ему можно.

Экземпляр создаётся вузу, а не платформе целиком. Владелец вуза подключает его в админке («Сервисы» → тип `user-profile`, размещение «облачное»). Если владельца ещё нет или адреса платформы переехали, оператор выполняет:

```bash
sudo docker compose exec backend python manage.py install-people INSTITUTION_UUID
```

Команда идемпотентна: создаёт экземпляр, начальную роль `profile_editor`, credential и binding, а на повторном запуске лишь приводит адреса и манифест к текущим настройкам. Право `profiles.manage` автоматически не выдаётся никому: владелец назначает роль «Редактор анкет» конкретному администратору в админке. Без неё должность и учёную степень не изменит даже профиль `admin`.

Что видит участник:

- «Профиль» — своя анкета: имя и описание правит сам владелец анкеты. Имя вводится пользователем и не считается подтверждённым ФИО.
- «Люди» — участники своего вуза, заполнившие анкету, с поиском по имени и должности. Анкеты других вузов недоступны, а снятое членство сразу убирает участника из списка и закрывает его карточку.

Как это устроено в развёрнутой версии:

- Оболочка получает service access token у ядра и обращается к `https://<origin>/people/api/v1/...`; Nginx проксирует этот префикс в контейнер. Отдельного origin и iframe нет — экраны рисует сама оболочка.
- Сервис на каждый защищённый запрос читает свой binding, обменивает credential на machine-токен и выполняет online introspection. Недоступность ядра даёт `503`, а не показ непроверенных анкет.
- Анкеты хранятся в разрезе `(вуз, экземпляр, пользователь)` и переживают перезапуск контейнера. Одновременная правка одной анкеты разрешается по `ETag`/`If-Match`: второй запрос получает `412`, а не молча перетирает первый.

Диагностика:

```bash
sudo docker compose logs --tail=80 user-profile
sudo docker compose exec user-profile python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8200/api/v1/health').read())"
```

Если в логах `Хранилище /data/profiles.db недоступно для записи`, значит volume `profile-data` принадлежит root, а процесс работает под UID 10003. Это бывает с томом, созданным до появления образа. Тома с анкетами в этом случае ещё нет, поэтому его можно пересоздать:

```bash
sudo docker compose stop user-profile
sudo docker volume rm $(basename $(pwd))_profile-data
sudo docker compose up -d user-profile
```

Контракт сервиса — [SPEC.md](docs/services/user-profile/SPEC.md), реализация и отличия от контракта — [IMPLEMENTATION.md](docs/services/user-profile/IMPLEMENTATION.md).

## Тестовый вуз и расписание

Для существующего пользователя:

```bash
sudo docker compose exec backend python seed_demo.py USER_UUID
```

Команда создаёт тестовый вуз, демо-расписание и назначает профиль студента. Повторный запуск не дублирует записи и сохраняет существующие профили. Затем откройте MAX → «Тестовый университет» → «Расписание».

Демо использует `https://195.133.197.144:8443`, показывает вымышленные занятия и кнопку обновления сервисной сессии. Собственного backend расписания нет. [Описание заглушки](services/demo-service/DEMO.md).

## Разработка и обновление

Исходники интерфейса находятся в `frontend/src`. Для просмотра оформления используйте `npm ci` и `npm run dev` из `frontend/`. Для проверки производственной сборки: `npm run build` и `npm run preview`. В производственном режиме вход доступен только через MAX.

После изменения дизайна пересоберите контейнер `web`. Имена CSS и JS версионируются Vite автоматически.

## Тесты

В отдельном виртуальном окружении установите `backend/requirements.txt`, `services/administration/requirements.txt` и `httpx`. Из `backend/` запускайте наборы отдельными процессами: они задают разные временные БД и настройки.

```bash
python -m unittest tests.test_max_integration -v
python -m unittest tests.test_administration_flow -v
python -m unittest tests.test_platform_core -v
python -m unittest tests.test_service_files -v
```

Из `services/administration/`:

```bash
python -m unittest tests.test_core_client -v
```

Из `services/user-profile/` (нужны `services/user-profile/requirements.txt` и `httpx`):

```bash
python -m unittest discover -s tests -t . -v
PYTHONPATH=../../backend python -m unittest tests.test_integration_core -v
```

Первый набор проверяет сам сервис на заглушке ядра: доступ, версии анкет, гонку правок, каталог и перезапуск на существующем томе. Второй поднимает настоящее ядро в том же процессе и прогоняет весь путь: установку экземпляра командой оператора, сессию сервиса, `GET /api/v1/service`, сохранение анкеты, выдачу роли `profile_editor` и её действие на уже выданный токен, отказ токену чужого сервиса, снятие членства и logout.

Из `frontend/`:

```bash
npm test
npm install
npx playwright install chromium
npm run test:design
```

Браузерные тесты используют тестовый API и не доказывают работу на всех клиентах MAX. Старый `backend/run_all_tests.py` предназначен для отдельного HTTP-стенда с dev-входом; это не инструкция запуска рабочего сервера.

## Сертификаты

Nginx использует сертификат `/etc/letsencrypt/live/max-miniapp/` из подключённого хранилища. Проверка и продление:

```bash
sudo docker compose run --rm certbot renew --dry-run
sudo docker compose run --rm certbot renew
sudo docker compose exec web nginx -t && sudo docker compose exec web nginx -s reload
```

Планировщик продления на сервере настраивается отдельно. Сертификат `bot/russian_trusted_root_ca_pem.crt` — дополнительный корневой сертификат для Node.js, а не сертификат сайта.

Контракты описывают целевую архитектуру; реализация ещё не полностью им соответствует. Проверка телефона и настоящие предметные сервисы остаются в разработке. JWT подписываются RS256; публичный JWKS содержит действующие access-ключи. [Запуск без миграций и ротация JWT-ключей](docs/core/JWT_OPERATIONS.md): Compose начинает с новой БД `core-jwt.db`, учётные записи разработчиков нужно создать заново. Администрация использует online introspection. Private API закрыт внешним Nginx, но работает в том же процессе ядра. Расширения административного API нужно согласовать с OpenAPI. Исследовательские материалы `docs/slop/` не заменяют актуальные инструкции запуска.
