# Вузы России — мини-приложение MAX

Платформа объединяет сервисы вузов в одном мини-приложении MAX. Пользователь выбирает вуз и свой профиль, затем получает доступ к сервисам этого вуза: администрированию, расписанию и анкетам пользователей. Локальный сервис курсовых работ предусмотрен как демонстрация расширения платформы.

Проект находится в разработке. В репозитории есть ядро-клиент по API-контракту, бот, система авторизации в Docker. Полный сценарий требует наполнения вузов и подключения клиентов сервисов.

## Текущее состояние

| Компонент | Что есть в коде | Как запускается |
| --- | --- | --- |
| `bot/` | JS-бот с кнопкой открытия привязанного мини-приложения | Сервис `bot` в Compose |
| `frontend/` | Вход через MAX, выбор вуза/профиля, каталог и загрузка клиентов через iframe | Nginx; для работы нужен API ядра |
| `backend/` | Пользователи, членства в вузах, профили, сессии, роли, манифесты и часть администрирования | Сервис `backend` в Compose |
| `administration/` | Облачный сервис «Администрирование»: фасад private API ядра и интерфейс в iframe | Сервис `administration` в Compose, HTTPS-порт 8444 |
| `demo-service/` | Статическая заглушка расписания с протоколом iframe; вымышленные занятия | Nginx, HTTPS-порт 8443 |
| `docs/core/` | Целевой контракт и спецификация API ядра | Документация |
| `docs/services/` | Контракты Service SDK и четырёх сервисов | Документация; реализации сервисов и SDK ещё нет |

**Compose запускает `backend/` как сервис `backend`.** Nginx направляет `/api/` в него. База SQLite и Redis хранятся в именованных Docker volumes. Инструкция проверки в MAX: [MAX_DEPLOYMENT.md](docs/core/MAX_DEPLOYMENT.md).

## Администрирование и поддержка платформы

Повседневное управление выполняется в интерфейсе, без `seed_demo.py` и правки БД: заявки вузов и их статус — в разделе «Поддержка платформы» оболочки; участники, профили, роли, сервисы и журнал — в сервисе «Администрирование» вуза. Одноразовые команды оператора и описание реализации: [IMPLEMENTATION.md](docs/services/administration/IMPLEMENTATION.md).

## Модель платформы

- **Пользователь** имеет внутренний ID и может состоять в нескольких вузах.
- **Членство** связывает пользователя с вузом и хранит его профили.
- **Профиль** — статус внутри вуза: `student`, `teacher` или `admin`. У человека может быть несколько профилей одновременно.
- **Экземпляр сервиса** принадлежит одному вузу. Облачные сервисы размещаются у платформы, локальные — в инфраструктуре вуза.
- **Роль** относится к пользователю, выбранному профилю и конкретному экземпляру сервиса. Роли определяют разрешения (`permissions`).

Профиль отвечает на вопрос «кто я в этом вузе», роль — «что мне можно в этом сервисе». Анкета пользователя в сервисе `user-profile` — отдельная сущность, не замена профиля доступа.

По целевой архитектуре ядро хранит пользователей, членства, профили, роли и сессии; сервисы — собственные предметные данные. Один процесс облачного сервиса должен обслуживать несколько логических экземпляров с изоляцией вузов. Подробности — в [манифесте](docs/SPEC_MANIFEST.md) и [спецификации облачного размещения](docs/services/CLOUD_RUNTIME_SPEC.md).

## Локальная работа с интерфейсом

После изменения HTML, CSS или JS обновляйте версии ресурсов перед коммитом:

```bash
node frontend/scripts/version-assets.mjs
```

Скрипт вычисляет общую версию по содержимому файлов и обновляет ссылки на CSS, JS и импорты модулей. Повторный запуск без изменений ничего не меняет. Зависимости npm для этой команды не нужны. Nginx отдаёт HTML без условного 304, а статику с `Cache-Control: no-cache`: браузер может хранить её, но должен проверять актуальность. После изменения конфигурации на сервере выполните `sudo docker compose exec web nginx -t && sudo docker compose exec web nginx -s reload`.


Для изменения дизайна достаточно файлов в `frontend/`. HTML, CSS и JavaScript разделены; сборщик не используется. Шаблоны пока отдаются как статические файлы.

Из корня репозитория:

```bash
python3 -m http.server 8080 --bind 127.0.0.1 --directory frontend
```

Откройте [ядро-клиент](http://127.0.0.1:8080/templates/index.html). Для остановки нажмите `Ctrl+C`.

Без данных MAX оболочка предлагает открыть приложение через бота. Вход выполняется передачей исходной строки `initData` серверу; `initDataUnsafe` не используется как доказательство личности. [Сценарий входа, привязка MAX ID к UUID, профили и протокол iframe](docs/core/CORE_CLIENT.md).

## Локальный запуск системы авторизации

`backend/` — FastAPI-приложение ядра, которое также запускается в Compose. Ниже приведён локальный режим для разработки с тестовыми данными. Встроенные HTTP-тесты ожидают `127.0.0.1:8000`.

Из корня репозитория:

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.txt

export ALLOW_DEV_LOGIN=true SEED_DEMO_DATA=true ALLOW_FAKE_REDIS=true
export DATABASE_URL='sqlite:///./dev.db'
export JWT_SECRET_KEY="$(python -c 'import secrets; print(secrets.token_hex(32))')"

python -m uvicorn main:app --host 127.0.0.1 --port 8000 --reload
```

Команды задают настройки для текущего терминала. Вместо переменных окружения можно использовать локальный `backend/.env`: настройки читаются относительно текущей рабочей директории. Сохраняйте один и тот же секрет, если нужно проверять ранее выданные токены после перезапуска.

| Переменная | Назначение | Значение по умолчанию |
| --- | --- | --- |
| `DATABASE_URL` | Подключение SQLAlchemy | Обязательна |
| `JWT_SECRET_KEY` | Ключ подписи JWT | Обязательна |
| `JWT_ALGORITHM` | Алгоритм JWT | `HS256` |
| `REDIS_HOST` | Адрес Redis | `localhost` |
| `REDIS_PORT` | Порт Redis | `6379` |

Compose использует SQLite. Таблицы создаются при запуске, демонстрационные данные — только при `SEED_DEMO_DATA=true`. Dev-вход включается только через `ALLOW_DEV_LOGIN=true`, FakeRedis — через `ALLOW_FAKE_REDIS=true`. В основном Compose все три флага выключены. Локальные старые тесты требуют включить их и использовать отдельную тестовую БД.

### Возможности и ограничения прототипа

В `backend/auth/routes.py` находятся вход, refresh/logout, текущий пользователь, сервисные сессии и machine-аутентификация. Маршруты вузов, реестра сервисов и администрирования находятся в `backend/routes/`. `/institution` и `/institution/{institution_id}` пока возвращают HTML-заглушки.

Перед интеграцией с реальными пользователями остаются существенные задачи:

- Настоящий MAX-вход использует `MAX_BOT_TOKEN`; Compose передаёт его из корневого `BOT_TOKEN`. Dev-вход выключен по умолчанию.
- JWKS возвращает демонстрационный RSA-ключ, тогда как фактическая подпись JWT по умолчанию использует HS256. Это не готовая реализация публичной проверки ключей.
- Private admin-маршруты находятся в том же приложении. Nginx закрывает эти пути на внешнем адресе; они доступны внутри сети Docker. Отдельный listener пока не реализован.
- Ядро-клиент подключён к API `backend`. Проверка телефона, полный процесс регистрации и ручного одобрения вузов, интерфейсы самих сервисов не завершены. Их загрузка оболочкой реализована, но требует клиентов с протоколом SDK.

Наличие обработчика не означает полного соответствия OpenAPI. Список недостающих проверок нужно сверять с целевыми контрактами; исследовательские документы не заменяют аудит реализации.

### Проверка backend

При запущенном локальном `backend` откройте второй терминал:

```bash
cd backend
source .venv/bin/activate
python run_all_tests.py
```

Путь `cd backend` здесь указан относительно корня репозитория. Runner вызывает четыре набора сценариев: core auth, service RBAC, private administration и lifecycle/compliance. Они создают пользователей, роли, членства и записи сервисов — используйте отдельную тестовую БД.

Runner не запускает сервер самостоятельно. При неудаче набора он выводит ошибку, но не выставляет ненулевой exit code; проверяйте итоговый отчёт, а не только код завершения процесса. Эти тесты не подтверждают безопасность production-конфигурации или полное соответствие контрактам.

## Запуск на настроенном сервере через Docker

Текущая конфигурация рассчитана на сервер `195.133.197.144` с уже выпущенным сертификатом. Обычный Compose запускает:

| Сервис | Назначение |
| --- | --- |
| `bot` | Node.js 24, long polling MAX, кнопка открытия мини-приложения |
| `backend` | `backend`, Python 3.13, FastAPI, один worker Uvicorn; внутренний порт 8000 |
| `redis` | Хранение отзывов сессий, без внешнего порта |
| `web` | Nginx, внешние порты 80 и 443; ожидает успешный healthcheck backend |
| `certbot` | Инструмент выпуска/продления сертификата в профиле `tools`; не работает постоянно |

Маршрутизация Nginx:

- HTTP перенаправляется на HTTPS, кроме пути ACME-проверки.
- `/` отдаёт `frontend/templates/index.html`.
- `/static/` отдаёт CSS и JavaScript из `frontend/static/`.
- `/api/` проксируется в `backend:8000` с сохранением пути.

SQLite находится в volume `core-data`, Redis — в `redis-data`. Не удаляйте volumes при обновлении. Порт backend наружу не опубликован. Автоматическая страница FastAPI `/docs` также не проксируется текущим Nginx.

### Подготовка

Нужны Docker Engine, Docker Compose, доступ к MAX API и свободные порты 80/443. В конфигурации используется существующее хранилище сертификатов:

```text
/var/lib/max-miniapp/acme/
/var/lib/max-miniapp/letsencrypt/
└── live/max-miniapp/
    ├── fullchain.pem
    └── privkey.pem
```

Сохраняйте весь каталог `letsencrypt`, включая файлы, на которые ссылается `live/`. На новом сервере без этих данных текущий Nginx не запустится: первичный выпуск сертификата требует отдельной настройки. При другом адресе измените `server_name`, редирект и настройки сертификата в `web/configs/docker-nginx.conf`.

При первом запуске из корня репозитория создайте `.env`, если его ещё нет:

```bash
cp .env.example .env
chmod 600 .env
```

Укажите свой токен в файле:

```dotenv
BOT_TOKEN=YOUR_BOT_TOKEN
```

Существующий `.env` при обновлении не перезаписывайте. Добавьте `JWT_SECRET_KEY` — постоянный случайный секрет (например, `openssl rand -hex 32`). Compose передаёт `BOT_TOKEN` боту и API ядра. Не публикуйте `.env`.

### Запуск и проверка

Остановите другие экземпляры того же бота, затем из корня репозитория:

```bash
sudo docker compose config --quiet
sudo docker compose up -d --build
sudo docker compose ps
sudo docker compose logs --tail=50 bot backend web
curl https://195.133.197.144/api/v1/health
```

Сайт: [https://195.133.197.144/](https://195.133.197.144/). В настройках мини-приложения бота MAX должен быть привязан этот адрес.

Бот получает свой username из MAX API и использует `Keyboard.button.openApp` для открытия связанного мини-приложения. URL сайта в `bot.mjs` не задаётся. Файл `russian_trusted_root_ca_pem.crt` используется Node.js как дополнительный корневой сертификат через `NODE_EXTRA_CA_CERTS`; это не HTTPS-сертификат сайта.

## Обновление и обслуживание

Обычное обновление на сервере при чистом рабочем дереве:

```bash
git pull --ff-only
sudo docker compose up -d --build
```

После изменения HTML/CSS/JS пересборка образа не нужна: frontend подключён через bind mount. Обновите страницу, при необходимости очистите кеш браузера или заново откройте мини-приложение.

После изменения Python-кода:

```bash
sudo docker compose up -d --build backend
```

После изменения кода бота:

```bash
sudo docker compose up -d --build bot
```

После изменения файла конфигурации Nginx:

```bash
sudo docker compose up -d --force-recreate web
sudo docker compose exec web nginx -t
sudo docker compose logs --tail=50 web
```

Общие команды:

```bash
sudo docker compose ps
sudo docker compose logs -f --tail=100
sudo docker compose stop
sudo docker compose down
```

`down` удаляет контейнеры и сеть проекта; файлы репозитория и внешнее хранилище сертификатов сохраняются.

Проверка продления существующего сертификата:

```bash
sudo docker compose run --rm certbot renew --dry-run
```

Реальное продление и применение сертификата:

```bash
sudo docker compose run --rm certbot renew
sudo docker compose exec web nginx -t && sudo docker compose exec web nginx -s reload
```

Планировщик продления не входит в репозиторий. Если на сервере настроен systemd timer, его конфигурация хранится отдельно от Compose.

## Тестовый вуз и сервис-заглушка

`backend/seed_demo.py` создаёт «Тестовый университет», регистрирует сервис «Расписание — демо» и назначает указанному существующему пользователю профиль `student`. Команда запускается явно: автоматического назначения членства при входе нет. Повторный запуск не создаёт дубликаты и сохраняет существующие профили.

После обновления кода на сервере:

```bash
cd /opt/MAX-hackathon-app
sudo docker compose up -d --build backend web
sudo docker compose exec backend python seed_demo.py USER_UUID
```

Замените `USER_UUID` на внутренний UUID, показанный приложением после входа через MAX. Это не MAX ID. Если пользователя нет в БД, команда завершится без изменений.

Заново откройте мини-приложение → «Тестовый университет» → «Расписание». Клиент заглушки находится в `demo-service/`, обслуживается на `https://195.133.197.144:8443` и открывается в iframe на отдельном origin. Порт 8443 должен быть доступен с устройства. Используется существующий сертификат IP.

Заглушка показывает вымышленные занятия и позволяет проверить обновление сервисной сессии кнопкой. Собственного backend расписания у неё нет; API URL в реестре зарезервирован для будущей реализации. Создание данных и выдача/обновление сервисной сессии проверены локально; открытие самой заглушки в MAX требует отдельной проверки. Подробнее: [demo-service/README.md](demo-service/README.md).

## Сервис администрирования

Сервис из `administration/` подключён к Compose. Он предоставляет интерфейс управления участниками, профилями, ролями и сервисами вуза, а его backend обращается к private API ядра. В оболочку добавлены заявки на подключение вузов и раздел поддержки платформы. Подробности и ограничения: [IMPLEMENTATION.md](docs/services/administration/IMPLEMENTATION.md).

Перед обновлением сервера добавьте в существующий `.env` (не перезаписывайте старые секреты):

```dotenv
CLOUD_BINDING_KEY=отдельный_случайный_секрет
ADMINISTRATION_PROVISIONING_TOKEN=другой_случайный_секрет
SHELL_ORIGIN=https://195.133.197.144
ADMINISTRATION_PUBLIC_ORIGIN=https://195.133.197.144:8444
```

Каждый новый секрет сгенерируйте отдельно через `openssl rand -hex 32` и сохраните между перезапусками. После резервного копирования существующей БД и обновления кода:

```bash
sudo docker compose config --quiet
sudo docker compose up -d --build backend administration web
```

Порт 8444 должен быть доступен с устройства. Для первого сотрудника поддержки оператор выполняет `sudo docker compose exec backend python manage.py grant-platform-role USER_UUID`. Для существующего вуза без владельца: `sudo docker compose exec backend python manage.py assign-owner INSTITUTION_UUID USER_UUID`. UUID заменяются реальными значениями; эти команды назначают права, не выполняйте их для случайного пользователя. Поддержка не может одобрить собственную заявку: для проверки нужен второй аккаунт. Обычные операции затем выполняются через интерфейс.

Первый запуск создаёт дополнительные таблицы и обеспечивает наличие защищённого сервиса администрации у существующих вузов. Назначения владельца автоматически не выдаются. Существующие таблицы пользователей и сессий сохраняют имена и схему при переносе кода в `auth/`.

## Пакет аутентификации backend/auth

- `routes.py`, `schemas.py` — HTTP-маршруты и тела запросов входа, core/service/machine-сессий.
- `service.py`, `max_validation.py` — операции сессий и проверка подписанных данных MAX.
- `security.py`, `revocations.py`, `config.py` — JWT, хеширование, отзывы и настройки аутентификации.
- `dependencies.py`, `authorization.py` — проверка core/machine-токенов, scopes и доступа к private admin API.
- `models.py` — User, CoreSession, ServiceSession, ServiceCredential. Общая SQLAlchemy metadata находится в `database/base.py`; `database/tables.py` регистрирует все модели и сохраняет совместимые импорты.

Управление вузами, манифестами и ролями сервисов отделено от операций входа. Внешние пути API не менялись. Тесты запускаются из `backend/` отдельными командами, поскольку используют разные временные БД и настройки:

```bash
python -m unittest tests.test_max_integration -v
python -m unittest tests.test_administration_flow -v
python -m unittest tests.test_platform_core -v
```

Из `administration/`: `python -m unittest tests.test_core_client -v`. Тестам FastAPI нужен `httpx`. Для разработки остаются проверка в настоящем MAX, телефонная привязка, полноценный JWKS и согласование расширений API с OpenAPI.
