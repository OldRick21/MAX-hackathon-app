# Вузы России — мини-приложение MAX

## Интерфейс из макета

Основной интерфейс перенесён из `vuzy-frontend.tar.gz`: React, TypeScript, Vite, адаптивная навигация, локальные шрифты. Исходники оформления находятся в `frontend/src/`; CSS — в `styles/` и CSS Modules рядом с компонентами.

`web` теперь собирается из `frontend/Dockerfile`: Node собирает интерфейс, Nginx отдаёт результат. После изменения оформления на сервере выполните:

```bash
sudo docker compose up -d --build web
```

Для локального просмотра дизайна:

```bash
cd frontend
npm ci
npm run dev
```

Локальная разработка использует демонстрационные данные. `npm run build` и Docker используют реальный API и вход через MAX; обычный браузер показывает заглушку. Проверка сборки: `npm run build`. Проверка нового интерфейса: `npm run test:design` (требуются Playwright и Chromium).

Сохранены заявки на подключение вуза и поддержка платформы. Администрирование и дополнительные сервисы открываются через iframe. Встроенные экраны «Профиль» и «Люди» работают против сервиса «Люди» (`services/user-profile`), «Расписание» и «Группы» — против сервиса расписания (`services/schedule`): оболочка рисует их сама, без iframe.

Старые `frontend/templates`, `frontend/static` и тесты старой оболочки пока сохранены для сравнения, в образ нового веб-клиента они не попадают. Старый `version:assets` для React не нужен: Vite добавляет хеши к именам ресурсов.

Органайзер сервисов вузов с единым входом через MAX. Пользователь выбирает вуз и профиль, затем открывает доступный сервис внутри приложения. Один пользователь может состоять в нескольких вузах и иметь несколько профилей в каждом.

Основной backend — Python/FastAPI, frontend — React/TypeScript, бот — Node.js. Приложения запускаются через Docker Compose, внешние запросы принимает Nginx.

## Что реализовано

- Вход по подписанным данным MAX, внутренний UUID пользователя, core/service-сессии, обновление и отзыв токенов. В обычном браузере без данных MAX показывается заглушка.
- Выбор вуза, профиля и сервиса; динамическая загрузка клиента сервиса в iframe по протоколу SDK.
- Заявки на подключение вузов и раздел поддержки платформы.
- Сервис администрирования: участники, профили, роли, подключённые сервисы и журнал операций.
- Сервис «Люди» (`user-profile`): отдельный контейнер со своим хранилищем анкет. В оболочке — пункты «Профиль» и «Люди»: своё имя и описание правит сам участник, должность и учёную степень — администратор с правом `profiles.manage`, список содержит только заполненные анкеты своего вуза.
- Сервис расписания (`schedule`): учебные группы и занятия. Преподаватель сам задаёт и меняет свои занятия, студент видит занятия своей группы, администратор с ролью «Редактор расписания» ведёт группы и правит всё расписание.
- Подключение любого своего сервиса вуза через админку по шагам: адреса → ключ → запуск на сервере вуза (сервис сам публикует меню и роли) → включение. Тестовый сторонний сервис курсовых — в `test-data/coursework`.
- Интерфейс как набор сервисов: внизу только «Главная» и «Сервисы», каждый сервис — одна карточка. Любой сервис, кроме администрирования, можно выключить в админке — остальные и интерфейс продолжают работать.
- Тестовый вуз с подключённым расписанием.
- Автоматическое сохранение настроек подключённых сервисов в JSON-файлы.

Вход проверен пользователем на iPhone и в MAX Web через Firefox. Новые административные сценарии проверены локальными тестами; это не заменяет проверку развёрнутой версии в MAX. Сервис курсовых и подключение локальных сервисов проверены тестами сервиса и сквозным тестом против живого ядра; на стенде ещё не разворачивались (нужно DNS-имя). Расписание проверено тестами сервиса и сквозным тестом против живого ядра; на развёрнутом стенде в MAX ещё не проверялось. Сервис «Люди» реализован, и его сквозной путь (сессия ядра → service access → анкеты) проверен тестом против живого ядра в одном процессе; на развёрнутом стенде в MAX он ещё не проверялся.

Все модели используют общую metadata из `backend/database/base.py`.

## Пользователи и права

MAX ID связывается с внутренним UUID после серверной проверки `initData`. Для назначения прав используется UUID платформы, отображаемый в приложении, а не MAX ID.

- Членство связывает пользователя с вузом.
- Профиль (`student`, `teacher`, `admin`) определяет статус пользователя в этом вузе.
- Роль определяет разрешения в конкретном сервисе и выбранном профиле. Профиля `admin` самого по себе недостаточно для административных полномочий.
- Поддержка платформы рассматривает заявки и управляет статусами вузов. Администратор вуза управляет своим вузом через сервис администрации.

Секреты сервисов остаются на сервере. Клиент сервиса получает только service access token; ядро-клиент хранит свои токены в памяти.

## Запуск на сервере

Текущий Nginx настроен на IP `195.133.197.144` и уже выпущенный сертификат в `/var/lib/max-miniapp/letsencrypt`. Для другого адреса нужно согласованно изменить Nginx, адрес мини-приложения в MAX и настройки сервисов.

Нужны Docker Engine и Docker Compose. Внешние порты: 80/443 для оболочки, 8444 для администрации, 8445 для пульта оператора (плюс `127.0.0.1:8500` только на самом сервере). Backend, administration, user-profile, schedule и Redis не публикуют свои внутренние порты напрямую. Расписанию, как и «Людям», отдельный порт не нужен: Nginx проксирует `/schedule/api/` в контейнер `schedule`. Сервису «Люди» отдельный порт не нужен: его экраны рисует сама оболочка, iframe с отдельным origin здесь не участвует, поэтому Nginx проксирует префикс `/people/api/` на origin оболочки в контейнер `user-profile`.

### Настройки

При первом запуске из корня проекта:

```bash
cp .env.example .env
chmod 600 .env
nano .env
```

При обновлении существующий `.env` не перезаписывайте — добавьте недостающие переменные:

```dotenv
BOT_TOKEN=актуальный_токен_бота
CURSOR_SECRET_KEY=постоянный_случайный_секрет
JWT_ISSUER=https://195.133.197.144
CLOUD_BINDING_KEY=отдельный_постоянный_случайный_секрет
ADMINISTRATION_PROVISIONING_TOKEN=ещё_один_случайный_секрет
SHELL_ORIGIN=https://195.133.197.144
ADMINISTRATION_PUBLIC_ORIGIN=https://195.133.197.144:8444
USER_PROFILE_PROVISIONING_TOKEN=отдельный_секрет_сервиса_Люди
SCHEDULE_PROVISIONING_TOKEN=отдельный_секрет_сервиса_расписания
OPERATOR_PASSWORD=пароль_пульта_оператора_от_12_символов
```

Для каждого из пяти секретов отдельно выполните `openssl rand -hex 32`. Сохраните значения между перезапусками. `.env` не добавляется в Git. Compose передаёт `BOT_TOKEN` боту и как `MAX_BOT_TOKEN` ядру. Dev-вход, демо-наполнение и FakeRedis в основном Compose выключены.

`USER_PROFILE_PROVISIONING_TOKEN` обязателен: без него Compose не запустится, потому что этим токеном контейнер «Людей» читает свой binding у ядра. Так же обязателен `SCHEDULE_PROVISIONING_TOKEN` для контейнера расписания. Токены не взаимозаменяемы — каждый тип сервиса получает только свои bindings.

Подготовьте папку экспорта для пользователя backend (UID 10001):

```bash
mkdir -p services/connected
sudo chown 10001:10001 services/connected
sudo chmod 750 services/connected
```

### Запуск и диагностика

```bash
sudo docker compose config --quiet
sudo docker compose up -d --build
sudo docker compose ps
curl --fail https://195.133.197.144/api/v1/health
sudo docker compose logs --tail=80 backend administration web
```

Ожидаемый ответ healthcheck: `{"status":"ok"}`. Затем откройте мини-приложение кнопкой бота MAX. К боту должен быть привязан адрес оболочки; URL сайта не задаётся напрямую в коде кнопки бота.

SQLite ядра хранится в volume `core-data`, анкеты сервиса «Люди» — в `profile-data`, Redis — в `redis-data`. Обе базы работают в режиме WAL: прерванная запись откатывается при следующем открытии файла, поэтому перезапуск или падение контейнера не оставляет БД повреждённой, а параллельные запросы ждут освобождения записи вместо ошибки. Перед обновлениями схемы сохраняйте резервную копию БД. Не используйте `docker compose down -v` для обычного обновления: это удаляет volumes. При запуске создаются дополнительные таблицы и защищённые экземпляры администрации для существующих вузов; права владельца автоматически не назначаются.

## Пульт оператора

Всё, что раньше делалось на сервере через `docker compose exec … manage.py`, делается в веб-панели оператора. Это контейнер `operator`: тот же образ и та же БД, что у ядра, поднимается вместе с ним.

- **Со своего компьютера:** `https://195.133.197.144:8445` — вход по паролю `OPERATOR_PASSWORD` из `.env` (не короче 12 символов). Пять неверных попыток подряд блокируют вход с этого IP на 5 минут. Чтобы пускать только свои адреса, добавьте `allow <ваш IP>; deny all;` в блок порта 8445 в `web/configs/docker-nginx.conf`.
- **Без открытого порта:** панель слушает `127.0.0.1:8500` на сервере. С компьютера: `ssh -L 8500:127.0.0.1:8500 user@195.133.197.144`, затем `http://localhost:8500`.

Что умеет панель:

| Раздел | Что там |
| --- | --- |
| Сводка | счётчики, состояние контейнеров, вузы без владельца и с новыми заявками |
| Заявки вузов | одобрение (с правкой названия и сразу с сервисами платформы) и отказ с причиной |
| Вузы | подключение вуза без заявки; в карточке вуза — название, статус, владельцы, сервисы платформы, одобренные хосты, заявки на вступление, участники, группы, сервисы, роли, журнал |
| Пользователи | поиск по имени, UUID, MAX ID и вузу; добавление в вуз; права поддержки платформы |
| Журнал | все изменения на платформе |
| Обслуживание | проверка инвариантов, выгрузка `services/connected`, импорт групп, тестовый вуз |

Внутри вуза оператор может то же, что владелец вуза в администрировании. Запреты предметной логики остаются: например, нельзя снять последнего владельца или удалить непустую группу. В журнал действия пишутся как `operator`.

`manage.py` оставлен для автоматизации и аварийного доступа без браузера.

## Вход пользователя и заявки на вступление

При первом входе пользователь указывает имя и выбирает один или несколько вузов, в каждом — «Студент» или «Преподаватель», а студент ещё и группу. Вузы и группы выбираются только из зарегистрированных, свободного ввода нет. Если в вузе нет групп, подать студенческую заявку в него нельзя.

Заявка приходит карточкой (имя, профиль, группа) в «Администрирование» → «Заявки» вуза (нужно право `members.manage`) и в пульт оператора. «Одобрить» создаёт членство (или добавляет профиль) и записывает студента в выбранную группу; «Отклонить» — с необязательной причиной, которую видит пользователь. Пока ни одна заявка не одобрена, пользователь видит их статусы.

Переход в другой вуз или профиль — кнопкой в правом верхнем углу; там же «Вступить в другой вуз». Своего вуза нет в списке — «Подать заявку на подключение вуза» на экране регистрации; её рассматривает оператор в пульте.

### Владелец вуза

Заявитель одобренной заявки становится владельцем (профиль `admin` и роль `owner`). Владельца любому вузу назначает оператор: «Вузы» → вуз → «Обзор» → «Владельцы».

## Подключение сервисов и общая папка

Собственные реализации размещаются в `services/<имя>/`. Подключение через админку создаёт экземпляр сервиса в БД, связанный с вузом. Облачный экземпляр использует уже развёрнутый процесс платформы; локальный сервис работает в инфраструктуре вуза по одобренным адресам.

После успешного добавления, изменения или удаления настройки синхронизируются в:

```text
services/connected/<service_uuid>.json
```

Файл содержит UUID сервиса и вуза, тип, способ размещения, адреса API/клиента, профили, манифест и состояние `enabled`. Credentials и JWT в него не выгружаются. БД остаётся источником истины: ручная правка JSON не меняет сервис и будет перезаписана.

Файлы исключены из Git. Отключённый сервис сохраняется с `enabled: false`; физически удалённая запись удаляется из экспорта. При ошибке записи на диск транзакция БД сохраняется, ошибка попадает в лог. Восстановление файлов — пульт оператора → «Обслуживание» → «Выгрузить настройки сервисов».

Полная синхронизация также выполняется при запуске ядра. Добавление сервиса через админку не загружает его исходники и не запускает новые контейнеры. Новый тип сервиса требует реализации, настройки размещения и добавления в каталог разрешённых типов. Подробности: [services/SERVICES.md](services/SERVICES.md).

## Сервис «Люди»

Анкеты участников вынесены в отдельный сервис: контейнер `user-profile`, собственная SQLite в volume `profile-data`, свой provisioning-токен. Ядро остаётся источником пользователей, членств и профилей — сервис хранит только анкету и на каждый запрос спрашивает у ядра, кто пришёл и что ему можно.

Экземпляр создаётся вузу, а не платформе целиком. Владелец вуза подключает его в админке («Сервисы» → тип `user-profile`, размещение «облачное»): адреса, манифест, роль `profile_editor` и binding создаются автоматически. Адреса уже созданных экземпляров ядро приводит к `SHELL_ORIGIN` при каждом запуске, поэтому после смены адреса достаточно перезапустить backend. Если владельца ещё нет, оператор подключает сервис в пульте: «Вузы» → вуз → «Обзор» → «Сервисы платформы».

Операция идемпотентна: создаёт экземпляр, начальную роль `profile_editor`, credential и binding, а на повторном запуске лишь приводит адреса и манифест к текущим настройкам. Право `profiles.manage` автоматически не выдаётся никому: владелец назначает роль «Редактор анкет» конкретному администратору в админке. Без неё должность и учёную степень не изменит даже профиль `admin`.

Что видит участник:

- «Профиль» — своя анкета: имя и описание правит сам владелец анкеты. Имя вводится пользователем и не считается подтверждённым ФИО. Пока человек не поменял имя в анкете, показывается имя из регистрации (заявки на вступление) — заполнять анкету, чтобы попасть в «Людей», не нужно.
- Фото: «Загрузить фото» в своём профиле. Картинка уменьшается на устройстве до 320×320, хранится в ядре (одна на все вузы) и видна участникам общих вузов. Фото из MAX не используется.
- Удаление участника из вуза удаляет его анкету в этом вузе и имя из его заявок: при повторном добавлении того же UUID анкета будет новой. Аватар при этом сохраняется — он общий для всех вузов.
- «Люди» — участники своего вуза, заполнившие анкету, с поиском по имени и должности. Анкеты других вузов недоступны, а снятое членство сразу убирает участника из списка и закрывает его карточку.

Как это устроено в развёрнутой версии:

- Оболочка получает service access token у ядра и обращается к `https://<origin>/people/api/v1/...`; Nginx проксирует этот префикс в контейнер. Отдельного origin и iframe нет — экраны рисует сама оболочка.
- Сервис на каждый защищённый запрос читает свой binding, обменивает credential на machine-токен и выполняет online introspection. Недоступность ядра даёт `503`, а не показ непроверенных анкет.
- Анкеты хранятся в разрезе `(вуз, экземпляр, пользователь)` и переживают перезапуск контейнера. Одновременная правка одной анкеты разрешается по `ETag`/`If-Match`: второй запрос получает `412`, а не молча перетирает первый.

Диагностика:

```bash
sudo docker compose logs --tail=80 user-profile
sudo docker compose exec user-profile python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8200/api/v1/health').read())"
```

Если в логах `Хранилище /data/profiles.db недоступно для записи`, значит volume `profile-data` принадлежит root, а процесс работает под UID 10003. Это бывает с томом, созданным до появления образа. Тома с анкетами в этом случае ещё нет, поэтому его можно пересоздать:

```bash
sudo docker compose stop user-profile
sudo docker volume rm $(basename $(pwd))_profile-data
sudo docker compose up -d user-profile
```

Контракт сервиса — [SPEC.md](docs/services/user-profile/SPEC.md), реализация и отличия от контракта — [IMPLEMENTATION.md](docs/services/user-profile/IMPLEMENTATION.md).

## Сервис расписания

Контейнер `schedule`, собственная SQLite в volume `schedule-data`, свой provisioning-токен. Экземпляр ставится вузу в админке («Сервисы» → «Расписание», облачное) или в пульте оператора («Вузы» → вуз → «Обзор» → «Сервисы платформы»).

Кто что делает:

- **Все участники** — студенты, преподаватели, администраторы — видят все учебные группы, их состав и расписание любой группы. Отдельная роль для просмотра не нужна. По умолчанию студент видит занятия своей группы, преподаватель — свои занятия, администратор — все.
- **Администратор с ролью «Редактор расписания»** (`schedule_editor`) создаёт, меняет и удаляет любые занятия. Преподаватели и студенты расписание только смотрят.
- **Администратор с ролью «Редактор групп»** (`group_editor`) создаёт, переименовывает и удаляет группы и меняет их состав прямо в разделе «Группы» расписания. Администраторы с правом `groups.manage` по-прежнему ведут группы и в «Администрирование» → «Группы».

Роли назначаются только профилю «Администратор»: админка вуза или пульт → «Роли» → «Расписание».

Группы открываются кнопкой «Группы» на экране расписания: там поиск по группам, состав раскрывается по нажатию, «Расписание группы» открывает её занятия. Студент состоит максимум в одной группе. Непустую группу или группу, на которую ссылается занятие, удалить нельзя. В группу попадают только участники с профилем «Студент», преподавателями занятия — только участники с профилем «Преподаватель»: сервис проверяет это у ядра.

Ядро при каждом запуске приводит адреса и меню облачных экземпляров расписания к `SHELL_ORIGIN`. Экземпляр прежней демо-заглушки расписания (порт 8443, удалена) при этом превращается в настоящее расписание вуза.

Диагностика:

```bash
sudo docker compose logs --tail=80 schedule
curl -i https://195.133.197.144/schedule/api/v1/health
```

Контракт — [SPEC.md](docs/services/schedule/SPEC.md), реализация и отличия — [IMPLEMENTATION.md](docs/services/schedule/IMPLEMENTATION.md).

## Подключение своего сервиса

К вузу можно подключить любой свой сервис: он работает на сервере вуза, а платформа только регистрирует его и проверяет доступ. Порядок — `docs/core/CORE_API_SPEC.md` §7:

1. **Оператор** одобряет DNS-имя вуза: пульт → «Вузы» → вуз → «Обзор» → «Хосты своих сервисов». IP-адреса ядро не принимает.
2. **Администратор вуза**: «Администрирование» → «Сервисы» → «Подключить сервис» → «Свой сервис». Указывает название, код (например, `library`), кому доступен сервис и адреса на одобренном хосте. Администраторам вуза сервис доступен всегда: профиль «Администратор» добавляется автоматически, а меню администратор видит и без ролей сервиса — что ему можно внутри, решает сам сервис. Сервис создаётся выключенным, тип — `custom.<код>`.
3. В карточке сервиса — шаги подключения. «Выдать ключ» один раз показывает строки `.env` для сервера вуза (`CORE_URL`, `SHELL_ORIGIN`, `SERVICE_CLIENT_ID`, `SERVICE_CLIENT_SECRET`, адреса).
4. Сервис на сервере вуза обменивает ключ на machine-токен, создаёт свои роли и публикует меню через machine API ядра. Права своего сервиса — только вида `<код>.<право>`: чужие (расписания, администрирования) ядро не примет. Меню можно задать и вручную в карточке («Меню вручную (JSON)»).
5. Администратор нажимает «Включить». Сервис появляется в «Все сервисы» у профилей, которым он доступен, и открывается внутри приложения (iframe) по протоколу из `docs/services/sdk/SPEC.md` §7.

Пользователи ходят в сервис напрямую, поэтому ему нужен HTTPS на одобренном DNS-имени.

Каркас для нового сервиса — [docs/services/sdk/service-template](docs/services/sdk/service-template/README.md): платформенная часть уже готова, остаётся код сервиса и интерфейс.

Пример готового стороннего сервиса — курсовые в `test-data/coursework/`: поднимаются отдельно своим `docker compose`, пошагово — в [его README](test-data/coursework/README.md).

## Учебные группы

Группы — сущность ядра, как участники и профили. Ведёт их администратор вуза (право `groups.manage` у владельца и «Администратора участников»): «Администрирование» → «Группы» (создание, состав, студенты без группы) и поле «Группа» у студента на вкладке «Участники». Студент состоит максимум в одной группе; новый студент сначала без группы.

Сервисы читают группы через machine API ядра (scope `groups:read`): `GET /api/v1/internal/service/{id}/groups`, `.../groups/{group_id}/members`, поле `group_ids` в introspection и `groups` в профилях участника. Расписание групп больше не хранит.

Перенос групп, созданных раньше в расписании (UUID сохраняются, занятия не теряют связи):

```bash
sudo docker compose exec -T schedule python -m app.export_groups > groups.json
```

Затем загрузите `groups.json` в пульте оператора: «Обслуживание» → «Импорт групп из расписания».

## Включение и отключение сервисов

Любой сервис, кроме администрирования, выключается в админке («Сервисы» → «Выключить»). Сессии выключенного сервиса завершаются, его карточка пропадает у пользователей, остальные сервисы работают как прежде. Если выключены «Люди», курсовые и расписание принимают ID преподавателя вручную, а ID пользователя показывается на главной.

## Тестовый вуз

Пульт оператора → «Обслуживание» → «Тестовый вуз», выберите пользователя. Операция создаёт «Тестовый университет» с сервисом расписания и назначает профиль студента. Повторный запуск не дублирует записи и сохраняет существующие профили.

## Разработка и обновление

Исходники интерфейса находятся в `frontend/src`. Для просмотра оформления используйте `npm ci` и `npm run dev` из `frontend/`. Для проверки производственной сборки: `npm run build` и `npm run preview`. В производственном режиме вход доступен только через MAX.

После изменения дизайна пересоберите контейнер `web`. Имена CSS и JS версионируются Vite автоматически.

## Тесты

В отдельном виртуальном окружении установите `backend/requirements.txt`, `services/administration/requirements.txt` и `httpx`. Из `backend/` запускайте наборы отдельными процессами: они задают разные временные БД и настройки.

```bash
python -m unittest tests.test_max_integration -v
python -m unittest tests.test_administration_flow -v
python -m unittest tests.test_platform_core -v
python -m unittest tests.test_service_files -v
python -m unittest tests.test_custom_services -v
python -m unittest tests.test_join_requests -v
python -m unittest tests.test_operator_panel -v
```

Из `services/administration/`:

```bash
python -m unittest tests.test_core_client -v
```

Из `services/user-profile/` (нужны `services/user-profile/requirements.txt` и `httpx`):

```bash
python -m unittest discover -s tests -t . -v
PYTHONPATH=../../backend python -m unittest tests.test_integration_core -v
```

Первый набор проверяет сам сервис на заглушке ядра: доступ, версии анкет, гонку правок, каталог и перезапуск на существующем томе. Второй поднимает настоящее ядро в том же процессе и прогоняет весь путь: установку экземпляра командой оператора, сессию сервиса, `GET /api/v1/service`, сохранение анкеты, выдачу роли `profile_editor` и её действие на уже выданный токен, отказ токену чужого сервиса, снятие членства и logout.

Из `test-data/coursework/` (дополнительно `python-multipart`):

```bash
python -m unittest discover -s tests -t . -v
PYTHONPATH=../../backend python -m unittest tests.test_integration_core -v
```

Первый набор — права, состояния работы, версии, загрузка и проверка PDF, лимиты, idempotency, очистка файлов и CORS на заглушке ядра. Второй — полный путь подключения через администрирование: регистрация, ключ, самостоятельная публикация меню и роли, включение, загрузка работы.

Из `services/schedule/` (те же зависимости):

```bash
python -m unittest discover -s tests -t . -v
PYTHONPATH=../../backend python -m unittest tests.test_integration_core -v
```

Первый набор проверяет доступ по профилям, группы и состав, занятия преподавателя, версии, idempotency, курсоры и изоляцию вузов на заглушке ядра. Второй — установку командой оператора, выдачу роли `schedule_editor`, проверку профилей через ядро, занятие преподавателя в расписании студента и превращение прежней заглушки в настоящее расписание.

Из `frontend/`:

```bash
npm test
npm install
npx playwright install chromium
npm run test:design
```

Браузерные тесты используют тестовый API и не доказывают работу на всех клиентах MAX. Старый `backend/run_all_tests.py` предназначен для отдельного HTTP-стенда с dev-входом; это не инструкция запуска рабочего сервера.

## Сертификаты

Nginx использует сертификат `/etc/letsencrypt/live/max-miniapp/` из подключённого хранилища. Проверка и продление:

```bash
sudo docker compose run --rm certbot renew --dry-run
sudo docker compose run --rm certbot renew
sudo docker compose exec web nginx -t && sudo docker compose exec web nginx -s reload
```

Планировщик продления на сервере настраивается отдельно. Сертификат `bot/russian_trusted_root_ca_pem.crt` — дополнительный корневой сертификат для Node.js, а не сертификат сайта.
