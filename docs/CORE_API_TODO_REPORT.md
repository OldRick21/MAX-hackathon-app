## 3. Предлагаемые решения, которые уточняют манифест

1. **Профиль — контекст внутри вуза, не анкета.** В MVP три фиксированных кода: `admin`, `teacher`, `student`. Вуз назначает и снимает их у участника. Создание произвольных типов профилей отложено: формулировку «создать профиль» в MVP трактуем как назначение одного из трёх существующих типов. Сервис «Профиль пользователя» хранит ФИО, должность и степень отдельно от этой модели.
2. **JWT не заменяет серверную сессию.** Access и refresh остаются JWT, как в манифесте, но отзыв и ротация опираются на БД. Пары для ядра и каждого сервиса различаются по audience и назначению. Для machine JWT refresh не нужен: бекенд повторяет обмен по credential.
3. **Браузер не получает привилегии сервиса.** Ядро-клиент хранит свои токены и refresh сервисов только в памяти. В iframe передаётся короткий access именно этого экземпляра и профиля. API сервиса не обязан принимать core access.
4. **Две границы управления.** Публичный `/api/v1/internal` обслуживает backend-to-backend запросы только в пределах собственного экземпляра. Закрытый `/api/v1/institution/{id}/internal` требует приватного сетевого пути, machine token сервиса администрирования этого вуза и `X-Actor-Token` администратора. Публичный ingress всегда возвращает для этого префикса `404`.
5. **Вход в MAX не доказывает принадлежность к вузу.** Он создаёт только аккаунт. Добавление в вуз выполняет администратор по внутреннему UUID уже зарегистрированного пользователя. Приглашения, синхронизация с кадровой системой и поиск глобального каталога пользователей вне MVP.
6. **Начальная регистрация — вручную.** Запрос на подключение вуза обрабатывает оператор платформы; после проверки он создаёт запись вуза, обязательный экземпляр администрирования, первый профиль `admin` и роль `owner`. Самообслуживание регистрации/одобрения вузов и API оператора платформы не нужны для MVP. Хранение и чтение реестра входят в ядро.
7. **Один экземпляр типа на вуз в MVP.** Это ограничение БД, не процесса. Сервис может иметь несколько меню. Все три облачных типа и локальный `coursework` заранее перечислены в каталоге, полноценного магазина нет.
8. **Сервис администрирования защищён от удаления и отключения.** Нельзя снять последнего владельца вуза. Его системные роли и permissions нельзя переписать публичным API. Управление локальными credentials доступно вузу; облачными — только оператору платформы.

Значения TTL, лимиты, обязательный русский перевод, ограничение одного экземпляра типа и ручное подключение — проектные предложения этого документа, а не извлечённые из кода требования. Их можно изменить до реализации; это не неявные факты о существующей системе.

## 4. Облачные экземпляры и локальный демонстратор

Для вузов A и B один backend расписания обслуживает два UUID экземпляров. Один и тот же URL backend допустим. Запрос не выбирает вуз по произвольному заголовку: backend сначала проверяет подпись, `aud=service:{service_id}`, тип JWT и соответствие `institution_id`, затем использует этот контекст в доступе к данным. Уникальные ключи и запросы к БД сервиса включают tenant-контекст. Отдельный процесс на вуз не нужен.

У каждого логического экземпляра — собственный machine credential, роли и manifest. Компрометация credential A не даёт доступ к API ядра от лица B, хотя компрометация всего общего процесса остаётся риском для всех его tenants. Поэтому cloud deployment — граница доверия платформы; это не физическая изоляция клиентов.

Локальный `coursework` использует тот же механизм выдачи пользовательских токенов и тот же публичный internal API ядра. Вуз разворачивает backend сам и регистрирует HTTPS-адреса, доступные браузеру пользователя. «Локальный» означает место размещения: адрес из закрытой LAN без VPN не станет доступным внутри MAX автоматически. Reverse tunnel, универсальный proxy через ядро и протокол API загрузки файлов сейчас не проектируются.

## 5. Персональные данные: ответ на TODO

152-ФЗ требует определить цели, основания и необходимый объём обработки (ст. 5–6); предусмотреть защиту (ст. 19), права субъектов и прекращение обработки (ст. 14, 20–21), проверить уведомление Роскомнадзора (ст. 22). Для данных граждан РФ отдельно проверяется локализация баз при сборе (ст. 18 ч. 5), для зарубежных получателей — трансграничная передача (ст. 12). Договор с вузом должен установить роли оператора и обработчика и условия поручения; аутентификация через MAX сама по себе не является согласием на все цели обработки. Основание — [официальная публикация текста 152-ФЗ у Минтруда](https://mintrud.gov.ru/docs/laws/130), [информация Роскомнадзора об уведомлении](https://82.rkn.gov.ru/directions/pers/p15375/).

Это предварительное определение применимых вопросов, не заключение о соответствии. Доступ к полному актуальному консолидированному тексту через официальные сайты во время проверки был нестабилен; конкретные исключения, новые редакции и применимость к участникам проекта необходимо подтвердить перед реальным пилотом. Нельзя считать юридический TODO закрытым только наличием JWT и российского сервера.

Практические проектные решения:

- Ядро сохраняет UUID, MAX user ID, членство, права и технические записи сессий. Имя, телефон, avatar, IP из `initData` и весь сырой payload не сохраняет. В сервисные JWT попадают UUID и права, без MAX ID и анкеты.
- Для демонстрации использовать вымышленные образовательные данные. Если используется настоящий аккаунт MAX, его идентификатор всё равно относится к обрабатываемым данным: назвать весь стенд обезличенным нельзя.
- Предварительно выбрать размещение основной БД, резервных копий и содержащих данные журналов в РФ; описать доступ обслуживающих лиц и поставщиков. География сама по себе не исчерпывает требования закона.
- Реестр retention, удаление/исправление по обращениям и журнал юридических оснований — процессы оператора до пилота. В контракт не добавлена фиктивная галочка `consent=true`: основание зависит от отношений с вузом и целей конкретного сервиса.
- Сроки хранения образовательных документов, необходимость отдельного согласия на распространение анкет и допустимость доступа к чужим профилям должен определить владелец соответствующего сервиса вместе с вузом. Его API здесь не описывается.

## 6. Что сознательно за пределами контракта

Нет API бота, MAX, SDK, сервиса администрирования как приложения, расписания, анкеты, групп и курсовых. Есть только операции, **которые обслуживает ядро**, в том числе когда клиентом выступает backend другого компонента. Наличие private API ядра не описывает публичный API сервиса администрирования.

Не входят: магазин сторонних типов, модерация сервисов, произвольные профили, публичная регистрация вузов, автоматическая проверка локальных backend, межвузовские роли, физическое удаление образовательных данных и автоматический deployment. Операции удаления вуза/аккаунта не маскируются удалением членства: их согласованный межсервисный жизненный цикл требует отдельного проектирования.

## 7. Порядок реализации после согласования

1. Подключить роутеры, миграции PostgreSQL и единые ответы об ошибках; настроить публичный и приватный ingress.
2. Реализовать MAX login, пары JWT, ротацию, logout и чтение своего аккаунта.
3. Добавить ручной bootstrap одного вуза, членство и контекст профиля; затем реестр сервисов/меню.
4. Реализовать machine credentials, JWKS, service sessions и introspection.
5. Реализовать private управление с actor-проверкой, роли, защиту последнего owner и отзыв credentials.
6. Проверить сценарии из §10 спецификации. Только затем связывать остальные компоненты с этим контрактом.

Ни один из этих шагов реализации в данной работе не выполнялся.
