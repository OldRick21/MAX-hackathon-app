# Сервис расписания: реализация

Код — `services/schedule/`. Контракт — [SPEC.md](SPEC.md) и [OPENAPI.yaml](OPENAPI.yaml); здесь только то, что в реализации устроено иначе или уточнено.

## Размещение

- Контейнер `schedule` (порт 8300, UID 10004), SQLite `/data/schedule.db` в volume `schedule-data`, режим WAL.
- `api_base_url` = `${SHELL_ORIGIN}/schedule/api/v1`, `client_base_url` = `${SHELL_ORIGIN}`. Экраны рисует оболочка, iframe и отдельного origin нет; Nginx проксирует `/schedule/api/` в контейнер. HTML-entrypoint `/schedule` не реализован.
- Binding процесс читает у ядра токеном `SCHEDULE_PROVISIONING_TOKEN`. Каждый защищённый запрос проходит online introspection; недоступность ядра — `503`.
- Ядро при запуске приводит адреса, манифест, профили и начальную роль всех облачных экземпляров `schedule` к настройкам платформы (`registry.sync_cloud_instance`). Так прежняя статическая заглушка на 8443 становится настоящим расписанием.

## Права и меню — по контракту

Меню `schedule` (student, teacher) и `schedule_admin` (admin, `schedule.read_all`), роль `schedule_editor` (admin и teacher, см. ниже) — сервис публикует сам при старте. Студент видит свою текущую группу и её занятия, преподаватель — названия групп и свои занятия, admin — всё только с `schedule.read_all`; занятия пишет только admin с `schedule.write`. Роли прежних версий (`group_editor`) и права, которых больше нет, сервис убирает сам.

## Отличие от контракта: правка расписания преподавателем

Роль одна — «Редактор расписания» (`schedule_editor`, права `schedule.read_all` и `schedule.write`), но разрешена двум профилям: admin (по контракту) и teacher. Назначение делается на профиль человека, поэтому администратор включает правку конкретному преподавателю, назначив ему роль в профиле «Преподаватель» в «Ролях», и выключает, сняв её. С ролью преподаватель видит и правит все занятия, без неё — только смотрит свои.

Прежние версии публиковали для преподавателя отдельную роль `teacher_editor`. При запуске сервис переносит её назначения на `schedule_editor` (onboarding, `RENAMED_ROLES`) и удаляет её — у преподавателей, которым правка была включена, она сохраняется.

## Отличие от контракта: группы в ядре

Учебные группы — сущность ядра (их выбирают при заявке на вступление, ведёт администрирование вуза). Сервис читает их через machine API (`groups:read`), своя группа студента — `group_ids` из introspection. Поэтому:

- `POST/PATCH/DELETE /api/v1/schedule/groups…` и `GET/PUT …/students` не реализованы (405); группы и состав меняются в администрировании (`groups.manage`);
- в роль `schedule_editor` право `groups.manage` не входит.

`GET /schedule` отдаёт статический HTML-клиент для iframe (занятия недели); оболочка рисует экраны сама.

## Уточнения

- Время принимается в RFC 3339 с любым смещением и хранится в UTC как `YYYY-MM-DDTHH:MM:SSZ`; доли секунды отбрасываются.
- Профили (`student` для состава, `teacher` для `teacher_ids`) проверяются через machine API ядра до локальной транзакции, по одному запросу на UUID.
- Idempotency-Key обязателен для POST (иначе `400`) и хранится 24 часа в разрезе (вуз, экземпляр, пользователь).
- Курсоры подписаны HMAC от provisioning-токена, живут 15 минут и привязаны к пользователю, профилю, периоду и фильтрам.
- Состав группы меняется в администрировании ядра; в группу попадают только студенты вуза.
- Аудита DELETE и rate limiting нет.

## Группы в ядре

Группы перенесены в ядро (CORE_API_SPEC §7.1). Сервис их не хранит и не меняет: `GET /api/v1/schedule/groups` отдаёт все группы ядра любому участнику, операции создания, переименования, удаления и состава из сервиса убраны. Роль `schedule_editor` больше не содержит `groups.manage`. Старые таблицы остаются для `python -m app.export_groups`.
