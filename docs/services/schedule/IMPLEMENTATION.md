# Сервис расписания: реализация

Код — `services/schedule/`. Контракт — [SPEC.md](SPEC.md) и [OPENAPI.yaml](OPENAPI.yaml); здесь только то, что в реализации устроено иначе или уточнено.

## Размещение

- Контейнер `schedule` (порт 8300, UID 10004), SQLite `/data/schedule.db` в volume `schedule-data`, режим WAL.
- `api_base_url` = `${SHELL_ORIGIN}/schedule/api/v1`, `client_base_url` = `${SHELL_ORIGIN}`. Экраны рисует оболочка, iframe и отдельного origin нет; Nginx проксирует `/schedule/api/` в контейнер. HTML-entrypoint `/schedule` не реализован.
- Binding процесс читает у ядра токеном `SCHEDULE_PROVISIONING_TOKEN`. Каждый защищённый запрос проходит online introspection; недоступность ядра — `503`.
- Ядро при запуске приводит адреса, манифест, профили и начальную роль всех облачных экземпляров `schedule` к настройкам платформы (`registry.sync_cloud_instance`). Так прежняя статическая заглушка на 8443 становится настоящим расписанием.

## Отличие от контракта: занятия задают преподаватели

По SPEC §1 занятия пишет только admin с `schedule.write`. В реализации:

| Кто | Чтение | Запись занятий | Группы |
| --- | --- | --- | --- |
| student | занятия своей группы; своя группа | — | — |
| teacher | свои занятия (он в `teacher_ids`); все группы вуза | создаёт занятия, где он сам в `teacher_ids`; меняет и удаляет только такие занятия и не может убрать из них себя | — |
| admin + `schedule.read_all` | всё | — | чтение |
| admin + `schedule.write` | всё | любые занятия | чтение |
| admin + `groups.manage` | группы | — | создание, переименование, удаление, состав |

Роль `schedule_editor` по-прежнему содержит все три permission. Отдельной роли преподавателю не нужно: профиль `teacher` подтверждает ядро. Чужое занятие для преподавателя — `404` и при чтении, и при записи. Попытка создать занятие без себя — `422 VALIDATION_ERROR`.

## Уточнения

- Время принимается в RFC 3339 с любым смещением и хранится в UTC как `YYYY-MM-DDTHH:MM:SSZ`; доли секунды отбрасываются.
- Профили (`student` для состава, `teacher` для `teacher_ids`) проверяются через machine API ядра до локальной транзакции, по одному запросу на UUID.
- Idempotency-Key обязателен для POST (иначе `400`) и хранится 24 часа в разрезе (вуз, экземпляр, пользователь).
- Курсоры подписаны HMAC от provisioning-токена, живут 15 минут и привязаны к пользователю, профилю, периоду и фильтрам.
- Состав группы читают и меняют только с `groups.manage`. Интерфейс предлагает людей из анкет и ввод UUID; не-студентов отклоняет сервер.
- Аудита DELETE и rate limiting нет.
