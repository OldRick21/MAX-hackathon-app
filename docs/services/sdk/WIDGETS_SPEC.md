# Виджеты главного экрана

Версия `0.2.0`, 29 сентября 2026. **Статус: реализовано в ядре, администрировании, оболочке и сервисах проекта** (разбор отличий — в конце документа). Расширяет [CORE_API_SPEC.md](../../core/CORE_API_SPEC.md) §6–§7 (manifest, список сервисов оболочки) и [SDK/SPEC.md](SPEC.md) §2, §4 (machine API, проверка запроса). Всё, что здесь не переопределено, работает по правилам этих документов: ошибки, ETag/If-Match, request_id, locale, лимиты.

## 1. Назначение

Виджет — карточка сервиса на главном экране оболочки: «Сегодня: 3 пары», «Работ на проверке: 5», карточка своего профиля. **Главный экран состоит только из виджетов**: у оболочки нет своих встроенных блоков. Виджет показывает сводку и ведёт в меню сервиса. Виджет — средство навигации, а не авторизации: данные для него сервис отдаёт своим API с обычной проверкой прав.

Принципы:

- **Сервис объявляет виджеты сам** — в своём manifest, рядом с меню, через тот же `PUT .../manifest`.
- **Сервис сам включает и выключает виджеты** для каждого профиля (`student`, `teacher`, `admin`) отдельным вызовом machine API, без повторной публикации manifest. Показ отдельным ролям сервиса задаётся через `required_permissions`.
- **Администратор вуза тоже включает и выключает виджеты** для каждого профиля — в администрировании, через private API ядра (§5). Уровни независимы: виджет показывается, только если его не выключил ни сервис, ни администратор.
- **Оболочка рисует виджеты сама** по одному из фиксированных шаблонов (§7), с данными из API сервиса. HTML и скрипты сервиса на главный экран не попадают, iframe-виджетов нет: главная открывается быстро, выглядит единообразно и не исполняет чужой код в контексте оболочки.
- **Ядро фильтрует, но не хранит данные виджетов.** Ядро знает, какие виджеты есть и кому они включены; содержимое (занятия, работы, анкеты) остаётся в сервисе.
- Выключенный или удалённый сервис — его виджеты пропадают с главной сразу, как и его меню.

Карточку профиля пользователя (имя, фото, группа, должность) даёт сервис «Люди» виджетом шаблона `profile` (§7).

## 2. Когда виджет виден

Виджет показывается пользователю в выбранном профиле, если выполнены **все** условия:

1. Вуз `active`, экземпляр сервиса включён и не удалён, профиль входит в `supported_profiles` экземпляра.
2. У пользователя есть этот профиль в вузе.
3. Профиль перечислен в `widget.profiles` (manifest).
4. Виджет включён для этого профиля **и сервисом (§4), и администратором вуза (§5)**. После публикации manifest новый виджет включён на обоих уровнях для всех своих профилей.
5. У пользователя в этом профиле есть **все** `widget.required_permissions` — так же, как у меню (CORE_API_SPEC §6 п.4; учитываются только роли, допустимые профилю).

Администратор не видит «всё»: у него те же пять условий, что у остальных профилей.

## 3. Объявление в manifest

Manifest получает необязательный массив `widgets` рядом с `menus`. Прежние manifest без `widgets` остаются валидными.

```json
{
  "titles": {"ru": "Расписание"},
  "menus": [ ... ],
  "widgets": [
    {
      "id": "today",
      "titles": {"ru": "Сегодня", "en": "Today"},
      "kind": "events",
      "size": "wide",
      "profiles": ["student", "teacher"],
      "required_permissions": [],
      "data_path": "/schedule/widgets/today",
      "open_menu": "schedule",
      "order": 0
    },
    {
      "id": "today_admin",
      "titles": {"ru": "Занятия сегодня"},
      "kind": "stat",
      "size": "small",
      "profiles": ["admin"],
      "required_permissions": ["schedule.read_all"],
      "data_path": "/schedule/widgets/today-admin",
      "open_menu": "schedule_admin",
      "order": 1
    }
  ]
}
```

| Поле | Тип и ограничения | Смысл |
| --- | --- | --- |
| `id` | код `^[a-z][a-z0-9_.-]{0,63}$`, уникален среди виджетов экземпляра | Постоянный идентификатор; по нему хранится включение (§4) |
| `titles` | LocalizedText, `ru` обязателен, до 200 символов | Заголовок карточки |
| `kind` | `profile` \| `events` \| `list` \| `stat` \| `progress` \| `notice` | Шаблон отрисовки и формат данных (§7) |
| `size` | `small` \| `wide` | `small` — половина строки на широком экране, `wide` — вся строка; на телефоне оба во всю ширину |
| `profiles` | непустое подмножество `supported_profiles` экземпляра | Кому виджет вообще может показываться |
| `required_permissions` | коды из словаря типа, до 16 | Все обязательны; так виджет адресуется ролям сервиса |
| `data_path` | абсолютный путь **относительно `api_base_url`** экземпляра, те же запреты, что у `entrypoint_path` (без query, fragment, `..`, `//`, `\`, percent-обходов) | Откуда оболочка берёт данные (§7) |
| `open_menu` | `id` меню этого же manifest или `null` | Куда ведёт нажатие на карточку; меню должно быть видимо пользователю, иначе карточка не кликабельна |
| `order` | целое 0..10000 | Порядок внутри сервиса; итоговый порядок на главной — §8 |

Проверки ядра при `PUT .../manifest` (ошибки — `422 VALIDATION_ERROR` с `details.path`):

- не более **8** виджетов на экземпляр; неизвестные поля отклоняются;
- `open_menu` ссылается на существующее меню, а профили виджета — подмножество профилей этого меню (иначе клик вёл бы в недоступный раздел);
- если у включённого экземпляра нет меню, manifest отклоняется как и сейчас (`409 MANIFEST_REQUIRED`); виджеты без меню смысла не имеют.

Manifest администрирования по-прежнему задаёт платформа; виджеты администрирования, если появятся, объявляет каталог ядра.

## 4. Включение и выключение (machine API)

Сервис включает и выключает свои виджеты для профилей отдельно от manifest: например, администратор расписания в интерфейсе сервиса скрывает «Сегодня» у преподавателей. Кто внутри сервиса вправе это делать, решает сам сервис (рекомендуется отдельное право `<тип>.widgets.manage` в словаре типа и роль с ним). Ядро проверяет только machine token экземпляра.

Scope — `manifest:write` (тот же уровень доверия, что и публикация manifest). Для `administration` запись запрещена: `403 PROTECTED_RESOURCE`. Чужой `service_id` — `404`.

### 4.1. Прочитать виджеты и их включение

`GET /api/v1/internal/service/{service_id}/widgets`

```json
{
  "items": [
    {
      "id": "today",
      "profiles": ["student", "teacher"],
      "visibility": {"student": true, "teacher": false},
      "admin_visibility": {"student": true, "teacher": true}
    },
    {
      "id": "today_admin",
      "profiles": ["admin"],
      "visibility": {"admin": true},
      "admin_visibility": {"admin": true}
    }
  ],
  "next_cursor": null
}
```

Заголовок `ETag` — версия набора включений всего экземпляра (обоих уровней). `visibility` — уровень сервиса, `admin_visibility` — уровень администратора вуза, только для чтения: сервис видит, что его виджет скрыт вузом, но не может это отменить. Ключи — ровно `profiles` виджета.

### 4.2. Изменить включение одного виджета

`PUT /api/v1/internal/service/{service_id}/widgets/{widget_id}/visibility`, заголовок `If-Match` (ETag из §4.1, иначе `428`/`412`):

```json
{"visibility": {"student": true, "teacher": false}}
```

- Передаются **все** профили виджета (`true`/`false`); лишний или пропущенный профиль — `422 VALIDATION_ERROR`.
- Неизвестный `widget_id` — `404`.
- Меняется только уровень сервиса; `admin_visibility` не затрагивается.
- Ответ `200` — элемент как в §4.1, новый `ETag` набора.
- Изменение действует сразу: следующий запрос оболочки (§6) его учитывает.
- Операция пишется в журнал вуза (`widget.visibility`, до/после, `machine_credential_id`, `request_id`).

### 4.3. Связь с manifest

- Новый `id` в manifest → включён на обоих уровнях для всех своих профилей.
- `id` удалён из manifest → его включения удаляются.
- Из `profiles` виджета убран профиль → ключ профиля удаляется; добавлен → включён на обоих уровнях.
- Повторная публикация того же manifest включения **не сбрасывает**: выключенное сервисом или администратором остаётся выключенным.

Выключение для всех профилей сразу — `PUT` со всеми значениями `false`. Удалять виджет из manifest ради этого не нужно.

## 5. Настройка администратором вуза (private API)

Администратор вуза настраивает главную для своих пользователей: например, скрывает «Работы на проверке» у преподавателей, пока курсовые не начались. Интерфейс — в администрировании, вкладка «Сервисы», блок «Виджеты на главной» у каждого сервиса: таблица «виджет × профиль» с переключателями. Если виджет выключен самим сервисом, переключатель показывает это («выключен сервисом») и не может его включить.

Операции — фасад private API ядра (CORE_API_SPEC §2.3, machine token администрирования + `X-Actor-Token`):

| Метод и путь (от `/api/v1/institution/{institution_id}/internal`) | Право | Смысл |
| --- | --- | --- |
| `GET /services/{service_id}/widgets` | `services.read` | Виджеты экземпляра: определения, `service_visibility` (уровень сервиса, чтение) и `visibility` (уровень вуза), `ETag` набора |
| `PUT /services/{service_id}/widgets/{widget_id}/visibility` | `services.manage` | Тело `{"visibility": {профиль: true\|false}}` со всеми профилями виджета, `If-Match` обязателен; ответ — новый список и `ETag` |

Ответ `GET`:

```json
{
  "items": [
    {
      "id": "today", "titles": {"ru": "Сегодня"}, "kind": "events", "size": "wide",
      "profiles": ["student", "teacher"], "required_permissions": [],
      "service_visibility": {"student": true, "teacher": true},
      "visibility": {"student": true, "teacher": false}
    }
  ],
  "next_cursor": null
}
```

Ошибки — как у остальных операций private API: чужой экземпляр или виджет — `404`, нет права — `403`, неверные профили — `422`, `428`/`412` по `If-Match`. Изменение пишется в журнал вуза (`widget.visibility`, `layer: admin`, до/после, actor). В фасаде администрирования операции доступны как `GET/PUT /api/v1/administration/services/{service_id}/widgets...` с теми же телами.

Владелец вуза и технический администратор имеют `services.manage`; администратор участников (`membership_admin`) видит настройки только при `services.read` — в MVP у него этого права нет, и блок не показывается.

## 6. Список виджетов для оболочки (API ядра)

`GET /api/v1/institution/{institution_id}/widgets?profile=student&locale=ru` (core access)

```json
{
  "items": [
    {
      "service_id": "c5d62394-acef-45b3-82f9-8e4e18f63f2b",
      "service_type": "schedule",
      "widget_id": "today",
      "display_name": "Сегодня",
      "locale": "ru",
      "kind": "events",
      "size": "wide",
      "data_url": "https://shell.example/schedule/c5d62394-acef-45b3-82f9-8e4e18f63f2b/api/v1/schedule/widgets/today",
      "open_menu": "schedule",
      "order": 0
    }
  ],
  "next_cursor": null
}
```

- Возвращаются только виджеты, прошедшие все условия §2, в порядке §8.
- `data_url` = `api_base_url` экземпляра + `data_path`, собирает ядро.
- Не больше **12** элементов: главная — сводка, а не второй каталог; `next_cursor` всегда `null`.
- Статусы — как у `GET .../service`: чужой вуз — `404`; нет профиля — `403`; вуз не активен — `409 RESOURCE_INACTIVE`; неизвестный `profile`/`locale` — `422`.
- `open_menu` возвращается, только если это меню видно пользователю, иначе `null`.

## 7. Данные виджета (API сервиса)

Оболочка вызывает `GET {data_url}` с `Authorization: Bearer <service access>` сессии **этого экземпляра и выбранного профиля**. Это та же service session, что используется для экранов сервиса; отдельной сессии для виджетов нет.

Сервис обрабатывает запрос по SDK §4.2: проверка JWT, online introspection, профиль, permissions, объектная видимость. Виджет показывает только то, что пользователь увидел бы в самом сервисе: студент — свою группу, преподаватель — свои занятия.

Общие правила ответа:

- `200`, `Cache-Control: no-store`, тело не больше **16 KB**, время ответа — до 3 с (дольше оболочка не ждёт);
- тело — объект `{"kind": "<kind>", ...}`; `kind` совпадает с объявленным, иначе оболочка не показывает виджет;
- ответ `204 No Content` — показывать нечего (карточка скрыта для этого пользователя);
- строки — простой текст: оболочка не интерпретирует HTML и Markdown; время — RFC 3339 UTC с `Z`;
- сервис с `data_path` в manifest обязан отвечать на этот путь. Для cloud-типов путь описывается в OpenAPI сервиса, для своих сервисов — рекомендуется;
- для local-сервиса на другом origin CORS разрешает origin оболочки для `GET` с `Authorization` (SDK §6).

Шаблоны:

**`profile`** — карточка пользователя (даёт сервис «Люди»).

```json
{
  "kind": "profile",
  "user_id": "a76e24db-05e7-4cde-8a60-fbe3b5e5dd42",
  "title": "Анна Смирнова",
  "lines": ["Студент · Группа ПИ-11", "НИЯУ МИФИ"],
  "progress": 60,
  "hint": "Добавьте телефон и должность"
}
```

`user_id` — владелец карточки; оболочка берёт фото из ядра (`GET /api/v1/users/{user_id}/avatar`). `lines` — до 3 строк. `progress` (0..100) и `hint` необязательны: заполненность анкеты. Не больше одного виджета `profile` на главной (первый по порядку).

**`events`** — ближайшие события дня (занятия, консультации).

```json
{
  "kind": "events",
  "day": "2026-09-29",
  "items": [
    {"title": "Базы данных", "starts_at": "2026-09-29T06:00:00Z", "ends_at": "2026-09-29T07:30:00Z",
     "place": "А-101", "status": "scheduled"}
  ],
  "empty_text": "На ближайшую неделю занятий нет"
}
```

`day` — дата дня карточки в часовом поясе вуза или `null`; оболочка пишет «Сегодня» либо день недели. `status`: `scheduled` \| `cancelled` (отменённое зачёркнуто). Не более 10 элементов; `more` (необязательно) — сколько событий дня не поместилось, оболочка пишет «Ещё N».

**`list`** — короткий список (работы на проверке, последние заявки).

```json
{
  "kind": "list",
  "items": [
    {"title": "Курсовая: Иванов И.", "subtitle": "Сдана 28 сентября", "badge": "новая", "tone": "accent"}
  ],
  "total": 5,
  "empty_text": "Работ на проверке нет"
}
```

`tone`: `normal` \| `muted` \| `accent` \| `warning` \| `danger`. Не более 5 элементов; `total` — полное число, оболочка пишет «Ещё N».

**`stat`** — одно число.

```json
{"kind": "stat", "value": 5, "unit": "работ", "caption": "ждут проверки", "tone": "warning"}
```

**`progress`** — доля выполнения.

```json
{"kind": "progress", "value": 60, "caption": "Анкета заполнена", "hint": "Добавьте должность и степень"}
```

`value` — целое 0..100.

**`notice`** — короткое сообщение сервиса.

```json
{"kind": "notice", "title": "Сессия с 12 января", "text": "Расписание экзаменов появится 20 декабря", "tone": "normal"}
```

Длины строк: `title` до 120, `subtitle`/`caption`/`place`/`badge`/`unit`/`hint` до 80, `text`/`empty_text` до 300 символов. Лишние поля оболочка игнорирует. Нарушение формата — виджет не показывается, в консоль оболочки пишется код ошибки.

Виджет может временно не иметь данных: сервис отвечает шаблоном с пустым `items` и `empty_text`. Скрыть карточку совсем для этого пользователя — ответ `204 No Content`. Постоянное скрытие — выключение (§4) или `required_permissions`.

## 8. Поведение оболочки

- **Порядок**: сервисы — в порядке списка сервисов (по наименьшему `order` меню, затем названию), внутри сервиса — по `order`, затем `widget_id`.
- **Состав**: главная — это заголовок-приветствие и сетка виджетов, больше ничего. Виджет `profile` всегда первый.
- **Раскладка**: `small` — половина строки на широком экране, `wide` — вся строка; на телефоне всё в одну колонку.
- **Заполнение пустот (только десктоп)**: если в последней строке остаётся свободная половина, оболочка ставит туда ярлыки облачных сервисов вуза из списка сервисов (иконка, название, переход в меню), которых ещё нет среди виджетов на главной. На телефоне ярлыков нет. Все сервисы по-прежнему доступны на вкладке «Сервисы».
- **Пусто**: если виджетов нет, главная показывает приветствие, строку «Виджетов на главной пока нет» и ID пользователя (его просят администраторы при добавлении в вуз).
- **Загрузка**: у каждой карточки свой скелет; данные запрашиваются параллельно, не больше 4 запросов одновременно. Ошибка одного виджета не мешает остальным.
- **Обновление** — при открытии главной, возврате в приложение и смене профиля или вуза. Периодического опроса нет.
- **Ошибки данных**:

| Ответ сервиса | Что показывает оболочка |
| --- | --- |
| `200` по формату | Карточку |
| `204` | Ничего (карточка скрыта для этого пользователя) |
| `401` | Обновляет service session один раз и повторяет; снова `401` — скрывает |
| `403`, `404` | Скрывает карточку |
| `429`, `5xx`, таймаут 3 с, неверный формат | Заголовок карточки и «Не удалось загрузить» |

- **Нажатие** открывает `open_menu`: встроенный экран, если меню его (как сейчас для расписания и «Людей»), иначе меню сервиса во встроенном окне. `open_menu = null` — карточка не кликабельна.
- **Безопасность**: `data_url` берётся только из ответа ядра, токен отправляется только туда; CSP оболочки разрешает `connect-src` для `api_base_url` включённых сервисов, так же как `frame-src` для их client origins.

## 10. Что меняется в реализации

| Часть | Изменение |
| --- | --- |
| Ядро, каталог | `check_manifest` принимает `widgets` по §3; словари типов получают право `<тип>.widgets.manage` (по желанию сервиса) |
| Ядро, БД | Таблица `widget_visibility(service_id, widget_id, profile, by_service, by_admin)`, PK из трёх полей, FK на экземпляр с `ON DELETE CASCADE`; синхронизация при публикации manifest (§4.3) |
| Ядро, machine API | `GET .../widgets`, `PUT .../widgets/{widget_id}/visibility` (§4), аудит |
| Ядро, private API | `GET .../services/{id}/widgets`, `PUT .../widgets/{widget_id}/visibility` (§5), аудит |
| Администрирование | Фасад двух операций и блок «Виджеты на главной» на вкладке «Сервисы» |
| Ядро, API оболочки | `GET /api/v1/institution/{id}/widgets` (§6); `connect-src` в CSP оболочки |
| Ядро, OpenAPI | Схемы `WidgetDefinition`, `WidgetVisibility`, `WidgetView`, три операции |
| SDK | Клиент ядра: `widgets()`, `set_widget_visibility()`; схемы данных §7 в SDK OpenAPI |
| Оболочка | Главная строится только из `GET .../widgets` и шаблонов §7; встроенные карточка профиля, «Сегодня» и плитки сервисов удалены; ярлыки облачных сервисов заполняют пустоты на десктопе |
| Расписание | Виджеты `today`, `today_admin`, `today_stats`; `GET /api/v1/schedule/widgets/today`, `/today-admin`, `/today-stats` |
| «Люди» | Виджет `me`; `GET /api/v1/profile/widgets/me` |
| Курсовые | Виджеты `my_work`, `to_review`, `all_works`; `GET /api/v1/coursework/widgets/...` |

Публикация и включение идут тем же путём, что меню и роли: сервис при запуске синхронизирует manifest (onboarding). Выключения, сделанные сервисом или администратором вуза, при этом сохраняются (§4.3).

## 11. Приёмка

1. Manifest с `widgets` публикуется; неверный `kind`, профиль вне `supported_profiles`, `open_menu` на несуществующее меню или больше 8 виджетов — `422`.
2. Новый виджет виден всем своим профилям; после `PUT visibility` с `teacher: false` преподаватель его не получает в `GET .../widgets`, студент получает; повторная публикация manifest этого не сбрасывает.
2a. Администратор вуза выключает виджет у профиля — профиль его не получает; включить виджет, выключенный сервисом, администратор не может, и наоборот.
3. Виджет с `required_permissions` виден только пользователям с ролью, дающей все права; снятие роли убирает его со следующего запроса.
4. Выключение или удаление экземпляра убирает его виджеты; включение возвращает с прежними настройками.
5. `PUT visibility` (оба уровня) без `If-Match` — `428`, со старым — `412`; machine API для administration — `403`; для чужого экземпляра — `404`; private API без `services.manage` — `403`; изменения есть в журнале.
6. Данные виджета отдаются только с service access своего экземпляра; студент получает занятия только своей группы, как и в самом расписании.
7. Ошибка или медленный ответ одного сервиса не мешает остальным карточкам; `403/404/204` скрывают карточку, `5xx` показывает «Не удалось загрузить».
8. На главную не попадают HTML и скрипты сервиса; токен отправляется только на `data_url` из ответа ядра.
9. На главной нет ничего, кроме приветствия и виджетов; на десктопе свободная половина строки занята ярлыком облачного сервиса, на телефоне ярлыков нет.
