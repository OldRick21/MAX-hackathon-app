# Шаблон своего сервиса

Каркас стороннего сервиса вуза на минимальном Service SDK. Реализует общие правила из [SPEC.md](../SPEC.md): проверку пользователя через ядро, публикацию меню и ролей, единые ошибки и протокол iframe. Доменной логики нет — её пишете вы.

## Состав

| Файл | Что это | Менять? |
| --- | --- | --- |
| `app/sdk.py` | Клиент ядра, самостоятельная публикация меню и ролей, проверка сессии (`Ctx`), ошибки, CORS, `GET /api/v1/health`, `GET /api/v1/service`, раздача клиента с CSP | Нет |
| `client/assets/sdk-client.js` | Протокол оболочка ↔ iframe (§7): приём токена, обновление, `ServiceSDK.api()` | Нет |
| `app/main.py` | Код сервиса, меню, виджет главной, роли, маршруты | Да |
| `client/index.html`, `client/assets/app.js` | Интерфейс сервиса | Да |
| `Dockerfile`, `.env.example` | Запуск на сервере вуза | По необходимости |

## Как сделать свой сервис

1. Скопируйте папку `service-template` в свой репозиторий.
2. В `app/main.py` заполните `SERVICE_CODE` (тот же код, что администратор укажет при подключении), `MANIFEST` и `ROLES`. Права сервиса — только вида `<код>.<право>`: ядро не примет чужие.
3. Добавьте маршруты. Каждый получает `ctx: sdk.Ctx = Depends(authenticate)`: вуз, экземпляр, пользователя, профиль и актуальные права. Храните и ищите данные только по `ctx.tenant`. Чужой или невидимый объект — `404`, нехватка права — `403` (`ctx.require(...)`).
4. Для изменений используйте версии: `sdk.etag_of(...)` в ответе и `sdk.check_if_match(...)` при записи.
5. В `client/assets/app.js` рисуйте интерфейс: `await ServiceSDK.ready` даёт контекст, `ServiceSDK.api('/путь')` ходит в ваш API с токеном.

## Виджет на главном экране

Главная приложения состоит только из виджетов сервисов. В шаблоне есть пример — виджет `summary`:

- объявление — в `MANIFEST["widgets"]` рядом с меню: `kind` (шаблон карточки: `profile`, `events`, `list`, `stat`, `progress`, `notice`), `size` (`small` — половина строки, `wide` — вся), профили, `required_permissions`, `data_path` (путь от `api_base_url`) и `open_menu` — меню, куда ведёт нажатие;
- данные — маршрут `GET /api/v1/widgets/summary`: обычная проверка сессии через `authenticate`, ответ `{"kind": "list", ...}` по формату шаблона, до 16 KB и 3 секунд; `204` — карточку не показывать;
- публикация — вместе с меню при старте сервиса, ничего отдельно делать не нужно;
- включение — администратор вуза в «Сервисы» → «Виджеты на главной» отмечает, каким профилям показывать виджет. Сервис тоже может выключать свои виджеты через machine API ядра.

Форматы всех шаблонов, правила видимости и ошибок — в [WIDGETS_SPEC.md](../WIDGETS_SPEC.md). HTML и скрипты сервиса на главную не попадают: карточку рисует оболочка.

## Подключение

Порядок из [CORE_API_SPEC.md](../../../core/CORE_API_SPEC.md) §7 и README проекта («Подключение своего сервиса»):

1. Поддержка платформы одобряет DNS-имя сервера вуза.
2. Администратор вуза: «Сервисы» → «Подключить сервис» → «Свой сервис» (название, код, профили, адреса).
3. «Выдать ключ» — строки для `.env` сервиса (образец — `.env.example`).
4. Запуск: `docker build -t my-service . && docker run --env-file .env -v my-service-data:/data -p 8500:8500 my-service`. Перед сервисом нужен HTTPS на одобренном имени. При старте сервис сам создаёт роли и публикует меню; состояние — в `GET /api/v1/health` (`onboarding: ready`).
5. Администратор нажимает «Включить». Сервис появляется в «Все сервисы» и открывается внутри приложения.

## Проверка

```bash
pip install -r requirements.txt httpx
python -m unittest discover -s tests -t . -v
```

Тесты проверяют каркас на заглушке ядра: `401` без сессии, `404` для токена чужого сервиса, `503` при недоступном ядре, `GET /api/v1/service`, данные виджета, CSP страницы клиента и CORS только для оболочки.
