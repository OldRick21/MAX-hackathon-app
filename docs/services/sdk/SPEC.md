# Общее для сервисов: Service SDK

Версия `0.1.0`, 26 сентября 2026. Требования к общей библиотеке, без программной реализации. [Общий OpenAPI](OPENAPI.yaml) · [Общие эндпоинты](ENDPOINTS.txt) · [Навигация](../INDEX.md).

SDK одинаков для cloud и local. Он обеспечивает протокол интеграции с ядром и клиентской оболочкой; конкретные операции, объекты и права описаны в комплекте соответствующего сервиса. Развёртывание облачных процессов вынесено в [CLOUD_RUNTIME_SPEC.md](../CLOUD_RUNTIME_SPEC.md).

## 1. Что включить в SDK

| Часть SDK | Общая обязанность | Что передаёт или реализует сервис |
| --- | --- | --- |
| Аутентификация | JWKS, проверка service access, online introspection без кэша прав | Issuer, origin ядра, ожидаемый service_type |
| Источник bindings | Получить доверенную привязку по проверенным UUID, сверить вуз/тип | Cloud-адаптер конфигурации платформы или local-адаптер серверной конфигурации |
| Контекст запроса | Неизменяемые tenant, user, profile, session, актуальные permissions и request_id | Использование контекста в доменном репозитории |
| Клиент machine API ядра | Обмен credential, кэш machine JWT по credential/revision, introspection, чтение профилей, manifest и RBAC в разрешённых scopes | Определения меню/ролей и решение, когда разрешено менять назначения |
| Авторизация | Проверка разрешённых профилей и требуемых permissions; отказ при отсутствии доступа | Объектные правила: своя группа, своя работа, назначенный проверяющий |
| Общие маршруты | GET health, GET service, раздача опубликованных assets | Настройки типа, manifest, статические файлы и HTML entrypoints |
| HTTP | Оболочка ошибок, request_id, no-store, валидация заголовков, locale/fallback, CORS по конфигурации | Доменные модели, статусы ошибок и payload-лимиты |
| Конкурентные изменения | Правила strong ETag/If-Match, idempotency, cursor и их контекст | Агрегат/revision, транзакция БД, фильтрация и ключ сортировки |
| Клиентский bridge | Проверенный postMessage, канал iframe, получение/обновление access, завершение контекста | UI сервиса; shell реализует ответную часть протокола |
| Наблюдаемость и лимиты | Единые request IDs, безопасные ошибки и журналы, rate-limit по экземпляру/пользователю | Доменные события аудита и дополнительные лимиты |

SDK не должен превращаться в универсальную модель всех учебных данных. Достаточно общего конвейера запросов, клиента ядра, клиентского bridge и небольших интеграционных интерфейсов для bindings/хранилища. ETag и idempotency становятся корректными только при участии транзакции доменного сервиса; библиотека не может обеспечить это одним HTTP middleware.

Приватный фасад управления вузом относится **только к administration**. У обычного SDK-клиента ядра нет универсального метода «вызвать любой private URL» и нет глобального credential. SDK не разворачивает процессы, не создаёт вузы/профили, не хранит анкеты/расписание и не управляет файлами курсовых.

## 2. Общие входящие операции

| Метод и путь | Поведение |
| --- | --- |
| GET /api/v1/health | Liveness процесса без tenant и секретов; security=[] |
| GET /api/v1/service | ServiceView текущего экземпляра после аутентификации: UUID, адреса, профиль, актуальные роли/permissions и видимые меню |
| GET /assets/{asset_name} | Только опубликованные статические файлы клиента с content hash; без произвольного файлового доступа |

Эти три операции описаны только в SDK OpenAPI. Доменные операции и конкретные HTML paths (`/admin`, `/schedule`, `/home`, `/users`, `/coursework`) находятся в соответствующих контрактах. Механизм раздачи HTML общий, но названия путей и содержимое принадлежат сервису. HTML/asset не содержит токенов и учебных данных; загрузка оболочки не означает авторизацию.

`GET /service` читает manifest через API ядра и фильтрует по текущим профилю/permissions. Все required_permissions пункта меню обязательны. Есть locale=ru|en, но нет выбора вуза/профиля параметром. Имена меню имеют обязательный перевод ru, fallback — ru; сортировка (order,id). Каждый тип задаёт supported_profiles, меню, словарь permissions и начальные определения ролей в своей спецификации. Меню не заменяет авторизацию API; наличие меню не требуется для headless service session.

Отдельных входящих auth/refresh/logout и публичного PUT manifest у SDK нет. Все пользовательские токены выдаёт/обновляет ядро, backend сервиса принимает только service access. Общие схемы, используемые доменными контрактами, локально включены в каждый YAML для автономного чтения; это копии форматов, а не новые реализации правил.

### Исходящие вызовы ядра

| Возможность клиента SDK | API ядра, которое уже существует |
| --- | --- |
| Machine access | POST /api/v1/internal/auth/token, Basic credential своего экземпляра |
| Access-ключи | GET /api/v1/internal/auth/jwks |
| Актуальная сервисная сессия | POST /api/v1/internal/auth/introspect |
| Manifest | GET/PUT /api/v1/internal/service/{service_id}/manifest |
| Профили известного участника | GET /api/v1/internal/service/{service_id}/users/{user_id}/profiles |
| Определения и назначения ролей | Операции под /api/v1/internal/service/{service_id}/roles и /users/{user_id}/profiles/{profile}/roles |

Точные тела и заголовки исходящих вызовов определены в [CORE_API_OPENAPI.yaml](../../core/CORE_API_OPENAPI.yaml). Эти вызовы **не публикуются** как новые endpoints SDK. Machine scopes ограничивают backend, но не заменяют авторизацию человека перед операцией с ролью/manifest. У administration публичные write-scopes RBAC отсутствуют; SDK не пытается обойти это ограничение. Создание/изменение членства и профилей не относится к общему machine API.

## 3. Контекст и изоляция

После аутентификации SDK создаёт неизменяемый **контекст одного запроса**: `institution_id`, `service_id`, `user_id`, `profile`, актуальные `roles/permissions`, `session_id`, `request_id`. Контекст передаётся обработчику и репозиторию явно. Нельзя хранить «текущий вуз» в глобальной переменной, менять общий объект клиента ядра под запрос или выбирать tenant из пользовательского заголовка.

Каждая доменная строка содержит `(institution_id, service_id)`. Каждый SELECT, UPDATE, DELETE и JOIN ограничен обеими координатами. Первичный/уникальный ключ ресурса и внешние ключи включают эти координаты: идентификатор группы A невозможно связать с занятием B. UUID сам по себе не является проверкой доступа.

Ключи файлов, idempotency, cache и фоновой очистки тоже начинаются с обеих координат. Если SQL-RLS добавляется для доменных таблиц, контекст соединения устанавливается только на время транзакции; возврат соединения в пул не должен переносить tenant следующему запросу. RLS не заменяет объектные проверки «своя работа»/«своя группа».

Источник binding возвращает institution_id, service_id, service_type, утверждённые API/UI URLs, client_id, защищённый секрет и binding_revision. Для cloud источник описан платформой, для local — конфигурацией вуза. Клиентский запрос не создаёт binding и не выбирает секрет напрямую. Каждый исходящий запрос в ядро использует credential текущего экземпляра.

Доменные таблицы не используют SQL FK на закрытые таблицы ядра. SDK может проверить внешнего пользователя через machine endpoint профилей; доменный сервис решает, требуется ли student/teacher и какое отношение создаётся. Удаление членства блокирует доступ через ядро, но не стирает доменные строки. Повторное добавление того же UUID восстанавливает прежние связи; историю периодов членства модель MVP не вводит.

## 4. Порядок доступа и проверки

### 4.1. Открытие сервиса пользователем

1. Shell входит в ядро через MAX, получает свои вузы и выбирает вуз.
2. Получает назначенные профили; пользователь выбирает один. `admin` не выбирается автоматически вместо student/teacher.
3. Запрашивает список сервисов ядра с этим `profile` и `locale`; выбирает экземпляр и меню.
4. Создаёт service session через `POST /api/v1/institution/{institution_id}/service/{service_id}/session`. Core access и service refresh остаются в памяти shell.
5. Загружает HTML выбранного меню в отдельный iframe. Передаёт только access **этого** экземпляра через проверенный handshake.
6. Iframe вызывает `GET /api/v1/service`, сверяет возвращённый контекст с переданным shell и затем обращается к своему доменному API.
7. При обновлении токена iframe просит shell; shell сериализует refresh семьи и вызывает ядро. Сервисный backend не выдаёт токены.
8. При смене вуза или профиля shell уничтожает старый iframe, по возможности отзывает его service session, затем повторяет выбор. Разные вкладки могут иметь разные профили одновременно.

Нет обязательного порядка «сначала user-profile, затем schedule»: каждый сервис доступен независимо. Обязателен только порядок: **вуз → профиль → экземпляр → сервисная сессия → конкретная операция**.

### 4.2. Обработка каждого защищённого запроса

1. Проверить формат Authorization и service JWT: подпись по JWKS ядра, фиксированные issuer/RS256, `token_use=service_access`, сроки, обязательные claims и `aud=service:{service_id}`. Поля неподтверждённого JWT не используются для сетевых запросов или загрузки credentials. Неизвестный kid обрабатывается по ограниченному refresh JWKS из [CORE_API_SPEC.md](../../core/CORE_API_SPEC.md).
2. По подписанным `institution_id/service_id` найти **заранее зарегистрированный** binding. Тип binding должен совпасть с текущим сервисом, institution — с JWT. Чужой известный binding — 404. Если подписанный токен корректен, но binding ещё недоступен, — 503 INSTANCE_NOT_READY; это не запускает автоматическую регистрацию. Без валидного JWT — 401.
3. Получить machine access из credentials именно этого binding. Машинный access можно переиспользовать до exp с запасом 30 с; одновременные обмены одного credential объединяются. На 401 ядра допускается один новый обмен; бесконечных повторов нет.
4. Выполнить online introspection входного service access в ядре. В MVP это обязательно **для всех** защищённых операций, включая чтение. `active=false` → 401 UNAUTHENTICATED. При active=true повторно сверить UUID, audience, subject и профиль с JWT и binding; права взять из introspection, а не из старого снимка JWT. Ошибка связи/доверенной machine-конфигурации → 503, без перехода к offline-правам.
5. Проверить разрешённый профиль и permission операции. Затем найти объект только в текущем экземпляре и проверить объектные ограничения. Чужой/невидимый объект → 404, недостаточные права на операцию в своём экземпляре → 403. Меню не является авторизацией.
6. Проверить If-Match/Idempotency-Key, тело и доменные связи; выполнить короткую транзакцию. При успехе вернуть новую версию ресурса. Во время медленной загрузки PDF сетевые и файловые операции не удерживают долгую транзакцию БД.

Introspection не кэшируется. Поэтому отключение экземпляра, снятие профиля и logout блокируют **следующий** online check, без пяти минут offline-окна. Уже прошедший проверку запрос может завершиться: общей транзакции между ядром и доменной БД нет. Это явно допустимая граница MVP. Перед commit загрузки файла проверка повторяется; длительная передача скачивания повторно не авторизуется на каждом байте.

Проверка связи с другим пользователем выполняется доступным machine endpoint ядра `GET /api/v1/internal/service/{service_id}/users/{user_id}/profiles`. Machine credential даёт чтение профилей только в вузе этого экземпляра. Нет membership/нужного профиля → 422 INVALID_REFERENCE при вводе ссылки; чтение недоступной анкеты → 404. Сбой ядра → 503. UUID не проверяется через прямой SELECT таблиц ядра.

## 5. Общие правила HTTP и хранилища

- JSON UTF-8, snake_case, UUID строками, даты UTC RFC 3339 с Z. Сначала auth, затем тело. Неизвестные поля тела отклоняются: JSON syntax — 400, структура/значения — 422. PATCH непустой; отсутствие поля не изменяет его. Nullable поля задаёт схема конкретного сервиса. У имён/заголовков удаляются крайние пробелы, пустой результат запрещён; описание может быть пустым.
- ErrorResponse сохраняет оболочку ядра; доменные коды берутся из контракта сервиса. В API-ответе X-Request-ID, в ошибке тот же error.request_id. JSON и downloads — no-store. Токены, secrets, файлы и анкеты не записываются в журнал; stacktrace/SQL не попадают в HTTP-ответ.
- Для изменения доменного ресурса нужен один strong If-Match: нет — 428, старая версия — 412, wildcard/списки запрещены. ETag связывает tenant, агрегат и revision. Авторизация/область проверяются до версии. Версию определяет сервис: SDK не предполагает, что URL файла и URL работы — разные агрегаты. Операции administration сохраняют правила ядра, включая отзыв credential без If-Match.
- Idempotency обязательна только на операциях, где есть заголовок в OpenAPI. Ключ UUID, область — instance, user, profile, method/path; хранение 24 ч в БД. Каноническое тело и результат создания фиксируются вместе с доменной транзакцией; способ описать бинарное тело задаёт coursework. Одинаковые конкурентные создания сериализуются, другое тело — 409 IDEMPOTENCY_CONFLICT. Перед replay снова проверяются права/видимость. Удалённый/невидимый результат — 404; доступный replay возвращает исходные 201, тело и ETag. Актуальную версию перед новым изменением читают GET.
- PUT/PATCH после потерянного ответа требуют перечитать и сверить результат, а не бесконечно повторять старый If-Match. Автоматические повторы допускаются только для чтения или явно идемпотентного создания. Выдача refresh или credential не получает произвольной replay-гарантии SDK.
- Пагинация: limit 1–100, default=50, items/next_cursor. Курсор непрозрачен, на 15 минут, связан с tenant/user/profile, актуальными permissions и фильтрами/locale. Недействительный cursor — 400 INVALID_CURSOR. Snapshot не обещается; права применяются заново на каждой странице. Сервис задаёт устойчивый порядок (обычно UUID, для занятий starts_at,id) и момент продвижения cursor после фильтрации.
- Лимит доменных запросов: 120/мин на instance+user; превышение — 429 с Retry-After. Дополнительные лимиты загрузки файлов принадлежат coursework. Лимит machine API ядра тоже учитывается: SDK ограничивает параллелизм исходящих проверок, не запускает неограниченное число запросов.
- Timeout обращения в ядро — 3 с на попытку. При 429 upstream сохраняются 429 и Retry-After; сбой ядра/БД/машинной конфигурации — 503 SERVICE_UNAVAILABLE, неизвестная ошибка — 500 INTERNAL_ERROR. Offline fallback нет. Даже корректная подпись не даёт мгновенного отзыва без online check; уже авторизованный запрос может закончиться по оговорённой границе.

SDK-хранилище технических записей может использовать ту же БД сервиса: idempotency с UNIQUE scope+key, счётчики лимитов, аудит без секретов. Данные не хранятся только в памяти процесса. Общий mutex по всем вузам не нужен; отдельные транзакции/версии защищают конфликтующие изменения. Объектные FK/уникальности задаёт доменная схема, автоматического фильтра tenant «по наличию колонки» не предполагается.

## 6. Адреса и доставка клиента

Client origin отличается от origin ядра и других типов. В MVP удобно размещать API и UI одного типа на одном origin; его адрес задаётся реестром/конфигурацией. api_base_url уже заканчивается на /api/v1, поэтому добавляется только доменный суффикс. HTML entrypoint присоединяется к origin client_base_url. Путь меню не содержит query, fragment, обходов каталогов или другого origin, как требует ядро.

Если UI/API разнесены, CORS разрешает только зарегистрированный client origin, нужные методы и Authorization, Content-Type, If-Match, Idempotency-Key; раскрывает ETag, Location, X-Request-ID, Retry-After, Content-Disposition. Cookies не используются. OPTIONS возвращает только CORS-метаданные, без tenant-данных. Публичный private-префикс ядра остаётся закрыт, включая OPTIONS.

Assets с hash имеют public, max-age=31536000, immutable; HTML — no-store. SDK раздаёт только опубликованные assets данного клиента. За build содержимого и реальные entrypoint paths отвечает сервис; SDK не исполняет сервисный HTML в JS-контексте shell.

## 7. Минимальный протокол shell ↔ iframe

Это браузерный протокол SDK, а не HTTP и потому описан здесь. Он реализует уже принятую ядром передачу service access, не создавая новую систему авторизации.

Сообщения — объекты с `type`, `protocol_version=1` и `channel_id` (новый UUID на каждую загрузку iframe):

| Направление | type | Дополнительные поля |
| --- | --- | --- |
| Shell → iframe после load | `platform.init` | Нет токенов; инициирует канал |
| Iframe → shell | `service.ready` | Подтверждает channel_id |
| Shell → iframe | `platform.context` | institution_id, service_id, profile, api_base_url, locale, access_token, expires_at (UTC) |
| Iframe → shell | `service.refresh_requested` | request_id (UUID) |
| Shell → iframe | `platform.access` | request_id, access_token, expires_at |
| Shell → iframe | `platform.session_ended` | reason: expired, revoked, context_changed или unavailable |

Обе стороны используют точный `targetOrigin`, сверяют `event.origin`, `event.source`, protocol_version и channel_id. Shell знает origin из реестра, iframe знает разрешённый origin shell из deployment-конфигурации. Применяется sandbox с нужными UI-возможностями и отдельным origin; точная политика embedding/CSP зависит от размещения MAX, но не должна лишать postMessage проверяемого origin. Если выбранный sandbox даёт opaque origin `null`, этот handshake нельзя ослаблять до `*` — нужно исправить конфигурацию размещения.

Iframe отвечает ready только на init от разрешённого родителя. При повторном load создаётся новый канал, старые сообщения/результаты запросов отбрасываются. Полученный api_base_url должен совпасть с настроенным разрешённым API origin клиента; iframe не отправляет bearer на URL из случайного сообщения. Значения контекста нужны UI, но backend доверяет только проверенному JWT и introspection.

Refresh запрашивается перед expires_at либо один раз после 401. Shell объединяет конкурентные запросы, делает один refresh в ядро и возвращает новый access. При провале/потере refresh-ответа не переиспользует старый refresh: создаёт новую service session либо завершает её по правилам ядра. Iframe прекращает новые запросы после session_ended; повторный API 401 после обновления не запускает цикл. При первоначальном GET /service несовпадение контекста завершает канал. Токены хранятся только в памяти, не в URL, HTML, localStorage или логах.

SDK клиента сервиса реализует приём init/context/access/session_ended и отправку ready/refresh_requested. Ядро-клиент реализует вторую сторону того же протокола: владеет core access и всеми refresh, выбирает профиль/экземпляр и управляет iframe. Service SDK не получает refresh ни через сообщение, ни через URL.

## 8. Общая приёмка SDK

1. Один процесс одновременно обслуживает запросы A/B без переноса tenant через глобальные переменные, кэш или пул соединений.
2. Query/body/header не переключают профиль/вуз; core/machine/refresh не проходят вместо service access, неизвестный binding не создаётся запросом.
3. После отзыва доступа следующий introspection отклоняет запрос; отказ ядра даёт 503 без offline fallback. При ротации используется credential/revision своего экземпляра.
4. Меню фильтруются по профилю и всем required_permissions; локализация не меняет коды/идентичность и не является авторизацией.
5. Общая оболочка ошибок, If-Match, idempotency и cursor работают с доменной транзакцией и текущей областью доступа, а не только с HTTP-параметрами.
6. Поддельные postMessage, старые каналы и результаты refresh другого iframe отклоняются. JWT не появляется в URL/storage/логах.
7. Local использует те же проверки через свой binding и не получает доступа к cloud provisioning или private API ядра.

Критерии предметных операций находятся в спецификациях сервисов. Успешная валидация OpenAPI подтверждает согласованность документов, а не реализацию этих проверок.
