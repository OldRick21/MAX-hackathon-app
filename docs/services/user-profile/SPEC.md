# Сервис анкет пользователей

Версия `0.1.0`, 26 сентября 2026. Облачные анкеты участников вуза: «Главная» и «Пользователи». Контракт разделён без изменения операций; код не реализуется.

[OpenAPI](OPENAPI.yaml) · [Эндпоинты](ENDPOINTS.txt) · [Общее и SDK](../sdk/SPEC.md) · [Навигация](../README.md).

Этот комплект содержит 7 собственных операций. Полный API дополняется тремя общими операциями [SDK](../sdk/OPENAPI.yaml). Все входящие защищённые запросы используют ServiceBearer и online introspection по общим правилам.

## 1. Размещение, права и меню

Один процесс user-profile обслуживает все вузы по [облачной схеме](../CLOUD_RUNTIME_SPEC.md). Анкета является доменными данными и не заменяет профиль admin/teacher/student ядра.

- api_base_url: `https://profiles.platform.example/api/v1`.
- client_base_url: `https://profiles.platform.example`.
- Поддерживаемые профили: admin, teacher, student.

Любой действующий участник читает доступные анкеты своего вуза и редактирует своё отображаемое имя/описание. Изменение должности/степени требует одновременно admin и `profiles.manage`.

Начальная роль `profile_editor`: permissions=[profiles.manage], allowed_profiles=[admin]. Платформа создаёт её при установке, owner назначает конкретному участнику; автоматически всем admin она не выдаётся.

| ID меню | Название | Путь | Профили | required_permissions | order |
| --- | --- | --- | --- | --- | --- |
| home | Главная | /home | admin, teacher, student | [] | 0 |
| users | Пользователи | /users | admin, teacher, student | [] | 10 |

## 2. Анкета и каталог

Карточка общая для всех профилей одного человека в одном вузе. Сам человек изменяет только `display_name` и `about`. Отображаемое имя вводится пользователем и не считается подтверждённым паспортным ФИО. Должность и степень задаёт admin с profiles.manage; nullable поля допускают null для очистки. Телефон, MAX ID, адрес, паспорт и закрытые учебные сведения не входят в карточку.

Все поля карточки доступны действующим участникам того же вуза. Для демонстрации используются учебные/вымышленные анкетные сведения; конкретные правила публикации реальных сведений определяются перед пилотом. Юридический TODO манифеста этим контрактом не закрывается.

GET своей или чужой действующей карточки без сохранённой строки возвращает виртуальную пустую карточку: display_name/position/academic_degree=null, about="". GET не записывает данные. ETag виртуальной версии стабилен и привязан к экземпляру/user_id; первая PATCH создаёт строку атомарно, вторая параллельная PATCH со старым ETag получает 412. Академическая PATCH может создать карточку без имени; владелец заполнит имя позже. Оба пути карточки используют одну версию.

Каталог содержит только сохранённые карточки с непустым display_name, а не всех участников ядра. В существующем machine API нет операции перечисления участников, поэтому обещать полный реестр было бы несовместимо с ядром. При GET по известному UUID членство проверяется доступным endpoint профилей. При поиске/списке сервер берёт не более limit кандидатов по user_id и для каждого проверяет текущее членство; недоступных пропускает, cursor указывает последнего **просмотренного** кандидата. Поэтому даже пустая страница может иметь next_cursor. Сбой ядра прерывает запрос с 503, а не подставляет непроверенные карточки. Для размеров демо это приемлемо; batch-проверка — возможное отдельное расширение ядра в будущем.

После удаления membership доменная карточка сохраняется, но не выдаётся. Повторное добавление того же UUID в вуз возвращает доступ к прежним данным; то же относится к составу групп и курсовым. Истории разных периодов членства в текущей модели нет. Автоматическая физическая очистка по снятию профиля не вводится.

## 3. Хранение и граница SDK

PK анкеты — `(institution_id, service_id, user_id)`; для всей карточки одна revision, независимо от пути `/me` или `/users/{user_id}`. Display_name и about редактирует владелец; position/academic_degree — уполномоченный admin. Последние два поля допускают null для очистки, about очищается пустой строкой.

SDK предоставляет проверку сессии, вызов профилей ядра, ETag и механизм cursor. Сервис решает, какие карточки показывать, когда вернуть виртуальную карточку и какой просмотренный кандидат должен попасть в cursor. SDK не создаёт анкету в ответ на GET и не обещает несуществующий machine endpoint полного списка членов вуза.

## 4. Приёмка

1. Student/teacher и admin без profiles.manage не меняют должность/степень.
2. Все профили одного человека в одном экземпляре используют одну карточку; другие вузы изолированы.
3. Первое параллельное изменение виртуальной карточки даёт один успех и один 412.
4. Удалённый участник недоступен по UUID и отсутствует в каталоге; сбой проверки ядра даёт 503.
5. Пустая отфильтрованная страница с next_cursor не завершает перечисление; чужие данные не возвращаются для заполнения страницы.
