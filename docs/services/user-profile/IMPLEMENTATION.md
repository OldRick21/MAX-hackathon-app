# Сервис «Люди» (user-profile): реализация

Документ описывает код в `services/user-profile/` и связанные изменения ядра (`backend/`) и оболочки (`frontend/`). Контракт — [SPEC.md](SPEC.md), [OPENAPI.yaml](OPENAPI.yaml) и [протокол SDK](../sdk/SPEC.md). Здесь перечислено, что реализовано, где реализация сознательно отходит от контракта и как это проверяется.

## Компоненты

| Где | Что делает |
| --- | --- |
| `services/user-profile/app/main.py` | Процесс сервиса (один на все вузы): SDK-проверка запроса, `GET /api/v1/service`, пять доменных операций анкет, своя SQLite |
| `services/user-profile/app/core_client.py` | Клиент ядра: binding по UUID, machine JWT с кэшем по credential/revision, online introspection без кэша, чтение манифеста и членства, отказ → 503 |
| `services/user-profile/Dockerfile` | Образ на порту 8200; непривилегированный UID 10003, каталог `/data` под том с анкетами, HEALTHCHECK на `/api/v1/health` |
| `backend/routes/platform.py` | Provisioning bindings: один эндпоинт обслуживает оба типа сервиса, токен выбирает тип |
| `backend/settings/config.py` | `USER_PROFILE_PROVISIONING_TOKEN` и адреса облачного типа |
| `backend/manage.py` | `install-people INSTITUTION_UUID` — установка и починка экземпляра вузу |
| `frontend/src/screens/users/` | Встроенные экраны «Профиль» и «Люди» оболочки; обращаются к сервису по `api_base_url` из каталога |
| `web/configs/docker-nginx.conf` | Прокси `/people/api/` → `user-profile:8200` на origin оболочки |

## Порядок обработки защищённого запроса

1. Проверяется формат `Authorization`, `token_use=service_access` и `aud=service:{service_id}`. Поля непроверенного JWT выбирают **только** binding.
2. Binding читается у ядра provisioning-токеном; тип binding обязан быть `user-profile`.
3. Credential этого binding обменивается на machine-токен (кэш по credential/revision, на 401 — один повторный обмен).
4. Выполняется online introspection входного токена. Сверяются `service_id`, `institution_id`, `sub`, `profile`, `sid` и `parent_sid`; права берутся из ответа ядра, а не из claims. Кэша нет: logout, снятие профиля и отключение экземпляра закрывают **следующий** запрос.
5. Членство участника проверяется machine-эндпоинтом профилей ядра. Сбой ядра → 503, без показа непроверенных анкет.
6. Правка академических полей требует одновременно `profile=admin` и права `profiles.manage`.

## Хранение

PK анкеты — `(institution_id, service_id, user_id)`, одна `revision` на всю карточку независимо от пути `/me` или `/users/{user_id}`. GET отсутствующей карточки отдаёт виртуальную пустую со стабильным ETag и ничего не записывает. Первая PATCH создаёт строку под `BEGIN IMMEDIATE`, поэтому две параллельные правки дают один `200` и один `412`; PATCH без `If-Match` — `428`.

Курсор каталога подписан HMAC на `USER_PROFILE_PROVISIONING_TOKEN` и живёт 15 минут; он указывает последнего **просмотренного** кандидата, поэтому пустая страница с `next_cursor` не означает конец списка — оболочка дочитывает следующие страницы.

SQLite открывается в режиме WAL с `busy_timeout`; `synchronous` остаётся штатным. Прерванная запись откатывается при следующем открытии файла, поэтому перезапуск контейнера посреди PATCH не оставляет БД нерабочей. Схема создаётся при каждом старте (`CREATE TABLE IF NOT EXISTS`) и существующий том не портит. Если `/data` недоступен для записи, процесс падает с сообщением о томе, а не отвечает ошибками на каждый запрос.

## Отличия от контракта

- **Клиентские страницы `GET /home` и `GET /users` не реализованы**, как и `GET /assets/{asset_name}` из SDK. Эти два меню оболочка рисует сама (`NATIVE_MENUS` в `frontend/src/state/institution.tsx`), iframe и отдельный origin для сервиса не используются, поэтому HTML-клиента у него нет. Nginx проксирует только `/people/api/`. Если появится внешний клиент, страницы и отдельный origin придётся добавить.
- **Чужой binding даёт 404, а не 503 `INSTANCE_NOT_READY`.** Ядро на неизвестный или чужой `service_id` отвечает 404, и отличить «экземпляра нет» от «binding ещё не выдан» на этом эндпоинте нельзя. По [SDK SPEC §4.2](../sdk/SPEC.md) чужой известный binding — 404, поэтому 404 выбран как поведение по умолчанию; 503 остаётся за случаем, когда ядро недоступно и проверить нечем. Иначе токен любого другого сервиса объявлял бы «Людей» недоступными.
- **Rate limits** из спецификации не реализованы.
- **Batch-проверка членства** отсутствует: список кандидатов проверяется по одному, как и описано в контракте для размеров демо.

## Проверка

```bash
cd services/user-profile && python -m unittest discover -s tests -t . -v
cd services/user-profile && PYTHONPATH=../../backend python -m unittest tests.test_integration_core -v
```

`tests/test_profiles.py` проверяет сервис на заглушке ядра: отказ без сессии, виртуальную карточку, гонку первой правки, запрет чужих полей, права на академические поля, каталог и поиск, снятое членство, сбой ядра, несовпадение профиля и сессии, изоляцию вузов, `GET /api/v1/service` с фильтром меню и локалью, перезапуск на существующем томе.

`tests/test_integration_core.py` поднимает настоящее ядро в том же процессе (транспорт замкнут на него, портов и ожиданий нет) и проходит весь путь: заявка вуза и одобрение, `manage.py install-people`, сессия сервиса, `ServiceView` из живого манифеста, сохранение анкеты и `412`, выдача роли `profile_editor` и её действие на **уже выданный** токен, отказ токену чужого сервиса, снятие членства, logout.
