Данный документ - манифест и спецификация программной архитектуры MVP проекта "Вузы России".

Функциональность, выходящая за рамки MVP, может упоминаться в спецификации, но не реализуется в проекте на данный момент.

Это черновик спецификации, необходимый для разработки её элементов.
# Идея проекта

Проект "Вузы России" представляет собой единую платформу для ВУЗов, интегрированную с мессенджером "Макс"(далее - Мессенджер).

Задачи, решаемые данной платформой:

1. Централизация управления образовательным процессом
2. Интеграция образовательного процесса с национальным мессенджером "Макс"
3. Улучшение соотношения "затраты-качество" ИТ-инфраструктуры высшего учебного заведения
4. Уменьшение поверхности кибератаки на инфраструктуру высшего образования

# Интеграция с мессенджером "Макс"

Ключевым элементом платформы является мини-приложение для Мессенджера, запускаемое с помощью бота. Платформа использует Max API для идентификации и первичной аутентификации пользователя. Платформа ориентирована на использование основной функциональности Мессенджера для коммуникации между участниками образовательного процесса.

# Сущности

Платформа моделирует следующие сущности:

### 1. Пользователь

Пользователь платформы. Обычно студент, преподаватель или администратор. Идентифицируется уникальным внутренним идентификатором

### 2. ВУЗ

Сущность, соответствующая ВУЗу в реальном мире. Регистрируется на платформе, регистрация одобряется вручную. Предоставляет пользователям экземпляры сервисов.

Идентифицируется уникальным внутренним идентификатором

Пользователь может иметь привязку к любому количеству вузов. Привязка означает, что пользователь участвует в образовательном процессе этих вузов в том или ином качестве.

Так, один человек может быть студентом ВУЗа A, преподавателем в ВУЗах A и B и админстратором в ВУЗе C. А может быть просто студентом одного ВУЗа.

### 3. Сервис

Сущность, предоставляющая полезную функциональность пользователям. Каждый экземпляр сервиса имеет привязку к какому-то вузу и идентифицируется уникальным внутренним идентификатором

Сервисы делятся на 2 типа:

1. Облачные сервисы - их экземпляры разворачиваются в инфраструктуре Платформы.
2. Локальные сервисы - их экземпляры необходимо развернуть сотрудникам ВУЗа в его инфраструктуре.

Техническая администрация ВУЗа выбирает набор предоставляемых сервисов и разворачивает локальные сервисы.

В ядре-клиенте слева список меню с функциональностью сервисов. Обычно одно меню слева - один сервис. Но не обязательно.

В MVP входят сервисы:

1. Сервис администрирования. Облачный. Позволяет управлять ВУЗом, не удаляется. Доступ к нему есть только с профиля администратора, но роли разграничивают возможности.
2. Сервис расписания. Облачный. Студенты делятся на группы. Каждый может видеть данные по своей группе. Преподаватели тоже видят своё расписание. Для администратора есть роль "автор расписания", которая позволяет менять расписание.

### 4. Профиль

Статус пользователя в связке "пользователь-ВУЗ". Отвечает на вопрос "кто этот человек в данном ВУЗе"? MVP включает в себя три стандартных профиля:

- Администратор
- Преподаватель
- Студент

Функциональность, предоставляемая сервисом, может различаться в зависимости от профиля.

Пользователь может переключаться между профилями в рамках ВУЗа, если имеет несколько профилей.

Профиль не локален для сервиса, им управляет ВУЗ.
### 5. Роль

Статус пользователя в связке "пользователь-профиль-экземпляр сервиса". Используется для реализации ролевой модели контроля доступа(RBAC) внутри сервиса.

Возможности, предоставляемые сервисов, могут различаться в зависимости от роли.

Паре "пользователь-профиль-экземпляр сервиса" может соотвествовать несколько ролей. Например, один администратор может совмещать роли "автор расписания" и "главный администратор" в одном экземпляре сервиса.
# Компоненты

Платформа состоит из следующих программных компонентов:

### 1. Бот

Минимальный бот, необходимый для открытия мини-приложения.
### 2. Ядро-бекенд

Код бекенда мини-приложения. Выполняет следующие задачи:

1. Первичная идентификация и аутентификация пользователя посредством интеграции с Мессенджером
2. Аутентификация запросов ядра-клиента
3. Организация и аутентификация взаимодействия между клиентами сервисов и бекендом сервисов
4. Хранение данных о профилях и ролях пользователей сервисов
5. Регистрация и учёт пользователей
6. Регистрация и учёт ВУЗов
7. Регистрация и учёт сервисов ВУЗов
8. Отправка кода ядра-клиента клиенту Мессенджера

### 3. Ядро-клиент

Клиентский код, загружаемый с ядра-бекенда. Выполняет следующие задачи:

1. Отображение общего интерфейса платформы
2. Динамическая загрузка клиентов сервисов
3. Отображение клиентов сервисов внутри своего интерфейса
### 4. Бекенд облачных сервисов

Серверный код, разворачиваемый в инфраструктуре Платформы. Может эмулировать множество экземпляров сервиса. То есть, функциональность облачного сервиса может обеспечиваться лишь одним процессом в инфраструктуре Платформы, имитирующим множественность экземпляров.

Платформа предоставляет возможность выбирать набор облачных сервисов, предоставляемых ВУЗом, через интерфейс.
### 5. Бекенд локальных сервисов

Серверный код, разворачиваемый в инфраструктуре ВУЗа. Позволяет ВУЗам предоставлять дополнительные услуги, не ограниченные облачными сервисами. Бекенд локальных сервисов может быть реализован сторонними разработчиками.

Локальные сервисы предоставляют API своим клиентам.

Вне MVP планируется "магазин сервисов" и процедура проверки безопасности локального сервиса.

### 6. Клиенты сервисов

Клиентский код, доставляемый от сервисов ядру-клиенту. Разворачивается внутри клиента, отвечает за взаимодействие пользователя с сервисом и отображение интерфейса сервиса.
### 7. Service SDK

Библиотека, предоставляющая возможность разрабатывать облачные и локальные сервисы. Обеспечивает единство в структуре кода сервисов разных типов Предоставляет следующую функциональность:

1. Аутентификация общения с клиентом сервиса посредством использования API ядра-бекенда.
2. Разделение функциональности по профилям
3. Контроль доступа по профилям и модели RBAC
4. Слой абстракции между логикой сервиса и его типом
5. API для сообщения информации об экземпляре сервиса

### API ядра-бекенда

Содержит следующие префиксы:

/api/v1/auth - аутентификация пользователя
/api/v1/institution - доступ пользователя к ВУЗу:

/api/v1/institution возвращает список вузов, в которых состоит пользователь
/api/v1/institution/{institution_id} - доступ к ВУЗу
/api/v1/institution/{institution_id}/service - список сервисов у вуза
/api/v1/institution/{institution_id}/service/{service_id} - доступ к экземпляру сервиса

можно, скажем, посмотреть список меню сервиса и имя каждой

/institution - страница выбора ВУЗа. Если у пользователя всего один ВУЗ, сразу редирект на него. Если несколько можно выбрать. Если нет, то нет.
/institution/{institution_id} - понятно, страница ВУЗа. Скачивает ту самую часть ядра-клиента, которая динамически загружает клиенты сервисов

/api/v1/internal - API для сервисов. Сервисы ходят на эту часть API, например, за публичным ключом для проверки JWT-токенов. Тут они могут:

- Добавлять, удалять, назначать роли.
- Получать информацию о ролях и профилях пользователя
- Менять информацию о ролях

Стоит отметить, что редактировать профили(создать профиль, добавить профиль пользователю, убрать) в /api/v1/internal нельзя. Потому что это API для сервисов. Профиль не локален для сервиса, им управляет ВУЗ.

Также стоит отметить, что эта ручка открыта для внешнего мира. Однако необходимо проводить аутентификацию сервиса и избежать уязвимостей
