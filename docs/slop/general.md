В диалоге чётко зафиксированы модель профилей и ролей, сервисная организация портала и состав MVP. Технические детали обсуждались с разной степенью определённости: ниже отделены принятые положения от предложений, для которых в приложенном фрагменте нет явного подтверждения.

### 1. Ядро платформы и сервисы

**Портал строится как расширяемая платформа. Вся прикладная функциональность MVP реализуется сервисами.** Это решение прямо подтверждено в диалоге.

Ядро обеспечивает общие механизмы:

* аутентификацию пользователей;
* регистрацию вузов и связь пользователей с ними;
* профили пользователей внутри вузов;
* контроль доступа по ролям;
* регистрацию и подключение сервисов, API их работы.

Сервисы предоставляют конкретную функциональность: расписание, администрирование, просмотр профилей и другие возможности. Поэтому основа проекта — не только готовый набор функций, но и механизм, позволяющий добавлять новые.

Клиент платформы выступает общей оболочкой: слева пользователь выбирает сервис своего вуза, а клиент выбранного сервиса работает внутри интерфейса портала.

### 2. Пользователь и связь с вузом

**Пользователь — общая сущность платформы, которая не ограничена одним вузом.**

Аутентификация предусмотрена по Max ID и номеру телефона. Один пользователь может быть связан с несколькими вузами. Внутри каждого вуза у него есть собственные профили.

Сам вуз проходит регистрацию на платформе и ручное одобрение поддержкой.

Способ подтверждения принадлежности пользователя к вузу в приложенном диалоге окончательно не выбран. Создание или одобрение профилей администратором и импорт по телефонам были предложениями.

### 3. Профиль: «кто я в этом вузе»

**Профиль обозначает статус пользователя внутри конкретного вуза.**

Для MVP предусмотрены три типа:

| Профиль       | Статус                                   |
| ------------- | ---------------------------------------- |
| Студент       | Пользователь действует как студент       |
| Преподаватель | Пользователь действует как преподаватель |
| Администратор | Пользователь действует как администратор |

У одного пользователя в одном вузе может быть несколько профилей. Например, человек может одновременно быть студентом и преподавателем и переключаться между этими профилями.

Сервисы предоставляют разную функциональность в зависимости от профиля. Таким образом, при работе с порталом имеет значение не только личность пользователя, но и выбранный им статус в конкретном вузе.

Предусмотрена возможность создавать профили, однако точный порядок их создания и круг уполномоченных пользователей в тексте не закреплены.

### 4. Роль: «что мне можно в этом сервисе»

**Роль и профиль — разные понятия. Профиль действует в рамках вуза, роль — в рамках отдельного сервиса.**

Для контроля доступа выбрана модель **RBAC**: разрешённые действия определяются ролями.

Пример из обсуждения — сервис расписания:

* студент и преподаватель могут просматривать расписание;
* администратор с ролью «автор расписания» может его редактировать.

Следовательно, профиль администратора и право редактировать расписание не отождествляются: в примере для редактирования указана отдельная сервисная роль.

В обсуждении предложена следующая структура данных:

`Пользователь → связь с вузом → профиль → назначение роли в подключённом сервисе`

Она соответствует принятому разделению понятий, но конкретная схема таблиц и способ хранения назначений отдельно не утверждались.

### 5. Сервис и его подключение к вузу

**Сервис — подключаемая функциональная часть портала.** Администратор может добавлять и убирать сервисы, доступные своему вузу.

Приняты два типа размещения:

| Тип       | Где работает         |
| --------- | -------------------- |
| Облачный  | На бэкенде платформы |
| Локальный | На стороне вуза      |

В конце диалога подтверждается единая модель работы через JWT для облачных и локальных сервисов. Разница между ними — место размещения.

Для реестра было предложено разделить:

* **описание сервиса** — что это за сервис, его тип, адрес клиента и объявленные роли;
* **подключение сервиса к вузу** — использование этого сервиса конкретным вузом.

Это полезное архитектурное уточнение из диалога, однако явного отдельного утверждения такой модели в приложенном фрагменте нет.

### 6. Набор сервисов MVP

| Сервис                         | Зафиксированные условия                                                                          |
| ------------------------------ | ------------------------------------------------------------------------------------------------ |
| Администрирование              | Облачный, подключён по умолчанию, нельзя удалить; предназначен для профиля администратора        |
| Расписание                     | Облачный, подключён по умолчанию, можно удалить; доступен любому профилю                         |
| Интерфейс профиля пользователя | Доступен по умолчанию                                                                            |
| Просмотр чужих профилей        | Включён в перечень MVP; сервис просмотра информации о пользователе ранее обозначен как локальный |

Загрузка курсовых и дипломных работ, магазин сервисов и проверка сервисов с криптографической подписью отнесены к развитию после MVP.

### 7. Технические решения: границы подтверждённого

Для встраивания клиентов сервисов предложены **iframe**, обмен сообщениями через **postMessage**, проверка источника сообщений и небольшой SDK. Для быстрого переключения — сохранение нескольких загруженных iframe и стандартное HTTP-кеширование.

В одной реплике ассистент уже перечисляет iframe, JWT, короткие access-токены, `sid` и SDK как выбранные решения. Однако предшествующее обсуждение их принятия в приложенном тексте отсутствует. Поэтому считать весь этот список достоверно утверждённым нельзя.

Также остаются предложениями без явного подтверждения:

* разделение баз данных ядра и сервисов;
* реализация администрирования только фронтендом, обращающимся к API ядра;
* точный состав JWT и механизм проверки через JWKS;
* формат манифеста сервиса;
* хранение активного профиля в токене;
* конкретные параметры кеширования и протокол взаимодействия клиента с сервисами.
