## 1. Что это такое и чем не является

`requestContact()` — метод моста, который показывает нативную модалку MAX с просьбой поделиться номером телефона. При согласии приложение получает номер **вместе с подписью**, доказывающей, что этот номер действительно привязан к аккаунту MAX данного пользователя.

Дословная формулировка доки о смысле проверки: *«Если значения совпадают, это подтверждает, что пользователь поделился номером телефона, привязанным к его аккаунту MAX»*.

**Что это даёт:** заверение от платформы — «номер `79990000000` принадлежит аккаунту MAX с `user.id = 67890`». Заверение сильное: подделать его без токена бота нельзя.

**Чем это не является:**

- **Это не подтверждение владения SIM в моменте.** Никакого SMS и кода не отправляется. MAX ручается за привязку, сделанную когда-то при регистрации в мессенджере, а не за то, что телефон сейчас в руках у пользователя. **[вывод]**
- **Это не второй фактор.** Фактор здесь ровно один — доступ к аккаунту MAX. Тот, кто захватил аккаунт MAX, получит и «подтверждённый» номер. Строить на этом 2FA бессмысленно.
- **Это не замена входу.** Вход в MAX-native приложении уже состоялся через `initData` (см. [MAX_ACCOUNTS_AND_PII.md](MAX_ACCOUNTS_AND_PII.md)). Телефон — **дополнительный атрибут**, а не способ аутентификации.

Отсюда главный тезис отчёта: **телефон в мини-приложении MAX нужен не для того, чтобы узнать, кто пользователь — это уже известно из `initData`. Он нужен, чтобы связать известного пользователя MAX с записью в вашей внешней системе.**

## 2. Когда телефон действительно нужен

| Сценарий | Нужен ли телефон | Комментарий |
|---|---|---|
| Узнать, кто пользователь | **нет** | `user.id` из `initData` уже доказан |
| Склейка с CRM / старой клиентской базой | **да** | телефон — обычно единственный общий ключ |
| Программа лояльности, где карта заведена по номеру | **да** | пример из самой доки |
| Статус заказа, оформленного на сайте по телефону | **да** | пример из самой доки |
| Звонок курьера, подтверждение доставки | **да** | рабочая необходимость |
| Рассылки и маркетинг | **нет** | это другая цель и отдельное согласие |
| «Чтобы был» | **нет** | ПД без цели — нарушение принципа минимизации |

Правило: запрашивать номер **в момент, когда он понадобился**, а не на первом экране. Модалка на старте — худшая из возможных схем: она стоит конверсии ровно там, где пользователь ещё не понял ценности сервиса.

⚠️ **Ограничение из доки:** данные, полученные через `requestContact()`, *«могут быть использованы только для взаимодействия с текущим мини-приложением»*. Перечисленные примеры — программы лояльности, проверка статуса заказа, идентификация пользователя. Выгрузка в сторонние системы, продажа, обогащение внешних профилей — за рамками разрешённого.

## 3. Процесс целиком

```
                     пользователь в мини-приложении
                                 │
                    жмёт «Продолжить с номером»
                                 │
                   wa.requestContact()  ──────────────┐
                                 │                     │
                   нативная модалка клиента MAX        │
                         ┌───────┴───────┐             │
                    отказ │               │ согласие   │
                         │                │           │
      reject: user_refused│      resolve: { phone,    │
      _provide_phone_number│              authDate,   │
                         │                hash }      │
                         ▼                │            │
             штатная ветка без            ▼            │
             телефона          POST /api/link-phone    │
                               { phone, authDate,      │
                                 hash }  + сессия      │
                                         │             │
                              бэкенд:    │             │
                              1. берёт userId из СЕССИИ (не из тела!)
                              2. строит строку authDate/phone/userId
                              3. HMAC_SHA256(key = botToken)
                              4. сравнивает с hash
                              5. проверяет свежесть authDate
                                         │
                                         ▼
                              привязка phone → account_id
```

Ключевой момент на шаге 1: `userId` для проверки подписи берётся из **уже проверенной сессии** (то есть из валидированного `initData`), а не из тела запроса. Клиент его и не присылает — в ответе `requestContact()` его нет.

---

## 4. Формат ответа

```ts
Promise<{
    phone: string;      // номер, в формате с '+'
    authDate: string;   // timestamp создания хеша
    hash: string;
}>
```

Обратите внимание: `authDate` — **строка**, а не число (в отличие от `auth_date: number` в `InitData`). И имена здесь camelCase, тогда как в `initData` — snake_case. Это два разных по стилю API, и путаница между ними — источник ошибок.

---

## 5. Проверка подписи

### Формула

```
hash == HMAC_SHA256(key = botToken, message = launch_string)
```

где `launch_string` — пары `key=value`, **в алфавитном порядке ключей**, склеенные через `\n`:

```
authDate=<значение>
phone=<значение без +>
userId=<user.id из initData>
```

Ключи именно такие: `authDate`, `phone`, `userId` — подтверждено дословно. Алфавитный порядок `a → p → u` совпадает с порядком их перечисления в доке.

### ⚠️ Три ловушки

**1. `phone` без `+`.** Буквальная цитата: *«При вычислении хеша значение `phone` не должно содержать `+`: вместо `+7**********` используется `7**********`»*. Это самая частая причина «подпись не сходится». Метод возвращает номер в одном формате, а подписывается он в другом.

**2. Схема HMAC другая, чем у `initData`.** Здесь ключ — **сам токен бота**, напрямую. Никакого промежуточного `secret_key`, выведенного из литерала `"WebAppData"`. Если скопировать функцию валидации из проверки `initData`, подпись не сойдётся, и причина будет неочевидна.

| | `initData` | `requestContact()` |
|---|---|---|
| Ключ HMAC | `HMAC("WebAppData", botToken)` | `botToken` напрямую |
| Состав | все параметры запуска | ровно три поля |
| Имена полей | `auth_date` (snake) | `authDate` (camel) |
| Тип времени | `number` | `string` |

**3. `userId` — ваш вход, а не их выход.** Его нет в ответе метода; вы подставляете его сами. Подставлять нужно **проверенный** id из сессии. Формально схема самозащитна (с чужим id подпись не сойдётся), но брать id из тела запроса — плохая привычка, которая однажды выстрелит в другом месте. **[вывод]**

### Код (Node)

```js
import crypto from 'node:crypto';

const PHONE_AUTH_MAX_AGE_SEC = 300; // окно свежести; доком не задано — наше решение

export function verifyContact({ phone, authDate, hash }, userId, botToken) {
  // 1. Нормализуем номер: для подписи '+' не участвует
  const phoneForHash = String(phone).replace(/^\+/, '');

  // 2. Строка для подписи: ключи в алфавитном порядке, разделитель \n
  const message = [
    `authDate=${authDate}`,
    `phone=${phoneForHash}`,
    `userId=${userId}`,
  ].join('\n');

  // 3. HMAC на токене бота напрямую — НЕ как в initData
  const expected = crypto.createHmac('sha256', botToken).update(message).digest('hex');

  // 4. Сравнение постоянного времени
  const a = Buffer.from(expected, 'hex');
  const b = Buffer.from(String(hash), 'hex');
  if (a.length !== b.length || !crypto.timingSafeEqual(a, b)) return null;

  // 5. Свежесть: защита от повторного использования старого ответа
  const ts = Number(authDate);
  if (!Number.isFinite(ts)) return null;
  if (Math.abs(Date.now() / 1000 - ts) > PHONE_AUTH_MAX_AGE_SEC) return null;

  return { phone: phoneForHash };
}
```

Про шаг 5: окно свежести дока не задаёт — по аналогии с часом для `initData` я бы взял **жёстче**, минуты. Привязка телефона — редкая операция, между показом модалки и запросом к бэкенду проходят секунды. **[вывод]**

Про единицы времени `authDate`: в `initData` это секунды, здесь дока говорит просто «timestamp». Формат стоит проверить эмпирически на первом же реальном ответе — если придут миллисекунды, сравнение со свежестью сломается молча. **[не подтверждено]**

## 6. Фронтенд

```js
async function linkPhone() {
  const wa = window.WebApp;
  try {
    const contact = await wa.requestContact();
    await api.post('/api/link-phone', contact);  // сессионный токен уже в заголовке
    showLinked();
  } catch (e) {
    const code = e?.error?.code ?? '';
    if (code.endsWith('user_refused_provide_phone_number')) {
      showManualFallback();   // отказ — штатный путь, не ошибка
    } else {
      showRetry();            // request_error: сеть/бэкенд, есть смысл повторить
    }
  }
}
```

### Коды ошибок

Формат: `{"error": {"code": "client.request_phone.<reason>"}}`

| Код | Что произошло | Как реагировать |
|---|---|---|
| `client.request_phone.user_refused_provide_phone_number` | пользователь отказался | **штатный сценарий**: продолжить без телефона, предложить ввести вручную |
| `client.request_phone.request_error` | сбой выполнения запроса (сеть, бэкенд) | предложить повтор |

**Отказ — не ошибка.** Приложение обязано оставаться работоспособным без телефона. Экран «без номера дальше нельзя» превращает мягкий запрос в жёсткий барьер и, с учётом принципа минимизации данных, плохо защитим: если сервис работает без номера, требовать его как условие доступа некорректно. **[вывод]**

## 7. Альтернативный путь: контакт через бота

На стороне Bot API есть вложение типа `contact`, которое бот получает, когда пользователь делится контактом в чате:

```json
{
  "type": "contact",
  "vcf_info": "BEGIN:VCARD\r\nVERSION:3.0\r\nTEL;TYPE=cell:79990000000\r\nFN:Ivan Ivanov\r\nEND:VCARD\r\n",
  "max_info": { },
  "hash": "<хеш поля vcf_info>"
}
```

Номер здесь приезжает внутри vCard, отдельным полем его нет — придётся парсить `TEL`. Есть и кнопка `request_contact` в inline-клавиатуре, которая *«запрашивает контакт и номер телефона из аккаунта MAX»*.

Когда это уместно: сценарий целиком живёт в чате с ботом и мини-приложение не открывается. Для мини-приложения путь через мост удобнее — номер приходит готовым полем, а не в vCard, и не требует кругового рейса через вебхук бота.

⚠️ Схема хеширования `hash` у вложения `contact` (подписывается `vcf_info`) в доступной выжимке не расписана. **[не подтверждено]**

## 8. Хранение номера

Телефон — полноценные ПД. Из отчёта [MAX_ACCOUNTS_AND_PII.md](MAX_ACCOUNTS_AND_PII.md) применимо целиком, здесь — специфика.

```sql
ALTER TABLE personal_data
  ADD COLUMN phone_enc      bytea,        -- шифротекст, ключ в KMS/переменных окружения
  ADD COLUMN phone_hash     bytea,        -- HMAC(phone, серверный pepper) — для поиска
  ADD COLUMN phone_linked_at timestamptz,
  ADD COLUMN phone_source   text;         -- 'max_request_contact' | 'manual' | 'crm'
```

Зачем два поля вместо одного:

- **`phone_enc`** — чтобы показать номер пользователю и позвонить курьером. Расшифровывается редко и под аудитом.
- **`phone_hash`** — чтобы искать по номеру («есть ли у нас такой клиент в CRM?») **без расшифровки всей таблицы**. HMAC с серверным pepper, а не голый SHA-256: пространство российских номеров мало, и чистый хеш перебирается за секунды.

**Нормализация обязательна и до хеширования, и до сравнения.** `+79990000000`, `79990000000`, `89990000000` — один и тот же номер. Приведите к единому виду (E.164 без `+` — как раз формат, в котором номер участвует в подписи) и храните только его, иначе поиск по `phone_hash` будет промахиваться.

**`phone_source` пригодится** при разборе инцидентов и при удалении данных: номер, полученный через `requestContact()`, ограничен в использовании условиями платформы, а введённый вручную на вашем сайте — регулируется вашим же согласием. Смешивать их в одной колонке без пометки — значит потерять основание обработки. **[вывод]**

## 9. Краевые случаи

1. **Номер уже привязан к другому аккаунту у вас.** Самый неприятный случай: человек сменил аккаунт MAX, либо номер сменил владельца. Молча сливать аккаунты нельзя — так чужие заказы утекут новому владельцу номера. Нужен явный сценарий разрешения конфликта. **[вывод]**
2. **Номер сменил владельца.** Привязка «навсегда» ошибочна. Разумно хранить `phone_linked_at` и перепроверять привязку при чувствительных операциях либо по истечении срока.
3. **Повторный вызов `requestContact()`.** Метод можно звать снова — например, если пользователь сменил номер в MAX. Нужен UI «обновить номер», а не одноразовая привязка навсегда.
4. **Пользователь отказался, потом передумал.** Точка входа в привязку должна оставаться доступной (в профиле), а не исчезать после первого отказа.
5. **Два аккаунта MAX с одним номером.** Маловероятно (номер обычно и есть идентификатор регистрации), но если возможно — ваш `phone_hash` станет неуникальным. Не вешайте на него `UNIQUE` без осознанного решения, что делать при коллизии. **[вывод]**
6. **Десктоп и веб.** Дока не помечает `requestContact()` как mobile-only (в отличие от биометрии и haptic), так что метод должен работать везде. Но проверить на десктоп-клиенте стоит — там нет DevTools, и отлаживать потом будет дорого. **[не подтверждено]**
7. **Номер в логах.** Тот же риск, что с `initData`: `{ phone, authDate, hash }` в теле запроса легко утекает в APM и трекеры ошибок. Маскировать на уровне middleware.

## 10. Когда этого мало: свой OTP

`requestContact()` не доказывает, что пользователь **сейчас** контролирует номер. Если это принципиально — подписание документов, финансовая операция, требование регулятора, — единственный вариант остаётся классическим: свой одноразовый код по SMS или звонку, со своим антифродом и лимитами.

Разумная комбинация: `requestContact()` как быстрый путь для 95% пользователей, свой OTP — только на чувствительной операции и только для неё. Заставлять всех проходить SMS на входе, когда платформа уже отдаёт заверенный номер в один тап, — потеря конверсии без выигрыша в безопасности для большинства сценариев. **[вывод]**

## 11. Чек-лист

**Запрос**
- [ ] Модалка вызывается в момент реальной нужды, а не на первом экране.
- [ ] Перед вызовом объяснено, зачем нужен номер.
- [ ] Отказ обработан как штатный путь; приложение работает без телефона.
- [ ] Есть способ привязать/обновить номер позже из профиля.

**Проверка**
- [ ] `phone` при подсчёте хеша — **без `+`**.
- [ ] Строка: `authDate=…\nphone=…\nuserId=…`, ключи в алфавитном порядке.
- [ ] Ключ HMAC — токен бота напрямую (не как в `initData`).
- [ ] `userId` взят из проверенной сессии, а не из тела запроса.
- [ ] Сравнение хешей постоянного времени.
- [ ] Проверена свежесть `authDate`; единицы времени подтверждены эмпирически.
- [ ] Токен бота — только на сервере.

**Хранение**
- [ ] Номер нормализован до E.164 без `+`.
- [ ] `phone_enc` (шифрование) и `phone_hash` (HMAC с pepper) разделены.
- [ ] Записан источник номера и время привязки.
- [ ] Телефон вырезан из логов, APM и трекеров.
- [ ] Использование ограничено взаимодействием с этим мини-приложением.
- [ ] Отвязка номера доступна пользователю.

## 12. Что проверить эмпирически

1. **Единицы `authDate`** — секунды или миллисекунды.
2. **Формат `phone` в ответе** — с `+` или без (дока показывает `+7**********` в примере того, чего быть не должно при хешировании, но формат самого ответа явно не фиксирует).
3. **Точная строка для подписи** — дока описывает её словами, дословного примера нет. Соберите на первом реальном ответе и сверьте.
4. **Работает ли метод на десктопе и в веб-версии.**
5. **Схема хеша у вложения `contact`** на стороне бота, если пойдёте этим путём.
