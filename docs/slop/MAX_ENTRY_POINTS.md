# Точки входа в мини-приложение MAX — полный разбор

> Третий отчёт серии: [MAX_MINI_APPS.md](MAX_MINI_APPS.md) (общее устройство), [MAX_INITDATA.md](MAX_INITDATA.md) (формат стартовых данных), этот — про то, **откуда** пользователь попадает в приложение.
> Дата сбора: 19.09.2026. Источники: `dev.max.ru/docs/webapps/*`, `dev.max.ru/docs-api`, SDK `max-bot-api-client-ts`.
> Выводы, которых нет в доке дословно, помечены как **[вывод]**. То, что подтвердить не удалось, — как **[не подтверждено]**.

## 0. Главный принцип

URL мини-приложения регистрируется **один раз** в настройках бота на `business.max.ru`. Дальше он живёт как свойство бота, и пользователь никогда не видит и не вводит его сам. Все точки входа — это разные способы заставить клиент MAX открыть **этот же самый URL** во встроенном WebView, подложив в фрагмент подписанный контекст.

Из этого следует несколько неочевидных вещей:

- **Одно приложение = один URL.** Нет отдельных ссылок на «экран заказа» и «экран профиля». Маршрутизацию внутри приложения вы делаете сами — по `start_param` и `entryPoint`.
- **Приложение всегда открывается со своего корня.** Никакого `/orders/42` в URL от клиента не придёт: путь фиксирован, переменная часть — только payload диплинка.
- **Мини-приложение не существует без бота.** Даже прямая ссылка имеет форму `https://max.ru/<botName>?startapp=...`, то есть адресует бота, а не сайт.

## 1. Сводная таблица

| # | Точка входа | Где инициируется | `entryPoint` | `start_param` | Бот запускается |
|---|---|---|---|---|---|
| 1 | Кнопка запуска в чате с ботом | экран чата | `default` | нет | да, диалог уже есть |
| 2 | Inline-кнопка `open_app` в сообщении | сообщение бота | `default` | нет **[вывод]** | да |
| 3 | Диплинк `?startapp=<payload>` | внешний источник | `default` **[вывод]** | **да** | **нет** |
| 4 | Таббар клиента | нижняя панель MAX | `tabbar` | нет **[вывод]** | нет **[вывод]** |
| 5 | Список чатов | список диалогов | `default` | нет | — |
| 6 | Экран настроек | настройки MAX | `default` | нет | — |
| 7 | `openMaxLink()` из другого мини-приложения | внутри MAX | зависит от ссылки | да, если в ссылке | нет |

Определяется всё это одним вызовом:

```js
const { entryPoint } = await window.WebApp.getLaunchContext();
const payload = window.WebApp.initDataUnsafe.start_param;
const chat = window.WebApp.initDataUnsafe.chat;   // { id, type: 'DIALOG'|'CHAT'|'CHANNEL' }
```

## 2. Кнопка запуска в чате с ботом

Основной сценарий. Как только URL подключён в настройках бота, в чате с ботом появляется кнопка запуска.

При подключении вы выбираете её надпись из четырёх фиксированных вариантов:

| Вариант | Когда уместен |
|---|---|
| **«Открыть»** | универсальный: сервис, каталог, личный кабинет |
| **«Старт»** | приложение с явным началом сценария — анкета, запись, оформление |
| **«Играть»** | игры |
| **без названия** | когда нужна только иконка, текст лишний |

Поменять надпись или URL можно там же, в настройках бота, в любой момент.

**Контекст на входе:** `chat.type === 'DIALOG'`, `chat.id` — идентификатор личного диалога с ботом, `start_param` отсутствует, `entryPoint === 'default'`.

## 3. Inline-кнопка `open_app` в сообщении бота

Бот отправляет сообщение с клавиатурой, одна из кнопок которой открывает мини-приложение. Это способ втянуть пользователя в приложение **из сценария бота**: после ответа на вопрос, по расписанию, в ответ на команду.

Тип кнопки в Bot API:

```json
{
  "type": "open_app",
  "text": "Текст кнопки"
}
```

Описание в доке: *«Открывает мини-приложение внутри чат-бота»*.

В TypeScript-SDK (`@maxhub/max-bot-api`):

```ts
const keyboard = Keyboard.inlineKeyboard([
  [Keyboard.button.callback('Действие', 'payload')],
  [Keyboard.button.link('Открыть ссылку', 'https://max.ru')],
  [Keyboard.button.openApp('Запустить приложение', 'webApp', contactId)]
]);
ctx.reply('Выберите действие', { attachments: [keyboard] });
```

Сигнатура: `button.openApp(text: string, webApp: string, contactId: number)`.

⚠️ **Расхождение источников.** В JSON-схеме публичной доки у `open_app` показаны только `type` и `text`, а SDK требует ещё `webApp` и `contactId`. Точные имена полей в JSON (`web_app`? `contact_id`?) и семантика `contactId` (идентификатор бота? получателя?) в доступной выжимке не раскрыты — **сверяйтесь с `dev.max.ru/docs-api` и типами SDK перед реализацией.** **[не подтверждено]**

**Лимиты клавиатуры:** до **210 кнопок** максимум в **30 рядов**.

**Остальные типы кнопок** (для контекста, чем `open_app` отличается от соседей): `callback` (шлёт `message_callback` на вебхук), `link` (открывает URL, до 2048 символов, во внешней вкладке), `request_contact`, `request_geo_location`, `message` (отправляет заданный текст от имени пользователя), `clipboard` (копирует текст в буфер).

Важно не перепутать: **`link` — это не точка входа в мини-приложение.** Кнопка `link` с адресом твоего сайта откроет его как обычную веб-страницу, без `window.WebApp`, без моста, без подписанных данных. Мини-приложение открывает только `open_app` (и диплинк `?startapp=`).

## 4. Диплинк `?startapp=` — единственный вход извне

```
https://max.ru/<botName>?startapp=<payload>
```

| Параметр | Ограничения |
|---|---|
| `botName` | ник бота, выданный при создании (`idИНН_bot` / `se(orgid)_bot`) |
| `payload` | до **512 символов**; только латиница, цифры, `_`, `-` |

Payload приезжает в `window.WebApp.initDataUnsafe.start_param`.

Две ключевые особенности:

1. **Это единственный способ передать в приложение что-либо снаружи.** Всё остальное открывает приложение «пустым».
2. **Бот при этом не запускается** — диалог с ним не создаётся, `/start` не срабатывает, сообщений от бота пользователь не получает. Приложение открывается сразу.

### Откуда такая ссылка может вести

- **Лендинг или сайт компании** — кнопка «Открыть в MAX».
- **QR-код** — офлайн-точка: стол в кафе, витрина, афиша, упаковка. Payload кодирует номер стола/товара.
- **Стороннее мобильное приложение** — переход в мини-приложение из своего же приложения.
- **Реклама и рассылки** — payload как UTM-метка: дока прямо называет сценарий отслеживания источников пользователей.
- **Реферальные программы** — payload с id пригласившего.

### Ограничения payload, о которых стоит помнить заранее

Разрешённый алфавит (`A-Za-z0-9_-`) — это **ровно base64url без `=`**. Значит:

- обычный base64 не пройдёт из-за `=` и `+/`;
- JSON в открытом виде не пройдёт (`{`, `"`, `:`);
- кириллица не пройдёт.

**[вывод]** Практичный подход: держать в payload короткий ключ (`ord_8fa21c`), а сами данные забирать с бэкенда по этому ключу. 512 символов — это про запас, а не приглашение паковать туда состояние.

## 5. Таббар

`getLaunchContext()` возвращает `entryPoint: 'tabbar'`, дословно — *«мини приложение запущено из таббара»*. То есть у клиента MAX есть нижняя панель, из которой мини-приложение может быть запущено напрямую, минуя чат с ботом.

⚠️ **Как приложение туда попадает — в доступной документации не описано.** Нет ни настройки в кабинете, ни метода API, ни критериев отбора. По вторичным источникам, в MAX формируется **закрытая витрина приложений** с уклоном в госуслуги, медицину, образование и корпоративные сервисы — похоже, размещение там курируется платформой, а не самообслуживание. **[не подтверждено]**

Что с этим делать практически: **обрабатывать `entryPoint === 'tabbar'` всё равно стоит**, даже если ваше приложение туда не попадёт. Стоимость — несколько строк, а сценарий принципиально другой: пользователь пришёл «в приложение», а не «в чат с ботом», и ждёт главный экран сервиса, а не продолжение диалога.

## 6. Список чатов и экран настроек

Дословное описание значения `default`: *«мини приложение запущено из списка чатов / экрана чата / экрана настроек»*.

То есть под одним значением `default` платформа объединяет три разных места клиента:

- **экран чата** — кнопка запуска или inline-кнопка (пп. 2–3);
- **список чатов** — запуск, не заходя в диалог;
- **экран настроек** — судя по всему, для сервисных приложений.

Механика попадания в список чатов и в настройки в доке не описана. **[не подтверждено]** Важен сам факт: `default` — это **не** «запущено из чата», а «запущено не из таббара». Различить внутри `default`, пришёл ли пользователь из диалога или из списка, через `getLaunchContext()` нельзя; косвенный признак — `chat.type` и наличие `chat.id`. **[вывод]**

## 7. Переходы внутри MAX: `openMaxLink()`

```js
window.WebApp.openMaxLink('https://max.ru/<some-url>');
```

Дословно: *«Открывает диплинк вида `https://max.ru/<some-url>` из мини-приложения внутри MAX»*.

Это даёт связки между приложениями: одно мини-приложение может открыть другое (или бота, или чат), передав payload через `?startapp=`. Для экосистемы из нескольких сервисов одного вендора — штатный способ навигации.

Не путать с `openLink(url)`, который выбрасывает пользователя **во внешний браузер** — оттуда он в приложение уже не вернётся с сохранённым контекстом.

## 8. Шеринг как канал дистрибуции

Сам по себе шеринг — не точка входа, но именно он порождает ссылки, по которым приходят новые пользователи.

**Отправка текста/ссылки в MAX:**

```
https://max.ru/:share?text=<URL-encoded текст>
```

Параметр `text` обязателен, спецсимволы требуют URL-кодирования. Открывает экран «Отправить в MAX».

**Из мини-приложения:**

- `shareMaxContent({ text?, link? })` — шеринг внутри MAX;
- `shareMaxContent({ mid, chatType })` — пересылка медиа: бот отправляет контент, приложение получает `mid` сообщения и передаёт его вместе с `chatType: 'DIALOG' | 'CHAT'`.
  Дословная оговорка доки: *«В метод передаются либо `text` и/или `link`, либо `mid` и `chatType`. Если при шеринге медиа или файла передать `text` или `link`, они будут проигнорированы»* — то есть это **два взаимоисключающих режима**, смешивать нельзя.
- `shareContent({ text?, link? })` — нативное системное меню «Поделиться», **только iOS/Android**. Для выхода за пределы MAX (в другие мессенджеры, заметки, почту).

**Виральная петля целиком:** пользователь в приложении → `shareMaxContent({ link: 'https://max.ru/mybot?startapp=ref_123' })` → друг получает ссылку в MAX → тапает → попадает в приложение с `start_param = 'ref_123'`, минуя бота.

## 9. Чего среди точек входа нет

Полезно знать, на что **нельзя** рассчитывать при планировании:

- **Глобального поиска приложений** в клиенте — не описан; витрина закрытая и курируемая. **[не подтверждено]**
- **Attach-menu** (как у Telegram: приложение в меню вложений любого чата) — в доке нет.
- **Произвольного URL-пути** — клиент открывает только зарегистрированный корневой URL, свой роутинг стройте на `start_param`.
- **Запуска из канала для читателя** — тип `CHANNEL` в `chat.type` есть, но как именно оттуда запускается приложение, дока не раскрывает. **[не подтверждено]**
- **Открытия приложения по инициативе бота** — бот может прислать кнопку, но не может открыть приложение принудительно. **[вывод]**

## 10. Практика: один роутер на все входы

Ключевой момент — **код запуска обязан быть один**, а ветвление происходит после чтения контекста. Типичная ошибка: писать логику только под кнопку в чате, а потом обнаружить, что при входе с диплинка `chat` выглядит иначе.

```js
async function bootstrap() {
  const wa = window.WebApp;
  const { entryPoint } = await wa.getLaunchContext();
  const { start_param: payload, chat, user } = wa.initDataUnsafe;

  // 1. Авторизация — одинаково для всех точек входа,
  //    всегда по сырой строке initData, не по объекту
  const session = await fetch('/api/session', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify({ initData: wa.initData })
  }).then(r => r.json());

  // 2. Аналитика источника — до всякой отрисовки
  track('app_open', {
    entryPoint,
    hasPayload: Boolean(payload),
    chatType: chat?.type ?? null,
    platform: wa.platform
  });

  // 3. Маршрутизация
  if (payload) {
    return routeByPayload(payload, session);   // диплинк: глубокий экран
  }
  if (entryPoint === 'tabbar') {
    return renderHome(session);                // таббар: главный экран сервиса
  }
  return renderChatEntry(session, chat);       // чат/список/настройки
}

function routeByPayload(payload, session) {
  // payload — base64url-совместимая строка, приходит от пользователя.
  // Валидировать по белому списку, не доверять, не eval-ить, не подставлять в DOM.
  const [kind, id] = payload.split('_');
  switch (kind) {
    case 'ord':   return renderOrder(id, session);
    case 'table': return renderTableMenu(id, session);
    case 'ref':   return renderHome(session, { referrer: id });
    default:      return renderHome(session);
  }
}
```

### Чек-лист по точкам входа

- [ ] Приложение корректно стартует **без** `start_param` — это самый частый случай.
- [ ] `start_param` валидируется по белому списку; неизвестный payload ведёт на главный экран, а не в ошибку.
- [ ] Обработан `entryPoint === 'tabbar'` — пользователь там не ждёт продолжения диалога с ботом.
- [ ] Учтено, что при входе по диплинку **бота в чатах может не быть вообще**: не ссылайтесь на «вернитесь в чат с ботом» вслепую.
- [ ] `chat.type` разобран для всех трёх значений (`DIALOG` / `CHAT` / `CHANNEL`); решено, что является ключом сессии — `user.id`, `chat.id` или пара.
- [ ] Источник входа логируется в аналитику с первого экрана.
- [ ] Для выхода наружу используется `openLink`, для переходов внутри MAX — `openMaxLink`.
- [ ] `BackButton` настроен: при входе с диплинка на глубокий экран пользователю нужен путь «назад» к главному.
