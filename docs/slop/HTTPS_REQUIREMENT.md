# Требование HTTPS для мини-приложения MAX — пруфы и обоснование

> Отчёт по запросу: откуда взялось утверждение, что адрес мини-приложения обязан быть `https`, и почему так устроено.
> Дата: 21.09.2026. Первоисточник — `dev.max.ru/docs/webapps/introduction`.
> Цитаты из документации приведены дословно; всё, что является моим рассуждением, помечено **[вывод]**.

---

## 1. Короткий ответ

Требование зафиксировано в официальной документации MAX **дважды, в двух разных местах одной страницы**, и сформулировано безальтернативно: «только `https://`». Это не рекомендация и не следствие чьей-то интерпретации.

Сверх того, требование совпадает с тем, как устроены мобильные платформы: на iOS плоский HTTP по умолчанию блокируется системой на уровне приложения, а не сайта. Даже если бы MAX это разрешал, страница по `http://` не открылась бы в клиенте.

## 2. Пруф: прямые цитаты из документации

Страница [«Подключение мини-приложения»](https://dev.max.ru/docs/webapps/introduction), раздел подготовительных шагов:

> «Загрузите файлы мини-приложения — `.html`, `.css`, `.js` и необходимые медиафайлы на хостинг, например, [VK Cloud](https://cloud.vk.com/promopage/max-mini-app/), [GitHub Pages](https://docs.github.com/ru/pages) или [Yandex Cloud](https://yandex.cloud/ru)»

> **«Убедитесь, что приложение работает по защищённому соединению — `https`»**

Там же, раздел требований к URL мини-приложения — дословно, списком:

> - «Длина: не более 1024 символов»
> - **«Протокол: только https://»**
> - «Допустимые символы: буквы (латиница), цифры, точка (.) и дефис (-)»
> - «Пробелы не поддерживаются»
> - «URL должен быть валидным»

Два независимых утверждения: одно в инструкции по подготовке, другое в формальных требованиях к полю. Формулировка «только https://» не оставляет места для `http`.

### Побочное наблюдение по этому же списку

Раз **протокол вынесен отдельным пунктом**, пункт про допустимые символы («латиница, цифры, точка и дефис») описывает **не весь URL, а доменную часть** — иначе он противоречил бы соседнему пункту, запрещая `:` и `/` в самом `https://`. **[вывод]**

Это снимает неоднозначность, которую я отмечал в [MAX_MINI_APPS.md](MAX_MINI_APPS.md) и [MINIAPP_SETUP.md](MINIAPP_SETUP.md). Вопрос о допустимости **пути** (`/app/`) по-прежнему открыт: список ограничивает домен, про путь не говорит ничего.

### Косвенные подтверждения в той же документации

- Метод `downloadFile(url, file_name)` в MAX Bridge описан как загрузка файла **по HTTPS** — тот же принцип применён к другому API.
- Все три хостинга, названные в доке (VK Cloud, GitHub Pages, Yandex Cloud), отдают статику по HTTPS по умолчанию. Выбор примеров согласован с требованием. **[вывод]**

## 3. Почему так: четыре независимые причины

Важно, что причин несколько и они **не зависят друг от друга**. Даже если бы платформа сняла своё правило, остальные три никуда бы не делись.

### 3.1 Правило платформы

Самое прямое: поле в кабинете валидируется. URL с `http://` не пройдёт проверку при сохранении, и приложение просто не будет привязано к боту. Обходного пути нет — программной привязки URL в Bot API не существует (там только читающий `GET /me`).

### 3.2 iOS блокирует HTTP на уровне системы

App Transport Security (ATS) в iOS **требует HTTPS по умолчанию для всех сетевых соединений приложения**, и `WKWebView` этому подчиняется: веб-контент внутри него должен идти по HTTPS, если разработчик приложения явно не прописал исключения в `Info.plist`.

Ключевой момент: исключения прописывает **разработчик клиента MAX**, а не вы. Рассчитывать, что национальный мессенджер включил `NSAllowsArbitraryLoads` ради чужих HTTP-страниц, не приходится. То есть `http://`-мини-приложение не загрузилось бы на iOS, даже будь оно зарегистрировано. **[вывод]**

### 3.3 Половина веб-API не работает вне защищённого контекста

Мини-приложение — обычная веб-страница, и на неё распространяется понятие **secure context**. По определению, документ является защищённым контекстом, если он доставлен по **HTTPS** или с локального адреса (`localhost`, `127.0.0.0/8`, `::1`). Страница по `http://<IP-сервера>` защищённым контекстом **не является**.

Что при этом отваливается (список неполный, но показательный):

| API | Нужен secure context |
|---|---|
| `navigator.clipboard` | да |
| Service Workers, офлайн-режим | да |
| `getUserMedia()` (камера, микрофон) | да |
| Geolocation | да (в современных браузерах) |
| Web Crypto `crypto.subtle` | да |

Последняя строка особенно неприятна: `crypto.subtle` — это то, чем считается HMAC в официальном примере валидации `initData`. Вне защищённого контекста он недоступен.

Проверить, где вы находитесь, можно одной строкой:

```js
console.log(window.isSecureContext);   // false на http://<IP>
```

### 3.4 Модель угроз: `initData` — предъявительский credential

Это главная содержательная причина, и она вытекает из разбора в [MAX_INITDATA.md](MAX_INITDATA.md).

В мини-приложение приезжает подписанный блок с ФИО пользователя, его `user.id`, чатом и подписью. Как разобрано в [MAX_ACCOUNTS_AND_PII.md](MAX_ACCOUNTS_AND_PII.md), этой строкой **аутентифицируется пользователь**: кто ею владеет, тот и пользователь — до истечения окна `auth_date`.

Теперь представим, что страница отдаётся по `http://`:

1. Любой, кто находится между пользователем и сервером (публичный Wi-Fi, провайдер, скомпрометированный роутер), может **подменить содержимое страницы** — HTTP не аутентифицирован и не зашифрован.
2. Атакующему достаточно внедрить в неё одну строку JS.
3. Эта строка читает `window.WebApp.initData` и отправляет на свой сервер.
4. Дальше он предъявляет её вашему бэкенду и **получает доступ к аккаунту жертвы** — подпись-то настоящая.

То есть по HTTP ломается не «приватность трафика», а **вся модель аутентификации мини-приложения целиком**. Плюс в открытом виде по сети идут ФИО пользователя, то есть персональные данные — со всеми обязанностями оператора из [MAX_ACCOUNTS_AND_PII.md](MAX_ACCOUNTS_AND_PII.md).

### 3.5 Бонус: mixed content в обратную сторону

Смежный механизм, о который спотыкаются при частичном переезде на HTTPS. Если страница по HTTPS обращается к API по `http://`, браузер **блокирует** такие запросы: `fetch()` и `XMLHttpRequest` относятся к категории blockable mixed content и не апгрейдятся, а отклоняются.

Отдельно: запросы **по IP-адресу не апгрейдятся, а блокируются** — даже те типы ресурсов, которые в других случаях браузер молча переводит на HTTPS. Ещё один довод против схемы «сервер по IP».

Вывод: HTTPS нужен **и фронтенду, и API**. Схема «страница по https, бэкенд по http://IP» не поедет.

## 4. Что это значит для текущего проекта

В [MAX-hackathon-app](MAX-hackathon-app) сервис `web` — это `nginx:stable-alpine` с `listen 80` и публикацией `80:80`. TLS не настроен нигде.

| Что произойдёт | Почему |
|---|---|
| URL `http://<IP>` не сохранится в кабинете | «Протокол: только https://» |
| Даже при сохранении страница не откроется на iOS | ATS блокирует HTTP в `WKWebView` |
| `crypto.subtle` и `navigator.clipboard` недоступны | не secure context |
| Запросы к API с HTTPS-страницы на `http://` будут заблокированы | blockable mixed content |
| `initData` перехватывается и воспроизводится | HTTP не аутентифицирован |

Причём сам код бота и страницы к этому отношения не имеет — там всё в порядке. Ломается именно транспорт.

## 5. Как выполнить требование

| Вариант | Трудозатраты | Комментарий |
|---|---|---|
| **GitHub Pages** | минуты | HTTPS из коробки, адрес стабилен, назван в доке как пример. Контейнер `web` тогда не нужен вовсе — остаётся только `bot` |
| **Домен + Let's Encrypt** (certbot рядом с nginx) | часы | нужен домен; полный контроль; подходит, если фронтенд и API на одном сервере |
| **Cloudflare перед сервером** | десятки минут | TLS терминируется у них; нужен домен |
| VK Cloud / Yandex Cloud | часы | названы в доке; плюс РФ-локализация для ПД |

### Почему голый IP не подходит

Формально `https://93.184.215.14` под требование «латиница, цифры, точка и дефис» подходит — цифры и точки. Но практически:

- публичные удостоверяющие центры сертификаты на IP-адрес почти не выдают, а самоподписанный сертификат WebView отклонит;
- запросы по IP браузеры **блокируют**, а не апгрейдят.

Нужен домен. **[вывод]**

### Про localhost

`http://localhost` и `127.0.0.1` **являются** защищённым контекстом по определению — поэтому локальная разработка страницы работает без TLS. Но зарегистрировать такой адрес в кабинете нельзя: клиент MAX на телефоне пойдёт по нему в собственный localhost. Локально проверяется вёрстка, а всё, что касается моста и `initData`, — только на реальном хостинге.

## 6. Как проверить, что всё сделано правильно

```bash
# 1. Сертификат валиден и цепочка полная
curl -sI https://ваш-домен | head -1          # ожидаем 200

# 2. HTTP редиректит на HTTPS, а не отдаёт контент
curl -sI http://ваш-домен | head -1           # ожидаем 301/308
```

В самом приложении:

```js
console.log(window.isSecureContext);          // должно быть true
console.log(location.protocol);               // 'https:'
```

Чек-лист:

- [ ] Зарегистрированный URL начинается с `https://`.
- [ ] Сертификат выдан публичным УЦ, цепочка полная (не самоподписанный).
- [ ] HTTP редиректит на HTTPS.
- [ ] API бэкенда тоже по HTTPS — иначе запросы заблокируются как mixed content.
- [ ] Все подключаемые ресурсы по HTTPS (мост `https://st.max.ru/js/max-web-app.js` — уже да).
- [ ] `window.isSecureContext === true` в клиенте MAX.
