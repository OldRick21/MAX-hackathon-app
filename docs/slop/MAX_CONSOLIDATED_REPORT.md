# Часть I. Что такое MAX и его платформа

## 1. Контекст

**MAX** — российский мессенджер, развиваемый VK и продвигаемый как национальная коммуникационная платформа. С 1 сентября 2025 года предустанавливается на все продаваемые в РФ смартфоны. Для инженера важно другое: MAX построен как **супер-приложение** — мессенджер, внутри которого работают сторонние сервисы, не требующие отдельной установки. Ближайшие аналоги по архитектуре — Telegram Mini Apps и WeChat Mini Programs.

Платформа для разработчиков состоит из трёх сущностей:

| Сущность | Что это |
|---|---|
| **Чат-бот** | программа, общающаяся с пользователем сообщениями через HTTP API |
| **Мини-приложение** | веб-страница, открываемая внутри клиента MAX во встроенном WebView |
| **Канал** | вещательный формат, аналог каналов в других мессенджерах |

Ключевое ограничение, которого нет в Telegram: **мини-приложение существует только внутри чат-бота**. Прямая цитата из документации: *«Мини-приложения работают только внутри чат-ботов в MAX и не могут существовать автономно»* **[ДОК]**. Автономной ссылки на приложение, как `t.me/app` у Telegram, не существует — всё адресуется через бота.

## 2. Барьер входа

В отличие от большинства мессенджерных платформ, зарегистрировать бота «из-под личного аккаунта» нельзя.

| Требование | Детали |
|---|---|
| Кто может публиковать | юрлицо, ИП или самозанятый — **резидент РФ** **[ДОК]** |
| Где | кабинет партнёра `business.max.ru` |
| Модерация | **до 48 часов** в рабочие дни **[ДОК]** |
| Что даётся после | токен бота и доступ к настройкам, включая поле URL мини-приложения |

Карточка бота при создании: логотип 500×500 px (до 5 МБ), имя 1–59 символов, автогенерируемый ник вида `idИНН_bot` или `se(orgid)_bot`, описание до 200 символов **[ДОК]**.

Практическое следствие для команды: **доступ — это внешняя зависимость со сроком до двух суток**, её нельзя закрыть кодом. Планировать получение доступа нужно до начала разработки, а не параллельно.

## 3. Инструменты платформы

| Инструмент | Что это | Где |
|---|---|---|
| **Bot API** | HTTP API для ботов | `https://platform-api2.max.ru` **[ДОК]** |
| **MAX Bridge** | JS-мост между веб-страницей и клиентом | `https://st.max.ru/js/max-web-app.js` **[ДОК]** |
| **MAX UI** | React-компоненты в фирменном дизайне | npm `@maxhub/max-ui` |
| **SDK ботов** | клиенты Bot API | TypeScript, Go, Python — `github.com/max-messenger` |
| Гайдлайн | Figma с примерами интерфейсов | упомянут в документации |

# Часть II. Боты

## 4. Bot API: базовые факты

```
База:          https://platform-api2.max.ru
Авторизация:   заголовок  Authorization: <токен>
```

Отдельно стоит отметить: *«Передача токена через query-параметры больше не поддерживается»* **[ДОК]**. Многочисленные сторонние статьи с примерами вида `?access_token=` устарели и дадут `401`.

Основные эндпоинты:

| Метод | Назначение |
|---|---|
| `GET /me` | информация о боте |
| `GET /updates` | получение событий через long polling |
| `POST /subscriptions` | регистрация webhook |
| `POST /messages` | отправка сообщений |

Коды ответов: `200`, `400`, `401`, `404`, `429` (лимит), `503` **[ДОК]**.

Схема ответа `/me` установлена по типам SDK **[SDK]**:

```ts
type BotInfo = {
  user_id: number;
  name: string;            // deprecated → first_name / last_name
  first_name: string;
  last_name?: string;
  username: string | null;
  is_bot: boolean;
  last_activity_time: number;
  description?: string | null;
  avatar_url?: string;
  full_avatar_url?: string;
  commands?: BotCommand[] | null;
};
```

Из этого следует важный отрицательный результат: **поля, сообщающего о привязанном мини-приложении, в API нет**, а весь модуль работы с ботом в SDK — это два метода, `getMyInfo()` и `editMyCommands()`. Узнать программно, привязан ли к боту URL приложения, нельзя.

## 5. Доставка событий: polling против webhook

| | Long polling (`GET /updates`) | Webhook (`POST /subscriptions`) |
|---|---|---|
| Кто инициирует | бот опрашивает сервер | MAX шлёт события на ваш URL |
| Нужен публичный HTTPS | нет | да |
| Оценка документации | *«ограничено по скорости и сроку хранения событий»*, для продакшена не рекомендуется **[ДОК]** | рекомендуется |

Практическая стратегия: разработка на polling (работает с ноутбука, ничего не настраивая), продакшен на webhook. Код обработчиков при переходе не меняется.

Два правила для webhook-эндпоинта, о которые чаще всего спотыкаются:

1. **Отвечать `200` немедленно**, до обработки. Иначе платформа сочтёт доставку неуспешной и будет ретраить.
2. **Быть идемпотентным.** Ретрай означает повторную доставку того же события.

## 6. Клавиатуры и типы кнопок

Лимит: до **210 кнопок** в **30 рядов**.

| Тип | Действие |
|---|---|
| `callback` | присылает боту событие `message_callback` с payload |
| `link` | открывает URL |
| `request_contact` | запрашивает контакт и номер телефона |
| `request_geo_location` | запрашивает геопозицию |
| `message` | отправляет боту заданный текст от имени пользователя |
| `clipboard` | копирует текст в буфер обмена |
| **`open_app`** | **открывает мини-приложение** |

Полная схема `open_app` в документации не раскрыта — там показаны только `type` и `text`. Мы восстановили её по типам SDK **[SDK]**:

```ts
type OpenAppButton = {
  type: 'open_app';
  text: string;
  web_app?: string | null;
  contact_id?: number | null;
  payload?: string | null;
};

// фабрика в SDK:
openApp: (text: string, webApp: string, contactId?: number, payload?: string) => OpenAppButton
```

Два практически значимых вывода: `web_app` и `contact_id` **опциональны**, и у кнопки **есть `payload`** — то есть параметр в приложение можно передать прямо из inline-кнопки, а не только через диплинк. Что именно платформа ожидает в `web_app` — ссылку на бота или идентификатор приложения — ни документация, ни типы не определяют **[?]**.

# Часть III. Мини-приложения: архитектура

## 7. Что это технически

Мини-приложение — **обычный статический сайт** (HTML/CSS/JS), отданный по HTTPS, который клиент MAX открывает во встроенном WebView и связывает с мессенджером через глобальный объект `window.WebApp`.

```
      business.max.ru (кабинет)
      └─ в настройках бота вписан URL приложения
                    │
 пользователь ──► кнопка в чате / inline-кнопка / диплинк / таббар
                    │
         клиент MAX (iOS / Android / desktop / web)
                    │  открывает WebView
                    ▼
      ваш фронтенд на HTTPS-хостинге
        │  <script src="https://st.max.ru/js/max-web-app.js">
        │  window.WebApp — мост к клиенту
        ▼
      ваш бэкенд ──► валидация initData (HMAC на токене бота)
```

Ключевой момент: **URL регистрируется один раз** в кабинете и дальше является свойством бота. Пользователь его не видит и не вводит. Программной привязки нет — только руками в кабинете (см. §4).

Требования к URL **[ДОК]**:

- длина не более 1024 символов;
- **протокол: только `https://`**;
- допустимые символы: латиница, цифры, точка, дефис;
- пробелы не поддерживаются;
- URL должен быть валидным.

Поскольку протокол вынесен отдельным пунктом, пункт про допустимые символы описывает **доменную часть**, а не весь URL — иначе он запрещал бы `:` и `/` в самом `https://` **[ВЫВОД]**. Допустимость пути (`/app/`) списком не оговорена **[?]**.

## 8. Требование HTTPS и почему оно жёсткое

В документации требование зафиксировано дважды: *«Убедитесь, что приложение работает по защищённому соединению — `https`»* и *«Протокол: только https://»* **[ДОК]**.

Помимо правила платформы действуют три независимых технических причины — они остались бы в силе, даже сними MAX своё требование:

1. **iOS блокирует HTTP на уровне системы.** App Transport Security требует HTTPS по умолчанию для всех соединений приложения, и `WKWebView` этому подчиняется. Исключения прописывает разработчик клиента MAX, а не вы.
2. **Страница по HTTP не является secure context.** Отваливаются `navigator.clipboard`, service workers, `getUserMedia`, геолокация и — что особенно существенно — `crypto.subtle`, на котором построен официальный пример валидации подписи.
3. **Модель угроз.** В приложение приезжает подписанный блок с ФИО пользователя и его идентификатором, которым оно и аутентифицируется. По HTTP атакующий в канале подменяет страницу, внедряет строку JS, читает `window.WebApp.initData` и предъявляет его вашему бэкенду с настоящей подписью. Ломается не приватность трафика, а вся модель аутентификации целиком **[ВЫВОД]**.

Смежное следствие: **HTTPS нужен обоим концам**. Страница по HTTPS, обращающаяся к API по `http://`, работать не будет — `fetch` относится к категории blockable mixed content и блокируется браузером, а запросы по IP-адресу блокируются даже там, где другие типы ресурсов молча апгрейдятся. Голый IP не подходит ещё и потому, что публичные УЦ практически не выдают сертификаты на IP.

## 9. Точки входа

Платформа различает их через `getLaunchContext()`, но только на два значения.

| Точка входа | Что это | `entryPoint` | `start_param` |
|---|---|---|---|
| Кнопка запуска в чате с ботом | появляется автоматически после привязки URL; надпись выбирается при подключении: «Открыть» / «Старт» / «Играть» / без названия **[ДОК]** | `default` | нет |
| Inline-кнопка `open_app` | бот присылает сообщение с клавиатурой | `default` | через `payload` кнопки **[SDK]** |
| **Диплинк** | ссылка вида `https://max.ru/<botName>?startapp=<payload>` | `default` **[ВЫВОД]** | **да** |
| Таббар | нижняя панель клиента | `tabbar` | нет **[ВЫВОД]** |
| Список чатов, экран настроек | описаны в доке как часть `default` **[ДОК]** | `default` | нет |

**Диплинк** (deep link) — ссылка, открывающая не приложение вообще, а конкретное место внутри него с параметром. Формально это HTTPS-адрес, поэтому его можно положить в QR-код, на лендинг, в рекламу или в стороннее приложение. Payload: до 512 символов, алфавит `A-Za-z0-9_-` — это ровно base64url без паддинга, то есть ни обычный base64, ни JSON, ни кириллица не пройдут **[ВЫВОД]**.

Две особенности диплинка, определяющие дизайн:

- это **единственный способ передать в приложение что-либо снаружи** (остальные входы открывают его «пустым»);
- переход по нему **открывает приложение, не запуская бота** — диалога с ботом может не существовать вовсе, поэтому нельзя строить сценарии на «вернитесь в чат с ботом».

**Таббар** (tab bar) — нижняя панель с иконками основных разделов клиента. Оттуда приложение может быть запущено напрямую, минуя чат. Как приложение туда попадает, в документации не описано **[?]**; по вторичным источникам витрина курируется платформой.

Чего среди точек входа **нет**: глобального поиска приложений, attach-menu как в Telegram, произвольного URL-пути от клиента, возможности боту открыть приложение принудительно.

## 10. Внутренний URL и роутинг

Клиент открывает зарегистрированный URL, дописывая к нему **фрагмент**:

```
https://example.com#WebAppData=<подписанные данные>&WebAppPlatform=web&WebAppVersion=26.2.8
```

Путей и query-параметров от клиента не приходит. Отсюда несколько жёстких следствий:

**Первый GET принципиально анонимный.** Фрагмент после `#` не отправляется на сервер, поэтому при отдаче HTML вы не знаете, кто пришёл: SSR с персонализацией невозможен, первый кадр всегда рисуется без данных пользователя.

**Hash-роутер использовать нельзя.** Фрагмент у страницы один, и клиент MAX его занял. Роутер, пишущий `#/orders/42`, затрёт `WebAppData`. Нужен History API: `BrowserRouter`, а не `HashRouter`; `createWebHistory`, а не `createWebHashHistory` **[ВЫВОД]**. `initData` следует прочитать один раз при старте, до инициализации роутера, и держать в памяти.

**Подписан только `WebAppData`.** `WebAppPlatform` и `WebAppVersion` лежат рядом вне подписи и подделываются тривиально — на них нельзя завязывать проверки доступа.

## 11. MAX Bridge: обзор API

Подключается одной строкой, отдельной инициализации не требует, npm-пакета не имеет:

```html
<script src="https://st.max.ru/js/max-web-app.js"></script>
```

| Группа | Методы |
|---|---|
| Данные запуска | `initData`, `initDataUnsafe`, `platform`, `version`, `deviceName` |
| Контекст | `getLaunchContext()` |
| Экран | `getViewportSize()`, `requestScreenMaxBrightness()`, `restoreScreenBrightness()`, `ScreenCapture.enable/disableScreenCapture()` |
| Пользователь | `requestContact()` |
| Навигация | `BackButton.show/hide/onClick/offClick`, `enable/disableClosingConfirmation()` |
| Ссылки и шеринг | `openLink()` (внешний браузер), `openMaxLink()` (внутри MAX), `shareContent()` (нативное меню, только iOS/Android), `shareMaxContent()`, `downloadFile()` |
| Хранилище | `DeviceStorage.*`, `SecureStorage.*` (**лимит 10 ключей на бота**) |
| Железо | `openCodeReader()` (QR), `BiometricManager.*` (только мобильные), `HapticFeedback.*` (только мобильные), `NfcManager.*` (только Android) |

Почти все методы возвращают Promise; при отказе reject приходит как `{ error: { code: string } }`.

Платформенные ограничения существенны: биометрия и haptic только на мобильных, NFC только Android, `shareContent` только iOS/Android. Проверять `WebApp.platform` и делать фолбэк обязательно.

# Часть IV. Идентичность, аутентификация и данные

## 12. `initData` и `initDataUnsafe`

Это **одни и те же данные в двух представлениях**, приезжающие при каждом запуске приложения.

| | `initData` | `initDataUnsafe` |
|---|---|---|
| Тип | строка в URL-кодировке | объект |
| Назначение | **валидация на сервере** | чтение в UI |
| Доверие | источник истины после проверки подписи | *«объект нельзя использовать для валидации данных»* **[ДОК]** |

Причина разделения: подпись считается по точной байтовой строке, и любой парсинг её разрушает.

Состав (интерфейс дословно из документации):

```ts
interface InitData {
    query_id: string;          // уникален на каждый запуск
    ip?: string;
    auth_date: number;         // рекомендуемое окно валидности — 1 час
    hash: string;
    user: { id, first_name, last_name, username, language_code, photo_url };
    chat: { id, type: 'DIALOG' | 'CHAT' | 'CHANNEL' };
    start_param: string;       // payload диплинка
}
```

Два расхождения интерфейса с реальностью, видимые в примере самой документации: `username` и `photo_url` там равны `null`, хотя объявлены как `string` без `?`. Считать их nullable обязательно **[ВЫВОД]**.

### Слои кодирования — главный источник багов

`WebAppData` — это query-строка, вложенная в query-строку, поэтому кодирование двойное. На примере из документации:

```
Слой 0 (сырой фрагмент):   chat%3D%257B%2522id%2522%253A12345...
Слой 1 (после разбора фрагмента):  chat=%7B%22id%22%3A12345%2C%22type%22%3A%22DIALOG%22%7D&ip=...
Слой 2 (после decodeURIComponent):  chat={"id":12345,"type":"DIALOG"}
```

Именно слой 2 подписывается. Отсюда типовая ошибка: скормить `initData` в `new URLSearchParams()` (которая декодирует автоматически) и затем применить `decodeURIComponent` ещё раз — подпись не сойдётся.

### Алгоритм проверки

```
launch_params = все пары key=value, кроме hash,
                значения URL-декодированы,
                ключи отсортированы a→z,
                склеены через \n

secret_key = HMAC_SHA256(key = "WebAppData", message = BOT_TOKEN)
signature  = hex(HMAC_SHA256(key = secret_key, message = launch_params))
signature === hash   →   данные подлинные
```

**Порядок аргументов обратен телеграмовскому**: там ключом выступает токен, а сообщением литерал; здесь наоборот. Это стоит часа отладки тем, кто переносит код из Telegram.

Дополнительно: параметры приходят в произвольном порядке (в примере документации — не алфавитном), сортировка обязательна; официальный пример использует `localeCompare` и `split('=')`, оба неустойчивы на краевых случаях, надёжнее байтовая сортировка и разбор по первому `=`.

### Что подпись доказывает, а что нет

**Доказывает:** данные выпустил MAX; ни одно поле не изменено; данные выпущены для вашего бота (ключ выведен из вашего токена).

**Не доказывает:** свежести (проверка `auth_date` — ваша работа) и того, что запрос делает тот самый человек прямо сейчас. Подписанная строка — **предъявительский credential**: кто ею владеет, тот и пользователь, до истечения окна.

Каналы утечки, по убыванию вероятности: сторонние скрипты на странице (любой из них читает `location.hash`), трекеры ошибок вроде Sentry, отправляющие полный URL, собственный код, положивший `initData` в query-строку. Сам по себе фрагмент относительно защищён — он не уходит ни в HTTP-запрос, ни в `Referer`.

**Важное ограничение жизненного цикла:** `initData` — снимок на момент старта, он не обновляется, метода запросить свежий нет. Поэтому окно в час — это окно на **первичный обмен** на сессию; поддерживать долгую сессию нужно собственным механизмом на бэкенде.

## 13. Телефон: `requestContact()`

Второй механизм идентификации — нативная модалка с запросом номера.

```ts
requestContact(): Promise<{ phone: string; authDate: string; hash: string }>
```

Схема подписи здесь **другая**:

```
hash == HMAC_SHA256(key = botToken, message = "authDate=…\nphone=…\nuserId=…")
```

Ключом выступает сам токен, без промежуточного `secret_key`; ключи camelCase против snake_case в `initData`; `authDate` — строка против числа. И отдельная ловушка: *«При вычислении хеша значение `phone` не должно содержать `+`»* **[ДОК]**. `userId` в ответе метода отсутствует — его подставляет бэкенд из проверенной сессии.

Что это даёт по существу: заверение платформы, что номер **привязан к аккаунту MAX**. Это **не** подтверждение владения SIM в моменте и **не** второй фактор — фактор здесь один, доступ к аккаунту MAX. Для операций, требующих доказательства владения номером здесь и сейчас, остаётся свой OTP.

Ограничение использования, зафиксированное документацией: данные *«могут быть использованы только для взаимодействия с текущим мини-приложением»* **[ДОК]**. Отказ пользователя (`user_refused_provide_phone_number`) — штатный сценарий, приложение обязано работать без телефона.

## 14. Архитектура аккаунтов

**Рекомендация: аутентификация по `user.id` из проверенного `initData`, без собственного логина и пароля.**

Обоснование: после проверки подписи `user.id` — доказанное утверждение платформы, по силе эквивалентное успешному входу по паролю. Добавлять поверх этого свою учётку — значит взять на себя хранение секретов, восстановление доступа и связанный класс уязвимостей, не получив ничего: прийти иначе как через MAX пользователь всё равно не может.

Приятное следствие, специфичное для мини-приложений: подписанная идентичность приезжает при каждом холодном старте, поэтому refresh-токены и долгоживущие куки не нужны.

Рассмотренные альтернативы и когда они оправданы:

| Вариант | Когда применим |
|---|---|
| Чистый MAX-ID | **база для MAX-native приложения** |
| + телефон через `requestContact()` | нужна склейка с CRM, офлайн-кассой, легаси-базой |
| Собственная учётка (e-mail/пароль) | только если появится второй контур входа вне MAX |
| Без серверного аккаунта (`DeviceStorage`) | приложение без состояния; как дополнение к основному |
| Digital ID | нужна верификация возраста или льготного статуса |

**Digital ID** — отдельный продукт MAX: цифровой аналог документов, данные подтягиваются из Госуслуг и верифицируются обеими системами; позволяет подтвердить совершеннолетие и статусы (студент, многодетный, инвалид, пенсионер). Доступен продавцам только из числа юрлиц и ИП, требует отдельного токена со сроком жизни 1 год **[ДОК]**. Правильный паттерн — хранить факт проверки, а не документ.

Официального «Войти через MAX» (OAuth/OIDC-провайдера для сторонних сайтов) в документации нет **[?]**. Найденные по запросу решения — это либо сторонние плагины на базе бота с одноразовым кодом, либо интеграция MAX как клиента к Госуслугам по OpenID Connect, то есть в обратную сторону.

## 15. Персональные данные

Правила платформы формулируют статус разработчика прямо: он действует *«как самостоятельный оператор персональных данных»*, платформа ответственности не несёт **[ДОК]**. Из правил следуют конкретные требования к продукту:

| Требование | Что это значит в коде |
|---|---|
| правовое основание сбора | экран согласия, фиксация версии и времени |
| публикация документов | политика обработки ПД по URL, ссылка из приложения |
| технические меры защиты | шифрование, разграничение доступа, журналирование |
| **удаление аккаунта и данных по требованию** | это фича, которую надо заложить |
| подтверждение оснований **в течение 3 дней** по запросу платформы | логи согласий должны быть готовы заранее |

Плюс контур 152-ФЗ, актуальный тем более, что публиковаться могут только резиденты РФ: локализация первичной обработки в базах на территории России, минимизация состава данных, раздельные согласия на разные цели.

**Инженерная рекомендация — не хранить лишнего.** ФИО приезжает в каждом запуске бесплатно, фото доступно по ссылке, `username` меняется. Всё это можно рендерить из `initDataUnsafe`, не записывая в БД.

Предлагаемая модель данных разводит псевдонимы и ПД по разным таблицам:

```
accounts       — внутренний UUID, статус, время. Никаких ПД.
identities     — (provider, external_id) → account_id. Сюда лягут будущие провайдеры.
personal_data  — шифрованный телефон, HMAC-хеш для поиска, согласия, срок хранения.
orders/…       — ссылаются только на account_id.
```

Стоит один join, но позволяет удалить ПД по требованию, не разрушив бизнес-историю, и резко сужает радиус поражения при утечке. Отдельно: `initData` не должен попадать в логи, APM и трекеры ошибок — строка выглядит технической, а содержит ФИО.

# Часть V. Модель доверия

## 16. Что может хост-приложение

Этот раздел меняет рамку всего предыдущего и важен при проектировании.

Академическая работа «Don't Trust the Super-App: A Case Study of Russia's Max» (препринт arXiv, 10 сентября 2026, группа Roya Ensafi, Мичиганский университет) разбирает клиент MAX методом динамической инструментации через Frida на выборке из 90 мини-приложений. Задокументированы пять возможностей хоста по отношению к любому мини-приложению внутри него **[ВНЕШ.]**:

1. **Снятие изображения интерфейса** через Android PixelCopy, успешность 88,5 %, без специальных разрешений и без уведомления — включая текст, введённый в форму до отправки.
2. **Доступ к хранилищу мини-приложений**: данные, проходящие через `DeviceStorage` и `SecureStorage`, видны хосту в открытом виде до шифрования.
3. **Инъекция JavaScript** через `evaluateJavascript`; мини-приложение не может отличить внедрённое событие от легитимного.
4. **Посредничество в сетевом трафике** через `shouldInterceptRequest`: загрузки, запросы, консольные логи, ошибки.
5. **Подмена пользователя**: хост формирует `WebAppData`, а мини-приложение не имеет независимого способа проверить, что данные соответствуют реальному пользователю.

Авторы подчёркивают, что это **не эксплуатация уязвимости, а следствие архитектуры**: все мини-приложения живут как WebView в одном UID и одной песочнице процесса, и такие привилегии супер-приложениям выдаёт сама ОС. Аналогичная модель действует в Telegram, WeChat и других супер-приложениях.

### Что из этого следует разработчику

**Подпись `initData` защищает вас от пользователя, но не от платформы.** Вся ваша аутентификация в конечном счёте доверяет MAX полностью. Это не аргумент против разработки — это граница, которую надо знать:

- `SecureStorage` не является секретным хранилищем в криминалистическом смысле — не кладите туда то, что не должно быть видно платформе **[ВЫВОД]**;
- чувствительные операции (крупные платежи, подписание документов) разумно подтверждать вторым каналом вне мини-приложения **[ВЫВОД]**;
- сторонние токены и ключи сессий других сервисов внутри мини-приложения находятся в доверенной зоне платформы.

Полный разбор клиента, включая находки в APK (сбор списка установленных приложений и детект VPN, самообновление мимо Google Play, серверный переключатель проверки TLS, отсутствие E2EE) и последствия регистрации для пользователя, вынесен в отдельный отчёт [MAX_SECURITY_REVIEW.md](MAX_SECURITY_REVIEW.md) — это соседняя тема, не связанная с разработкой напрямую.

## 19. Результаты: что осталось неизвестным

Честный перечень — это часть результата. Каждый пункт помечен способом проверки.

| Открытый вопрос | Почему важен | Как проверить |
|---|---|---|
| Глобален ли `user.id` или выдаётся в рамках бота | если per-bot — два бота увидят человека как двух разных | два тестовых бота на один аккаунт, сравнить id |
| Присутствует ли `chat` при запуске из таббара | код падает на `chat.type`, если поля нет | диагностическая страница, запуск из таббара |
| Входит ли `start_param` в подписанную часть | если да — payload диплинка доверенный; если нет — это непроверенный пользовательский ввод | диагностическая страница, вход по диплинку |
| Совпадает ли `initData` байт в байт с сырым `WebAppData` | влияет на число декодирований | вывести обе строки рядом |
| Единицы `authDate` в `requestContact` (секунды или мс) | при ошибке проверка свежести молча ломается | первый реальный ответ метода |
| Что ожидается в `web_app` у кнопки `open_app` | от этого зависит, откроется ли приложение | перебор вариантов на живом клиенте |
| Как приложение попадает в таббар | влияет на дистрибуцию | вопрос платформе |
| Всегда ли появляется кнопка запуска в чате | определяет, нужен ли запасной путь входа | открыть чат с ботом на разных клиентах |
| Куда попадает `payload` кнопки `open_app` | в `start_param` или отдельным полем | диагностическая страница |
| Допустим ли путь в URL приложения | влияет на структуру хостинга | попытка сохранить URL в кабинете |

**Практический вывод из этого списка:** прежде чем писать продуктовый фронтенд, следует выложить **диагностическую страницу**, выводящую `platform`, сырой `location.hash`, `initData`, `initDataUnsafe` и результат `getLaunchContext()`. Причина прагматичная: в десктоп-клиенте MAX **нет DevTools** — ни Inspect, ни F12, ни описанного способа их включить. Отлаживать приходится в веб-версии MAX, где работает обычный браузерный инструментарий, но её поведение отличается от клиента (User-Agent, политики безопасности, нативные интеграции). Одна страница закрывает сразу шесть пунктов таблицы выше.

# Часть VII. Практические выводы

## 21. Порядок работ

1. Получить доступ: токен бота и понимание, кто вписывает URL приложения в кабинет (внешняя зависимость до 48 часов).
2. Проверить токен: `GET /me` → записать `username`, он нужен для диплинков.
3. Поднять бота на long polling, локально.
4. Зафиксировать **HTTPS**-адрес фронтенда — он должен совпасть с зарегистрированным символ в символ. Туннели вроде ngrok не подходят: адрес меняется при перезапуске.
5. Выложить диагностическую страницу, закрыть открытые вопросы из §19.
6. Проверить кнопку запуска в чате — она работает без кода в боте.
7. Добавить команду с inline-кнопкой `open_app`, сверив аргументы по типам SDK.
8. Поднять `/api/session` с валидацией `initData`.
9. Заменить диагностику продуктовым фронтендом (React + `@maxhub/max-ui`).
10. Перед продакшеном: webhook вместо polling, хостинг в РФ при работе с ПД.

## 22. Сводка типовых ошибок

**Аутентификация**
- Использовать `initDataUnsafe` на бэкенде — валидация в принципе невозможна.
- Перенести валидатор из Telegram, не поменяв порядок аргументов HMAC.
- Декодировать значения дважды (`URLSearchParams` + `decodeURIComponent`).
- Не проверять `auth_date` — перехваченная строка работает вечно.
- Переиспользовать валидатор `initData` для `requestContact` — там другая схема.
- Забыть убрать `+` из номера при подсчёте хеша.

**Архитектура**
- Hash-роутер — затирает `WebAppData`.
- Приложение не переживает отсутствие `start_param` — это самый частый случай.
- Не обработан `entryPoint === 'tabbar'`.
- Единственный путь входа завязан на кнопку в чате.
- Расчёт на `chat`/`username`/`photo_url` как на обязательные поля.

**Инфраструктура и данные**
- HTTP-хостинг: URL не зарегистрируется, на iOS не откроется, `crypto.subtle` недоступен.
- API по HTTP при странице по HTTPS — mixed content блокируется.
- `initData` в query-строке, логах или Sentry — утечка ПД.
- Токен бота вне переменных окружения: он же ключ подписи, его утечка = подделка любой личности.
- Сторонние скрипты на странице: каждый читает `location.hash`.
- `SecureStorage` как основное хранилище — лимит 10 ключей и видимость для хоста.
