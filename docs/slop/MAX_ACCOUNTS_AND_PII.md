## 1. Короткий ответ

**Делайте аутентификацию по `user.id` из подписанного `initData` и не изобретайте свою.** Логин/пароль, e-mail, коды подтверждения, «забыли пароль» — всё это в MAX-native приложении не нужно и вредно: вы добавите себе хранение секретов, флоу восстановления и новый класс уязвимостей, не получив взамен ничего, потому что пользователь всё равно не может прийти иначе как через MAX.

Ключевой факт: `initData` **криптографически подписан** токеном вашего бота. После проверки подписи `user.id` — это не «то, что сказал клиент», а доказанное утверждение платформы «этот запуск сделал вот этот пользователь MAX». По силе это эквивалент успешного входа по паролю, только без пароля.

Персональные данные при этом лучше **не хранить вообще**, а если нужно — хранить у себя на серверах в РФ, в минимальном объёме, отдельно от рабочих таблиц, и никогда не полагаться на MAX как на хранилище.

Дальше — почему именно так, какие есть варианты и где подводные камни.

## 2. Что платформа даёт в качестве идентификаторов

| Идентификатор | Откуда | Подтверждён подписью | ПД? | Стабильность |
|---|---|---|---|---|
| `user.id` | `initData` | **да** | сам по себе — псевдоним; в связке с ФИО становится ПД | предположительно постоянный **[не подтверждено]** |
| `user.first_name` / `last_name` | `initData` | да | **да, ПД** | меняется пользователем |
| `user.username` | `initData` | да | косвенно | меняется пользователем; в примере доки бывает `null` |
| `user.photo_url` | `initData` | да | **да** (биометрия-адъяцентно) | меняется; бывает `null` |
| `user.language_code` | `initData` | да | нет | RFC 5646 |
| телефон | `requestContact()` | да, отдельной подписью | **да, ПД** | меняется редко |
| `chat.id` + `chat.type` | `initData` | да | нет | стабилен для диалога |
| `query_id` | `initData` | да | нет | **уникален на каждый запуск** |
| `ip` | `initData` | да | **да, ПД** по практике РКН | меняется постоянно |
| Digital ID | отдельный продукт MAX | — | **да, чувствительные** | идентификатор ротируется раз в 25 секунд |

Три вывода из таблицы:

1. **Вы получаете ФИО пользователя, даже если оно вам не нужно.** `first_name`/`last_name` приезжают в каждом запуске. Это уже обработка ПД — с момента первого сохранения в вашу БД.
2. **`query_id` — не идентификатор пользователя.** Он новый на каждый запуск; годится как nonce против replay, не как ключ.
3. **Телефон отдельно не приходит.** Только явным запросом с модальным окном и отдельной подписью — то есть это осознанное решение пользователя, и у него есть стоимость в конверсии.

### 2.1 Главный непроверенный риск: глобален ли `user.id`

В документации **нигде не сказано**, уникален ли `user_id` глобально или выдаётся в рамках конкретного бота. **[не подтверждено]** Для Telegram он глобален; для MAX подтверждения нет.

Почему это важно: если id окажется per-bot, то два ваших бота (или будущая миграция на другого бота) увидят одного человека как двух разных, и связать аккаунты без телефона будет невозможно.

**Что делать:** относиться к `user.id` как к **непрозрачному внешнему ключу**, а не как к первичному. В БД первичный ключ — ваш внутренний UUID, а `(provider='max_bot_<id>', external_id=user.id)` лежит в отдельной таблице идентичностей. Тогда при любом развитии событий вы добавляете строку, а не переписываете схему. Проверяется это за полчаса: заведите второго тестового бота на тот же аккаунт и сравните `user.id` в обоих мини-приложениях.

## 3. Варианты архитектуры аккаунта

### Вариант A. Чистый MAX-ID — **рекомендуемый**

Аккаунт создаётся автоматически при первом запуске. Паролей нет, экрана входа нет.

```
запуск → initData → проверка HMAC на бэкенде → upsert по max_user_id → сессия
```

- **Плюсы:** нулевой фрикшен (пользователь уже «вошёл», ничего не заметив), нечего красть (нет паролей), нечего восстанавливать, нет форм ввода — а значит и типового набора уязвимостей вокруг них.
- **Минусы:** доступ только внутри MAX; при потере аккаунта MAX данные пользователя недостижимы; вы зависите от стабильности `user.id`.
- **Когда:** условие задачи — ровно этот случай.

### Вариант B. MAX-ID + телефон как второй ключ

То же, что A, плюс `requestContact()` в тот момент, когда телефон **реально нужен** (связать с существующей клиентской базой, программа лояльности, доставка, звонок курьера).

- **Плюсы:** склейка с вашей прежней базой (CRM, офлайн-касса, старое приложение); устойчивость к смене `user.id`; омниканальность.
- **Минусы:** это уже полноценные ПД со всеми обязанностями оператора; модалка режет конверсию; телефон меняет владельца — привязка «навсегда» ошибочна.
- **Когда:** есть офлайн- или легаси-контур, который надо связать с мини-приложением.
- ⚠️ Дока прямо ограничивает использование: данные из `requestContact()` *«могут быть использованы только для взаимодействия с текущим мини-приложением»* — примеры из доки: программы лояльности, статус заказа, идентификация пользователя. Рассылки в обход, продажа, обогащение внешних профилей — за рамками.

### Вариант C. Собственный аккаунт (e-mail/пароль) + привязка MAX

Классическая своя учётка, MAX — один из способов входа.

- **Плюсы:** работает вне MAX (веб, мобильное приложение); пользователь не теряет данные вместе с мессенджером.
- **Минусы:** всё, чего вы избегаете в A: хранение паролей, восстановление, верификация почты, привязка/отвязка, коллизии при слиянии аккаунтов. Плюс экран входа поверх мессенджера выглядит инородно и убивает конверсию.
- **Когда:** **не ваш случай по условию.** Оправдан, только если появится второй контур входа. Если такая вероятность ненулевая — берите A, но со схемой из §5, которая превращается в C добавлением одной строки в таблицу идентичностей, без миграции данных.

### Вариант D. Вообще без серверного аккаунта

Состояние живёт в `DeviceStorage` / `SecureStorage` на устройстве, бэкенда с ПД нет.

- **Плюсы:** предельная минимизация — нет ПД, нет обязанностей оператора, нет утечки; хакатонная скорость.
- **Минусы:** данные не переживают смену устройства и переустановку; `SecureStorage` — **максимум 10 ключей на бота**; на бэкенде невозможна аналитика и серверная логика.
- **Когда:** калькулятор, тест, игра без прогресса, справочник. Для приложения «с аутентификацией» — недостаточно, но как **дополнение** к A полезно: кэш UI-настроек на клиенте вместо лишних полей в БД.

### Вариант E. Digital ID — для подтверждённых статусов

Отдельный продукт MAX: цифровой аналог паспорта, данные подтягиваются пользователем из Госуслуг и верифицируются обеими системами. Позволяет подтвердить совершеннолетие и статусы (студент, многодетный, инвалид, пенсионер). Предъявление — QR (Android/iOS) или NFC (только Android), идентификатор обновляется каждые 25 секунд.

- **Это не замена входа, а слой верификации** поверх аккаунта из A/B. **[вывод]**
- Доступен продавцам только из числа **юрлиц и ИП** — самозанятым нет. Нужен отдельный API-токен со **сроком жизни 1 год**; перевыпуск временно отключает все подключённые точки.
- **Когда:** возрастные ограничения, льготные тарифы, скидки по статусу.
- ⚠️ Это чувствительные данные. Правильный паттерн — **хранить факт, а не документ**: `age_verified_at`, `status='student'`, срок действия. Никаких сканов и реквизитов у себя.

### Чего в MAX нет

Официального «Войти через MAX» (OAuth/OIDC-провайдера для сторонних сайтов) в документации для разработчиков **я не нашёл**. То, что находится по запросу, — это либо сторонние плагины, реализующие вход через бота и одноразовый код, либо интеграция MAX **как клиента** к Госуслугам по OpenID Connect, то есть в обратную сторону. **[не подтверждено]** Рассчитывать на «SSO через MAX для нашего сайта» не стоит.

### Сводка

| | A: MAX-ID | B: +телефон | C: своя учётка | D: без сервера | E: Digital ID |
|---|---|---|---|---|---|
| Фрикшен входа | нет | средний | высокий | нет | средний |
| Объём ПД | минимальный | средний | средний | нулевой | высокий |
| Работа вне MAX | нет | нет | да | нет | нет |
| Склейка с CRM | нет | да | да | нет | нет |
| Сложность | низкая | средняя | высокая | низкая | высокая |
| Для нашей задачи | **база** | по необходимости | нет | как дополнение | если нужны статусы |

## 4. Механика сессии

### 4.1 Обмен `initData` на сессию

Мини-приложение отличается от обычного веба тем, что **подписанная идентичность приезжает при каждом запуске заново**. Это снимает целый пласт задач: не нужны refresh-токены, «запомнить меня», долгоживущие куки. Каждый холодный старт — это полноценная новая аутентификация стоимостью в один HMAC.

```js
// backend: POST /api/session
app.post('/api/session', async (req, res) => {
  const data = parseAndValidate(req.body.initData, BOT_TOKEN);  // см. MAX_INITDATA.md §6
  if (!data) return res.status(401).json({ error: 'invalid_init_data' });

  // data.user.id доверенный — только теперь его можно использовать как ключ
  const account = await upsertAccount({
    externalId: String(data.user.id),
    provider: `max_bot_${BOT_ID}`,
    languageCode: data.user.language_code,
  });

  const token = signSessionJWT({ sub: account.id, ttl: '30m' });
  res.json({ token, profile: publicProfile(account) });
});
```

**Правила:**

1. **Срок жизни сессии — короткий** (15–60 минут). Продление — повторной отправкой свежего `initData`, а не refresh-токеном.
2. **`auth_date` проверять обязательно** — дока рекомендует окно в 1 час. Без этого перехваченный `initData` работает вечно.
3. **`query_id` уникален на запуск** — можно складывать в кэш с TTL и отклонять повтор, закрывая replay полностью. **[вывод]**
4. **Сессионный токен — в память JS**, не в `localStorage`. Приложение всё равно переполучает `initData` при каждом старте, так что хранить нечего.
5. **`initDataUnsafe` на бэкенде не появляется никогда.** Если фронт отправляет разобранный объект — валидация невозможна в принципе.
6. **Токен бота — только на сервере.** Он же ключ подписи: утёк токен — подделывается любая личность.

### 4.2 Проверка телефона — другая формула

Важная ловушка: `requestContact()` подписывается **иначе**, чем `initData`.

```
hash == HMAC_SHA256(key = botToken, message = "authDate=<...>\nphone=<...>\nuserId=<...>")
```
где пары идут в алфавитном порядке ключей и склеены через `\n`.

Отличия от `initData`: здесь ключом HMAC выступает **сам токен бота** (без промежуточного `secret_key` из литерала `"WebAppData"`), и набор полей фиксирован.

⚠️ **`phone` при подсчёте хеша — без `+`**: вместо `+7**********` берётся `7**********`. Это буквальная цитата из доки и самая вероятная причина «подпись не сходится».

Коды ошибок: `client.request_phone.user_refused_provide_phone_number` (пользователь отказался) и `client.request_phone.request_error` (сбой запроса). Отказ — **штатный сценарий**, приложение обязано продолжать работать без телефона.

## 5. Модель данных: где что лежит

Основная идея — **развести псевдонимы и персональные данные по разным таблицам** с самого начала. Это стоит один join, но даёт возможность удалить ПД по требованию пользователя, не разрушив бизнес-историю, и резко сужает радиус поражения при утечке.

```sql
-- Ядро: никаких ПД, только псевдонимы. Живёт вечно.
CREATE TABLE accounts (
  id            uuid PRIMARY KEY,
  created_at    timestamptz NOT NULL,
  last_seen_at  timestamptz NOT NULL,
  status        text NOT NULL          -- active | deleted
);

-- Идентичности: сюда же лягут будущие провайдеры, если появятся.
CREATE TABLE identities (
  account_id   uuid REFERENCES accounts(id),
  provider     text NOT NULL,          -- 'max_bot_42'
  external_id  text NOT NULL,          -- user.id из MAX
  linked_at    timestamptz NOT NULL,
  PRIMARY KEY (provider, external_id)
);

-- ПД: отдельная таблица, шифрование на уровне колонок, отдельные права доступа.
CREATE TABLE personal_data (
  account_id    uuid PRIMARY KEY REFERENCES accounts(id),
  phone_enc     bytea,                 -- если собран через requestContact()
  phone_hash    bytea,                 -- HMAC с серверным pepper — для поиска без расшифровки
  display_name  text,                  -- если реально нужен в UI
  consent_at    timestamptz,           -- когда и на что согласился
  consent_ver   text,
  purge_after   timestamptz            -- срок хранения
);

-- Бизнес-данные ссылаются только на account_id.
CREATE TABLE orders (
  id uuid PRIMARY KEY,
  account_id uuid REFERENCES accounts(id),
  ...
);
```

### Что осознанно **не** хранить

| Данные | Почему не хранить | Что делать вместо |
|---|---|---|
| `first_name` / `last_name` | приезжают в каждом `initData` бесплатно | брать из запуска, показывать, не сохранять |
| `photo_url` | ПД + протухшая ссылка | отдавать в `<img>` напрямую из `initDataUnsafe` |
| `username` | меняется, склейка по нему сломается | не использовать как ключ |
| `ip` | ПД, ценности почти нет | не писать; если нужен антифрод — хешировать и хранить часы, не годы |
| сырой `initData` | содержит ФИО и подпись; в логах живёт вечно | **вырезать из логов на уровне middleware** |
| документы Digital ID | чувствительные ПД | хранить только факт проверки и срок |

Отдельно: **`initData` не должен попадать в логи, APM, Sentry и трассировки.** Это самая вероятная утечка ПД в таком приложении — строка выглядит технической, а содержит ФИО, и оседает в облачном хранилище логов, возможно за границей. **[вывод]**

### Хранение на клиенте

- `DeviceStorage` — UI-настройки, черновики, последняя вкладка. Не ПД.
- `SecureStorage` — шифрованное, **лимит 10 ключей на бота**. Годится для небольшого секрета, но не как хранилище профиля.
- Ни то, ни другое не заменяет сервер: это WebView на устройстве пользователя, данные не переживут переустановку и не должны быть источником истины.

## 6. Правовой контур (инженерная выжимка)

Правила платформы для разработчиков формулируют это прямо: разработчик действует **«как самостоятельный оператор персональных данных»**. MAX ответственности за вашу обработку не несёт. Из правил следуют конкретные требования к продукту:

| Требование правил | Что это значит в коде/продукте |
|---|---|
| обеспечить правовое основание сбора | экран согласия при первом запуске, если собираете ПД; фиксация версии и времени согласия |
| опубликовать в общем доступе необходимые документы | политика обработки ПД по URL, ссылка из приложения |
| правовые, организационные и **технические** меры защиты | шифрование, разграничение доступа к таблице ПД, журналирование |
| прекращать обработку при достижении цели / по требованию | `purge_after`, фоновая чистка |
| **свободная возможность удаления аккаунта и данных из приложения** | это фича, которую надо заложить: экран «Удалить аккаунт» |
| платформа может запросить подтверждение оснований **в течение 3 дней** | документы и логи согласий должны быть под рукой, а не «потом соберём» |

Плюс общий контур 152-ФЗ, актуальный тем более, что публиковаться в MAX могут только российские юрлица/ИП/самозанятые:

- **Локализация:** первичный сбор, запись, систематизация, накопление, хранение, уточнение и извлечение ПД граждан РФ — в базах на территории РФ. Практически: БД в российском облаке (VK Cloud, Yandex Cloud), не в зарубежном.
- **Минимизация:** собирать только то, что нужно для конкретной цели. Это не только закон, но и лучшая инженерная стратегия здесь — см. таблицу «что не хранить».
- **Раздельные согласия** на разные цели (работа сервиса ≠ маркетинговые рассылки).
- **Регистрация оператора** в реестре РКН и уведомление — процедурная часть, не инженерная, но сроки закладывайте.
- Зарубежные облака и сервисы без первичного размещения в РФ — недопустимы. Это касается и **логов с аналитикой**: типовой Sentry/GA на зарубежных серверах с ПД внутри — ровно тот случай.

## 7. Краевые случаи и риски

1. **`user.id` может оказаться per-bot** → схема из §5 позволяет пережить это добавлением строки. **[не подтверждено]**
2. **Один человек — два аккаунта MAX** (личный и рабочий): для вас это два разных пользователя. Склейка возможна только по телефону, и только если он собран.
3. **Телефон сменил владельца.** Привязка «навсегда» ошибочна: при входе по MAX-ID с уже привязанным чужим телефоном нужен сценарий перепривязки, а не молчаливое слияние. **[вывод]**
4. **Пользователь удалил аккаунт MAX** → он навсегда теряет доступ к своим данным у вас. В варианте A это неизбежная плата за отсутствие пароля; честно написать об этом в интерфейсе.
5. **Запуск из группового чата или канала** (`chat.type = 'CHAT' | 'CHANNEL'`): `user` — не обязательно владелец контента, а один и тот же человек приходит с разными `chat.id`. Решите заранее: ключ сессии — `user.id`, а `chat.id` — только контекст. **[вывод]**
6. **Вход по диплинку без бота**: пользователь может не иметь диалога с ботом вообще, поэтому нельзя строить восстановление доступа на «напишите боту».
7. **`username`/`photo_url` бывают `null`** вопреки типам в интерфейсе — падение на `user.username.toLowerCase()` в проде выглядит именно так.
8. **Отладка вслепую:** в десктоп-клиенте нет DevTools. Ошибки авторизации ловятся только серверными логами — но при этом из логов надо вырезать `initData`. Логируйте **результат** проверки и `user.id`, не входную строку.
9. **Утечка токена бота = полная компрометация.** Это одновременно ключ подписи и ключ к Bot API. Только переменные окружения, ротация при подозрении.

## 8. Чек-лист

**Аутентификация**
- [ ] Нет экранов логина/пароля/почты/OTP — вход происходит неявно из `initData`.
- [ ] Подпись `initData` проверяется на каждом создании сессии; `auth_date` — не старше часа.
- [ ] `query_id` проверяется на повтор (anti-replay).
- [ ] Сессия короткая, продлевается свежим `initData`; refresh-токенов нет.
- [ ] `user.id` используется только после успешной валидации, и нигде — из `initDataUnsafe`.

**Данные**
- [ ] Первичный ключ — внутренний UUID; `max_user_id` лежит в таблице идентичностей.
- [ ] ПД отделены от бизнес-таблиц, шифруются, доступ разграничен.
- [ ] ФИО, фото, `ip`, `username` не сохраняются без явной необходимости.
- [ ] `initData` вырезан из логов, APM и трекеров ошибок.
- [ ] Телефон запрашивается только в момент реальной нужды; отказ — штатный путь.
- [ ] Формула хеша телефона — с `phone` **без `+`**.

**Соответствие правилам**
- [ ] БД с ПД физически в РФ.
- [ ] Политика обработки ПД опубликована, ссылка есть в приложении.
- [ ] Согласие фиксируется с версией и временем.
- [ ] Реализован экран «Удалить аккаунт и данные».
- [ ] Сроки хранения заданы, чистка автоматизирована.
- [ ] Аналитика и логи — на российских серверах либо без ПД.

## 9. Что проверить перед реализацией

1. **Глобален ли `user.id`** — два тестовых бота, один аккаунт, сравнить. Определяет живучесть схемы идентичностей.
2. **Точный формат строки для хеша `requestContact()`** — дока описывает её словами («параметры в алфавитном порядке, `key=value` через `\n`»), но дословного примера строки нет. Собрать эмпирически на реальном ответе.
3. **Приходит ли `start_param` в подписанной части `WebAppData`** — если да, диплинк можно использовать для доверенных сценариев (инвайты, привязка). Если нет — payload остаётся непроверенным пользовательским вводом. **[не подтверждено]**
4. **Условия доступа к Digital ID** — если возрастная верификация в скоупе, уточнить порядок получения токена и сроки.
5. **Юридическая часть** — необходимость регистрации оператора и формулировки согласий с юристом.
