# Ядро-клиент

Реализация находится в `frontend/`. Это браузерная оболочка платформы: она входит через MAX, получает свои вузы и профили, показывает каталог и открывает клиент выбранного сервиса в iframe. Код сервиса не вставляется в DOM оболочки и не исполняется через `eval` или динамический `import`.

Основание: [манифест](../SPEC_MANIFEST.md), [контракт ядра](CORE_API_OPENAPI.yaml), [клиентский сценарий](CORE_API_SPEC.md) и [протокол Service SDK, раздел 7](../services/sdk/SPEC.md).

## Вход студента и связь идентификаторов

В платформу входят через MAX. Пользователь не вводит отдельно MAX ID и не выбирает себе полномочия при регистрации.

```text
Пользователь открывает мини-приложение через бота MAX
  → MAX Bridge предоставляет подписанную строку WebApp.initData
  → ядро-клиент отправляет её в POST /api/v1/auth/token
  → ядро-бекенд проверяет подпись, срок и структуру данных
  → извлекает MAX user.id из проверенных данных
  → находит или создаёт User по уникальному max_user_id
  → выдаёт core access/refresh
  → GET /api/v1/auth/me возвращает внутренний User.id (UUID)
  → GET /api/v1/institution возвращает членства и назначенные профили
```

| Понятие | Пример / формат | Кто определяет |
| --- | --- | --- |
| MAX `user.id` | Идентификатор аккаунта мессенджера | MAX; доверять можно только после проверки подписанных данных сервером |
| `User.max_user_id` | Тот же идентификатор, строка десятичных цифр | Ядро-бекенд, уникальная связь с пользователем |
| `User.id` | UUID платформы | Ядро-бекенд; используется для членств, сессий и операций платформы |
| Членство | `institution_id` + `user_id` | Вуз / уполномоченное администрирование |
| Профиль доступа | `student`, `teacher`, `admin` | Назначается пользователю в рамках конкретного вуза |
| Анкета `user-profile` | Имя, описание, должность и другие разрешённые поля | Отдельный сервис; не является способом первичного входа |

Пример: один аккаунт MAX связан с одним внутренним UUID. В вузе A этому UUID назначены `student` и `teacher`, в вузе B — только `student`. Если профиль один, клиент выбирает его автоматически. Если несколько — предлагает выбор; `admin` автоматически не предпочитается. Смена профиля создаёт новую сервисную сессию и не меняет идентичность пользователя.

Новый пользователь может не состоять ни в одном вузе. Ядро-клиент показывает пустое состояние и внутренний UUID, который можно сообщить администратору для добавления. Отображённые кнопки и выбранный профиль не дают прав сами по себе: сервер обязан проверять членство и полномочия в каждом запросе.

### Где здесь номер телефона

В текущем `AuthTokenRequest` контракта есть только `initData`. API подтверждения телефона и связывания по нему аккаунтов пока нет, поэтому ядро-клиент не отправляет номер в обход контракта и не подменяет им MAX ID.

Если телефон понадобится для поиска уже существующей записи студента, требуется отдельный согласованный сценарий: получение согласия и подтверждённых данных контакта, серверная проверка, правила уникальности и разрешения конфликтов. Один введённый номер или отдельно присланный `max_user_id` не доказывает владение аккаунтом. Такой сценарий нельзя незаметно добавить только на frontend.

## Реализованный сценарий

1. На `/` или `/institution` оболочка читает исходный `WebApp.initData`, отправляет `{ "initData": "…" }` и получает аккаунт через `/auth/me`. Без данных MAX отображается инструкция открыть приложение через бота; dev-входа по произвольному ID нет.
2. Клиент получает все страницы списка вузов с `limit` и `cursor`. При одном вузе выбирает его автоматически и заменяет адрес на `/institution/{id}`. При нескольких показывает выбор.
3. Карточка вуза и список профилей запрашиваются отдельно. Для `pending` и `suspended` сервисы не открываются.
4. При выборе профиля клиент получает `/service?profile=…&locale=…`, включая последующие страницы. Меню отображаются в порядке `(order, id)`; API должен возвращать уже отфильтрованные меню.
5. Перед открытием запрашивается свежая карточка сервиса. Если меню исчезло или контекст вуза/профиля не совпал, загрузка останавливается.
6. Создаётся сервисная сессия через `POST .../service/{id}/session` с телом `{ "profile": "student" }`. Ответ проверяется на совпадение вуза, сервиса, профиля и родительской сессии.
7. В iframe загружается `client_base_url` + путь меню. HTML, CSS и JS клиента браузер скачивает с хоста сервиса напрямую. Ядро-бекенд выдаёт каталог и сессию, а не пересылает все клиентские файлы одним большим ответом.
8. При смене вуза, профиля или сервиса старый iframe удаляется; клиент по возможности отзывает его сервисную сессию. Запоздавшие ответы не открывают старый сервис в новом контексте.

В памяти находится один активный iframe. Число сервисов не зашито в коде; новые экземпляры и меню появляются через каталог API. Переключение выгружает старый документ и может сбросить несохранённые данные сервиса.

Переключатель RU/EN задаёт `locale` в запросах данных. Интерфейс самой оболочки сейчас на русском. Если язык ещё не выбран человеком, используется `default_locale` выбранного вуза.

## API, используемый клиентом

| Операция | Назначение |
| --- | --- |
| `POST /api/v1/auth/token` | Вход с `initData` |
| `GET /api/v1/auth/me` | Внутренний UUID пользователя |
| `POST /api/v1/auth/refresh` | Ротация core-пары |
| `POST /api/v1/auth/logout` | Завершение core-сессии |
| `GET /api/v1/institution` | Свои вузы |
| `GET /api/v1/institution/{id}` | Карточка выбранного вуза |
| `GET /api/v1/institution/{id}/profiles` | Разрешённые профили пользователя |
| `GET /api/v1/institution/{id}/service` | Сервисы и разрешённые меню |
| `GET /api/v1/institution/{id}/service/{service_id}` | Проверка актуальной карточки перед открытием |
| `POST .../service/{service_id}/session` | Сессия выбранного сервиса и профиля |
| `POST .../service/{service_id}/session/refresh` | Ротация service-пары |
| `DELETE .../service/{service_id}/session/{session_id}` | Отзыв при закрытии / переключении |

Все JSON-запросы оболочки идут на тот же origin, что и сама оболочка. Она не обращается к private admin API, не получает machine credentials и не знает токен бота.

## Протокол iframe

Клиент сервиса должен реализовать протокол версии 1 из SDK; произвольный сайт без этого протокола не считается подключённым сервисом.

```text
iframe load
  shell → platform.init {protocol_version: 1, channel_id}
  service → service.ready {protocol_version: 1, channel_id}
  shell → platform.context {...контекст, access_token, expires_at}

service → service.refresh_requested {..., request_id}
  shell → ядро: POST session/refresh
  shell → platform.access {..., request_id, access_token, expires_at}

закрытие / отзыв / ошибка
  shell → platform.session_ended {..., reason}
```

- Для каждого `load` создаётся новый `channel_id`; сообщения старого канала игнорируются.
- Оболочка проверяет точный `event.origin`, `event.source`, версию и канал. Используется точный `targetOrigin`, не `*`.
- Iframe получает только service access. Core access, core refresh и service refresh остаются в памяти JS-модулей оболочки; браузерное постоянное хранилище не используется.
- Клиент сервиса должен запросить refresh перед истечением `expires_at` либо один раз после 401. Параллельные запросы объединяются в одну ротацию с отдельным ответом на каждый `request_id`.
- Повтор уже обработанного `request_id` игнорируется. При потере refresh-ответа старый refresh не повторяется: iframe закрывается, повторное открытие создаёт новую сессию.
- Если клиент не обновил токен до его истечения, оболочка завершает сервисную сессию и убирает iframe.
- Core access обновляется перед запросом при приближении срока. После 401 автоматически повторяется только чтение и только один раз. Изменяющие запросы не дублируются автоматически.
- Logout очищает память и отправляет запрос отзыва серверу. Если сервер не ответил, UI явно сообщает, что подтверждения отзыва нет.

`client_base_url` должен быть отдельным HTTPS origin без credentials, query и fragment. Пути меню — абсолютные пути внутри origin, без обходов, `//`, percent-encoding, query и fragment. Iframe использует `sandbox="allow-scripts allow-same-origin allow-forms allow-downloads"` и `referrerpolicy="no-referrer"`. Разрешение `allow-same-origin` нужно для проверяемого origin, поэтому размещение клиентского HTML на origin ядра запрещено.

Серверы сервисов должны разрешать embedding через CSP `frame-ancestors` / X-Frame-Options. Платформа должна настроить CSP `frame-src` оболочки под утверждённые origin: универсальный перечень невозможно прописать в статический Nginx до появления реестра размещения. В этой реализации адреса проверяются клиентом по ответу API, но динамическая серверная CSP ещё не реализована. Политику embedding нужно отдельно проверить в MAX Web, Android и iOS.

## Файлы и запуск

- `frontend/templates/index.html` — оболочка входа, выбора и рабочего пространства.
- `frontend/static/css/styles.css` — оформление и адаптивность.
- `frontend/static/js/app.js` — состояния UI, выбор вуза/профиля, навигация.
- `frontend/static/js/core/api.js` — HTTP, core-сессия, ротация и пагинация.
- `frontend/static/js/core/service-frame.js` — загрузка iframe и жизненный цикл сервисной сессии.
- `web/configs/docker-nginx.conf` — раздача той же HTML-оболочки для `/institution` и `/institution/{UUID}`.

Сборщик для браузерного кода не нужен. `frontend/package.json` содержит только инструменты тестирования.

Для просмотра состояния без MAX:

```bash
python3 -m http.server 8080 --bind 127.0.0.1 --directory frontend
```

Открыть `http://127.0.0.1:8080/templates/index.html`. В обычном браузере без Bridge будет экран открытия через MAX, а не имитация успешного входа.

Для рабочего входа нужны: подписанные данные MAX, ядро API на том же origin и хотя бы один доступный клиент сервиса с протоколом SDK. Основной Compose запускает `backend` как `backend`, использует постоянную SQLite и Redis. Вход проверяется настоящим токеном бота из `.env`, dev-вход выключен. Порядок серверного запуска: [MAX_DEPLOYMENT.md](MAX_DEPLOYMENT.md).

## Проверки

Из `frontend/`:

```bash
npm test
npm install
npx playwright install chromium
npm run test:browser
```

Модульные тесты проверяют вход, сериализацию refresh, потерю ответа, поздние ответы, пагинацию и адреса клиентов. Браузерные тесты используют перехваченные HTTP-ответы по контракту и отдельный HTTPS-origin клиента: профили, iframe handshake, ротацию, выгрузку, logout, пустые состояния и отказ при недопустимом origin. Настоящие токены MAX не используются.

Если Chromium установлен отдельно, можно задать `CHROMIUM_PATH=/usr/bin/chromium`. Успешные тесты на fixtures не доказывают совместимость с незавершённым backend или со всеми WebView MAX. Приёмка интеграции должна повторить те же действия в MAX с реальными серверными сессиями.
