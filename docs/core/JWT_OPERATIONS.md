# JWT: запуск и ротация ключей

## Чистый прототип, без миграций

Compose теперь использует новую SQLite БД `/data/core-jwt.db`. Старый `core.db`
не читается и не переносится. После обновления два разработчика заново входят
через MAX; права поддержки, вузы и членство создаются заново.
Повторные запуски сохраняют уже новую БД. Для запуска вне Compose также укажите
новый пустой файл в `DATABASE_URL`: `create_all` не обновляет старую схему.

В `.env` нужны `JWT_ISSUER` (точный публичный HTTPS URL ядра) и
`CURSOR_SECRET_KEY` (отдельный случайный секрет, `openssl rand -hex 32`).
`JWT_SECRET_KEY` больше не используется. CURSOR_SECRET_KEY подписывает только
курсоры списков, а не JWT. Остальные секреты из `.env.example` остаются нужны.

```bash
docker compose up -d --build backend administration web
docker compose exec backend python -m auth.keyctl status
```

При первом старте ядро создаёт две независимые RSA-пары: access и refresh.
Файл `/data/jwt/keys.json` находится в постоянном томе `core-data`, доступном
только контейнеру ядра. Внутри Linux каталог создаётся с правами 700, файл — 600.
Не монтируйте этот том локальным сервисам, не публикуйте файл и не добавляйте его
в Git. При локальном запуске Windows ограничьте ACL каталога учётной записью
ядра. Отсутствующий файл при запуске создаётся; повреждённый останавливает запуск.
Во время работы потеря файла приводит к 503, ключи автоматически не заменяются.

Все workers должны видеть один файл и поддерживать общую файловую блокировку.
Это реализация для одного узла с общим томом, не распределённый KMS.

## Что изменилось

1. Все пять типов JWT подписываются RS256, с `typ=JWT` и UUID `kid`.
   Публичный `/api/v1/internal/auth/jwks` содержит только RSA access-ключи.
   Refresh-ключи в JWKS не попадают.
2. Обязательны `iss`, `sub`, `aud`, `iat`, `nbf`, `exp`, `jti`, `token_use` и
   поля контекста соответствующего типа. В JWT используются `sid`, `parent_sid`,
   `family_id`; JSON-ответы сохраняют `session_id` и `parent_session_id`.
3. Проверяются подпись, алгоритм, issuer, точная audience, тип токена, сроки,
   идентификаторы и соответствие живым записям БД. Допустимое расхождение часов —
   30 секунд; истёкшая запись сессии не оживает из-за этого допуска.
4. Refresh потребляется атомарно, без повторного продления семьи: core — 7 суток,
   service — 24 часа и не дольше родителя. БД хранит SHA-256 полного refresh и
   историю jti до окончания семьи + 30 секунд. Plaintext refresh не сохраняется.
5. Повтор использованного refresh отзывает семью; core reuse/logout — также её
   дочерние сессии. Logout принимает только core refresh. DELETE проверяет весь
   путь и владельца. Интроспекция проверяет живое состояние и считает текущие
   права. Redis не участвует в авторизации или отзыве.
6. Nginx пропускает JWKS и machine API для локальных сервисов. Provisioning и
   private API вузов закрыты снаружи. Администрация использует online introspection
   без положительного кэша; сетевой сбой не разрешает операцию.

## Плановая ротация

Создать новый access-ключ и опубликовать его в JWKS:

```bash
docker compose exec backend python -m auth.keyctl prepare access
```

Команда выводит только новый `kid`. Подождите **не менее 300 секунд** с момента
публикации. Затем:

```bash
docker compose exec backend python -m auth.keyctl activate <ACCESS_KID>
```

Команда откажет при слишком ранней активации. Все workers читают активный ключ
из общего файла; перезапуск не нужен. Старый закрытый ключ удаляется из файла,
открытый остаётся для проверки старых JWT минимум 930 секунд после переключения.

Для refresh:

```bash
docker compose exec backend python -m auth.keyctl prepare refresh
docker compose exec backend python -m auth.keyctl activate <REFRESH_KID>
```

Прогрев JWKS для refresh не нужен. Старый открытый refresh-ключ остаётся внутри
ядра 7 суток + 30 секунд после переключения. Это покрывает все ранее выданные
семьи. Плановая ротация сохраняет действующие сессии.

Периодически запускайте (например, ежечасно из планировщика оператора):

```bash
docker compose exec backend python -m auth.keyctl prune
docker compose exec backend python -m auth.keyctl cleanup-history
```

`prune` удаляет только отставные ключи после retention; `cleanup-history` —
только истёкшие записи refresh-истории. Без этих команд безопасность проверки
сроков сохраняется, но файл и таблица будут расти.

## Компрометация и offline-проверка

Плановая ротация не является аварийным отзывом. При утечке закрытого ключа
нужно остановить скомпрометированное ядро, заменить набор ключей из доверенной
среды, отозвать активные сессии и очистить JWKS-кэши сервисов. Неподконтрольный
offline-кэш нельзя отозвать мгновенно. Для чувствительных операций обязательна
online introspection; остальные операции могут сохранять старые права до
300 секунд + 30 секунд допуска. Сервисы никогда не получают закрытые ключи.

## Проверки

Запускать наборы отдельно: каждый задаёт собственные настройки до импорта app.

```bash
cd backend
python -m unittest discover -s tests -p test_jwt_contract.py -v
python -m unittest discover -s tests -p test_max_integration.py -v
python -m unittest discover -s tests -p test_administration_flow.py -v
```

JWT-тесты используют временную SQLite и реальные RSA-подписи: проверяют JWKS,
обязательные claims, смешение типов/ключей, абсолютные сроки, reuse, каскадный
отзыв, гонку refresh, границы tenant, ошибки хранилища и ротацию без ожидания
реального времени. Проверка гонок относится к SQLite; PostgreSQL и боевой
reverse proxy требуют отдельного прогона в соответствующем окружении.
