# Проверка ядра-клиента в MAX

Бот: https://max.ru/t337_hakaton_max_bot. Текущий Nginx настроен на https://195.133.197.144. В настройках мини-приложения бота должен быть тот же адрес.

## Подготовка сервера

После доставки изменений в `/opt/MAX-hackathon-app` сохраните существующий `.env` и добавьте `JWT_SECRET_KEY`: случайный постоянный секрет не короче 32 символов. Сгенерировать значение можно командой `openssl rand -hex 32`. Не меняйте его при каждом запуске. `BOT_TOKEN` должен принадлежать именно этому боту; API получает его как `MAX_BOT_TOKEN`. Ранее опубликованный токен замените через управление ботом и обновите `.env`.

```bash
cd /opt/MAX-hackathon-app
chmod 600 .env
sudo docker compose config --quiet
sudo docker compose up -d --build backend web
sudo docker compose ps
curl --fail https://195.133.197.144/api/v1/health
```

Redis поднимется как зависимость. Бот не требует изменения кода. При замене его токена также выполните `sudo docker compose up -d bot`.

Первый запуск создаёт пустую БД. Существующая БД другого приложения автоматически не импортируется. `core-data` хранит пользователей, членства и сессии, `redis-data` — отзывы. Не выполняйте `down -v`; перед миграцией существующих данных сделайте резервную копию. Рабочий код ядра находится в `backend/`; прежняя заготовка заменена.

## Сервис «Администрирование» и поддержка платформы

Добавьте в `.env` (см. `.env.example`) три секрета — каждый `openssl rand -hex 32` — и адреса:

```bash
CLOUD_BINDING_KEY=...
ADMINISTRATION_PROVISIONING_TOKEN=...
SHELL_ORIGIN=https://195.133.197.144
ADMINISTRATION_PUBLIC_ORIGIN=https://195.133.197.144:8444
```

Порт 8444 должен быть открыт так же, как 8443. Запуск и первоначальная настройка (выполняются один раз):

```bash
sudo docker compose up -d --build backend administration web
# UUID сотрудника поддержки виден на главном экране приложения после входа
sudo docker compose exec backend python manage.py grant-platform-role <USER_UUID>
sudo docker compose exec backend python manage.py list-institutions
```

Дальше всё делается в интерфейсе: пользователь подаёт заявку («Подключить свой вуз»), поддержка одобряет её («Поддержка платформы»), заявитель становится владельцем и открывает «Администрирование» в профиле администратора. У вузов, созданных до обновления, владельца нет — назначьте его в карточке вуза в разделе поддержки. `seed_demo.py` для этого больше не нужен.

## Проверка на устройстве

1. Откройте мини-приложение кнопкой бота в MAX заново (для получения свежего `initData`).
2. Успешный первый вход показывает внутренний UUID и пустой список вузов. Это ожидаемо: права не выдаются автоматически.
3. Повторное открытие тем же аккаунтом должно показывать тот же UUID.
4. Внешний браузер без данных MAX должен показывать только заглушку.
5. После назначения членства через администрирование проверьте выбор вуза, профиля и меню сервиса.
6. Для iframe нужен реальный клиент сервиса на отдельном HTTPS origin, разрешающий embedding и реализующий Service SDK. Демо-адреса `*.platform.example` не работают. Проверяйте загрузку, смену профиля, закрытие и обновление сессии отдельно на Android/iOS/MAX Web.

Без настроенных клиентов сервисов можно проверить настоящий вход и пустой каталог, но нельзя заявлять проверку iframe в MAX.

Диагностика:

```bash
sudo docker compose logs --tail=80 backend web
```

Не публикуйте `initData`, JWT, `.env` и токен бота. Сообщите текст ошибки UI и request ID. Ошибка 401 при входе: проверить совпадение токена с ботом, время сервера и заново открыть мини-приложение (окно свежести 300 секунд).

## Локальная проверка API

В отдельном виртуальном окружении:

```bash
pip install -r backend/requirements.txt httpx
cd backend
python -m unittest discover -s tests -p test_max_integration.py
```

Тест создаёт временную SQLite, использует FakeRedis и собственный тестовый HMAC-ключ. Проверяет подписанный вход, сохранение UUID, запрет dev-входа, повреждённые/просроченные данные, refresh и logout. Это не заменяет реальный запуск в MAX.

Private/machine API закрыт во внешнем Nginx и доступен внутри Docker. Публичный JWKS в текущем прототипе не готов: не используйте демонстрационный RSA-ключ для проверки фактически HS256-токенов. Доработка service JWT/JWKS необходима перед подключением клиентов с офлайн-проверкой подписи.
