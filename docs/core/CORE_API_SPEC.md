# Техническая спецификация API ядра-бекенда

Версия предложения: `0.1.0`, 24 сентября 2026. Основной машинный контракт: [CORE_API_OPENAPI.yaml](CORE_API_OPENAPI.yaml). Обоснования и ответы на исходные TODO: [CORE_API_TODO_REPORT.md](CORE_API_TODO_REPORT.md). Оба документа описывают целевой MVP, не текущую реализацию.

## 1. Область и приоритет

Здесь описаны только правила, которые неудобно или невозможно проверить средствами OpenAPI: авторизация между субъектами, состояния, транзакции, отзыв JWT и устройство хранилища. Форматы запросов, схемы и статусы операций берутся из OpenAPI. При расхождении документы необходимо исправить до реализации, а не выбирать удобный вариант во время обработки запроса.

Все production-соединения используют HTTPS. HTTP из манифеста трактуется как прикладной протокол; передача секретов по незашифрованному публичному HTTP недопустима. URL `.example` в контракте — примеры конфигурации. `core.private.example` обозначает приватный listener, а не просто секретное имя публичного хоста.

## 2. Идентичность и права

### 2.1. Модель

- `User.id` — UUID платформы; `max_user_id` уникален и передаётся строкой десятичных цифр. Он доступен только в `GET /auth/me`. Аккаунт создаётся после проверки MAX, не содержит образовательную анкету.
- `Institution` имеет UUID и состояние `pending | active | suspended`. Регистрация, одобрение и приостановка выполняются оператором платформы вне HTTP-контракта MVP. В членских списках видны все свои вузы со статусом; сервисы доступны только у `active`.
- `Membership` — уникальная пара `(institution_id, user_id)` с непустым набором профилей. Профили фиксированы: `admin`, `teacher`, `student`. Вуз назначает их; сервис может только читать.
- `ServiceType` — разрешённый платформой тип из каталога. MVP: `administration`, `schedule`, `user-profile` (cloud), `coursework` (local). У типа фиксированы поддерживаемые профили и словарь permission codes. Это не каталог API сервисов.
- `ServiceInstance` — UUID, один вуз, один тип, endpoints, `enabled`, локализованное имя и manifest меню. В MVP уникальна пара `(institution_id, service_type)`.
- `Role` локальна экземпляру: уникален `(service_id, code)`. Роль содержит разрешённые профили, переводы имени и permissions из словаря своего типа.
- `RoleAssignment` — `(service_id, user_id, profile, role_code)`. Несколько ролей складывают permissions; deny-правил и иерархий ролей в MVP нет. Профили друг друга не наследуют.

Профиль задаёт базовый класс поведения сервиса; роль даёт дополнительные возможности. Пустой набор ролей допустим: сервис может разрешать базовое действие непосредственно профилю. Если меню требует permissions, должны присутствовать **все** перечисленные permissions. В выдаваемом JWT поле `permissions` — объединение назначенных ролей, без скрытых прав из названия профиля.

### 2.2. Изоляция

Каждый запрос проверяет связи, а не только существование UUID. Экземпляр из другого вуза, чужое членство или ресурс вне области machine credential возвращают `404 RESOURCE_NOT_FOUND`. Недостающий профиль или permission в доступном вузе — `403`. Для pending/suspended вуза либо отключённого экземпляра выдача/обновление сессии возвращает `409 RESOURCE_INACTIVE`. В пользовательских списках отключённые экземпляры не показываются.

Публичный machine token даёт права только на `service_id` из собственных claims. Запрещено создавать членство, назначать профили, обращаться к чужому экземпляру или менять его роли. Владелец backend сервиса считается доверенным администратором **своей** ролевой модели; его API должен отдельно авторизовать действия людей. Ядро не предполагает, что любой пользователь сервиса вправе назначать роли, лишь потому что backend имеет machine credential.

### 2.3. Private управление

Каждая операция `/api/v1/institution/{institution_id}/internal...` проходит три независимые проверки:

1. Запрос пришёл на private listener от workload сервиса администрирования. Network policy/ACL закрывает listener для остальных workload. Public ingress отвечает одинаковым `404` на весь префикс для любых методов, включая `OPTIONS`; прямой backend-port извне недоступен. `Host`, CORS, `X-Forwarded-For` и неизвестные proxy-заголовки не доказывают принадлежность инфраструктуре.
2. `Authorization: Bearer <machine_access>` принадлежит активному экземпляру типа `administration` **этого вуза**, scope содержит `institution:manage`. Этот scope назначает платформа, запрос `/auth/token` не может его расширить.
3. `X-Actor-Token: <service_access>` принадлежит человеку: тот же вуз/экземпляр администрирования, профиль `admin`, действующая корневая и сервисная сессия, живое членство. Permissions вычисляются заново по БД на каждой операции. Actor token передаётся backend администрирования по его обычному пользовательскому запросу; доверять одному `user_id` нельзя.

| Permission администратора | Операции private API |
| --- | --- |
| `institution.read` | Карточка настроек вуза, каталог типов |
| `institution.update` | Изменение имени и языка вуза |
| `members.read` | Список/карточка участников |
| `members.manage` | Добавление/удаление участника, изменение профилей |
| `groups.manage` | Создание учебных групп и изменение их состава |
| `group_chats.manage` | Чтение и изменение ссылок на чаты учебных групп, без доступа к участникам |
| `services.read` | Список/карточка экземпляров, их роли |
| `services.manage` | Установка, настройка, удаление разрешённых экземпляров |
| `roles.manage` | Чтение и замена назначений ролей в любом экземпляре данного вуза |
| `credentials.manage` | Список, выдача и отзыв credentials локального экземпляра |

У admin service системные неизменяемые роли: `owner` (все permissions таблицы), `technical_admin` (`institution.read`, `services.read`, `services.manage`, `credentials.manage`), `membership_admin` (`institution.read`, `members.read`, `members.manage`, `groups.manage`) и `chat_creator` (только `group_chats.manage`). У всех допустим только профиль `admin`. Публичный machine API этого экземпляра может читать, но **не изменять** определения и назначения ролей (`403 PROTECTED_RESOURCE`). Назначения меняются через private API только actor с текущей ролью `owner`; одного `roles.manage` недостаточно. Это препятствует эскалации до owner через собственное назначение. У остальных типов ролевую модель обслуживает их backend.

### 2.4. Ссылки на чаты учебных групп и API бота

Ядро хранит не более одной активной HTTPS-ссылки `https://max.ru/...` на учебную группу. Ссылка не входит в публичные пользовательские и machine-представления группы. Через private API её видят и меняют только actors с `group_chats.manage`; изменение требует `If-Match` и журналируется без полного URL.

`POST /api/v1/internal/bot/group-chats/resolve` принимает `{"max_user_id":"<digits>"}` и отдельный bearer `BOT_CORE_TOKEN`. Публичный ingress всегда отвечает на этот маршрут `404`. Ответ содержит только активные вузы, текущее student-членство, текущую учебную группу и настроенную ссылку. Неизвестный пользователь, отсутствие группы или ссылки дают стабильный `{"institutions":[]}`. Бот не имеет write-операций и при каждом callback повторно разрешает доступ, поэтому устаревший ID из кнопки не даёт ссылку после снятия членства.

Нельзя удалить/отключить экземпляр администрирования, переписать его endpoints либо убрать последнего owner удалением членства, профиля или роли. Проверка последнего owner и изменение выполняются в одной транзакции под блокировкой записи вуза; иначе два параллельных запроса могут оба пройти проверку. Ошибка — `409 LAST_OWNER` или `409 PROTECTED_RESOURCE` соответственно.

## 3. Общие правила HTTP

- JSON UTF-8; поля `snake_case`, кроме сохраняемого из текущего кода `initData`. UUID передаются строками, время — RFC 3339 UTC с `Z`, JWT NumericDate — секунды Unix. Неизвестные поля входных объектов отклоняются.
- На JSON-маршрутах auth-проверка предшествует проверке тела. Невалидный JSON — `400`, валидный JSON с неверной структурой/значением — `422`. Ошибки имеют одну оболочку `ErrorResponse`, включая стандартные ошибки FastAPI. Тело не содержит stacktrace, SQL и входные секреты.
- Все ответы API имеют `X-Request-ID`, сгенерированный сервером UUID; клиентский произвольный request ID не переносится без проверки. JWT, `initData`, Basic credentials и тела выдачи секретов не журналируются. Все JSON-ответы, кроме JWKS и health, имеют `Cache-Control: no-store`.
- Пагинированные списки: `limit` 1–100 (50 по умолчанию), непрозрачный `cursor`, ответ `items` и `next_cursor` (строка или null). Порядок: UUID по возрастанию, для ролей — `code` по возрастанию. Курсор привязан к фильтрам, actor и области доступа, действует 15 минут. При смене `profile`/`locale` начать с первой страницы. Невалидный или устаревший cursor — `400 INVALID_CURSOR`. Это keyset pagination без гарантии snapshot при параллельных изменениях.
- Малые фиксированные списки профилей и каталог типов не пагинируются; ограничения размера заданы схемами. Меню сортируются по `(order, id)`.
- `locale=ru|en` для пользовательских карточек/списков: точный перевод либо `ru`. Каждая локализованная строка содержит фактически использованный `locale`; в одном ответе fallback может различаться по меню. `Accept-Language` не меняет ответ. `default_locale` вуза — рекомендация shell при отсутствии предпочтения пользователя; shell передаёт её явно. Если query вообще нет, API всегда использует `ru`. Private и manifest API возвращают полные карты переводов.
- `PATCH` меняет только переданные поля, минимум одно поле; null не означает удаление. Массивы в `PUT` заменяются целиком. `204` не имеет тела. Завершающий `/` не является отдельной операцией; клиенты используют пути из контракта.
- Для создания экземпляра обязателен `Idempotency-Key` (UUID). В течение 24 часов ядро хранит результат по `(actor, institution, method, path, key)` и каноническому JSON тела. Повтор с тем же телом возвращает исходные `201` и ресурс; другое тело — `409 IDEMPOTENCY_CONFLICT`. Авторизация проверяется заново до replay. Параллельные одинаковые запросы сериализуются. Уникальность типа дополнительно даёт `409 SERVICE_ALREADY_EXISTS` для нового ключа.
- Редактирование существующих ресурсов требует ровно один strong `If-Match` из `ETag` последнего GET/изменения: wildcard и списки не поддерживаются. Нет заголовка — `428`, другая версия — `412`; сначала выполняются auth и проверки области. Для набора ролей ETag существует даже при пустом наборе; для профилей используется ETag membership. Изменение связанных прав инвалидирует соответствующие версии. Это не заменяет транзакционные проверки инвариантов.
- Rate limits MVP: login 10/min/IP, refresh 30/min/session, machine exchange 30/min/client, прочие запросы 120/min/user или 600/min/credential; при превышении `429` с `Retry-After` в секундах. Значения конфигурируемы, ответы о лимите не раскрывают существование аккаунта.

## 4. Пользовательские сессии

### 4.1. Вход через MAX

`POST /api/v1/auth/token` принимает неизменённую строку `WebApp.initData` в JSON. Верификатор следует [инструкции MAX](https://dev.max.ru/docs/webapps/validation): формирует отсортированную строку параметров без `hash`, URL-декодирует значения один раз и проверяет HMAC-SHA256 через ключ, производный от bot token. Повторяющиеся ключи, неверный hex, некорректное UTF-8 и структура подписанных данных отклоняются. `initDataUnsafe`, username, имя и присланный отдельно MAX ID не являются доказательством личности.

Политика проекта: `auth_date` не старше 300 секунд и не более чем на 30 секунд в будущем, `user.id` — положительное целое. Все ошибки содержимого initData дают одинаковый `401 INVALID_INIT_DATA`; неверная оболочка запроса — `422`. Отсутствующая конфигурация/БД — `503`, без выдачи значения bot token. Запись User создаётся атомарным upsert по MAX ID. Подписанная строка не хранится.

Повторный login с валидным ещё свежим initData создаёт новую независимую сессию и не дублирует аккаунт. Это явный компромисс MVP: initData является переиспользуемым доказательством в пределах окна, и logout не запрещает новый login с этой строкой. Для восстановления после перезагрузки webview нужна свежая строка MAX; отказ от постоянного browser-storage может потребовать заново открыть мини-приложение. Одноразовый обмен initData и persistent cookies сейчас не проектируются.

### 4.2. JWT-профили

Алгоритм MVP — `RS256`, ключ RSA не менее 2048 бит, случайный `kid`. Приватные ключи есть только у ядра. Все JWT требуют `iss` (точный настроенный URL issuer), `sub`, `aud`, `iat`, `nbf`, `exp`, `jti`, `token_use`; header `typ=JWT`. Каждый валидатор имеет allowlist алгоритма, проверяет подпись, issuer, audience и **token_use**; допускается временной skew 30 секунд. Отсутствующий claim — отказ. JWT key/URL из `jku`/`x5u` не используется.

| Назначение | `token_use` | `aud` | `sub` | Дополнительные обязательные claims | Срок |
| --- | --- | --- | --- | --- | --- |
| Core access | `core_access` | `core-api` | UUID пользователя | `sid` | 600 с |
| Core refresh | `core_refresh` | `core-refresh` | UUID пользователя | `sid`, `family_id` | Остаток до 7 суток с login |
| Service access | `service_access` | `service:{service_id}` | UUID пользователя | `sid`, `parent_sid`, `institution_id`, `service_id`, `profile`, `roles`, `permissions` | Не более 300 с |
| Service refresh | `service_refresh` | `core-service-refresh` | UUID пользователя | `sid`, `parent_sid`, `family_id`, `institution_id`, `service_id`, `profile` | Остаток до 24 ч с создания, не позднее core session |
| Machine access | `machine_access` | `core-internal` | `client_id` | `credential_id`, `institution_id`, `service_id`, `scopes` | 300 с |

`sid` сервисной пары — UUID дочерней сессии, а не core session. Ни один refresh не принимается ресурсными API как access. Refresh подписываются отдельным набором ключей, который не публикуется в JWKS. Ядро сохраняет возможность проверить старые refresh-ключи до конца всех подписанных ими семей + 30 с. Access не живёт дольше соответствующей сессии; возвращаемые `expires_in` и `refresh_expires_in` — реальные оставшиеся секунды, а не всегда номинальный TTL. Roles/permissions в service access — снимок на момент выпуска; при refresh они вычисляются заново.

Разделение audience и правил проверки опирается на [RFC 8725](https://www.rfc-editor.org/rfc/rfc8725.html). Этот контракт не заявляет реализацию полного OAuth/OIDC: endpoint обмена credentials — собственный JSON-протокол.

### 4.3. Ротация и отзыв

Обе пользовательские пары возвращаются JSON. Core access/refresh и service refresh хранит только shell в памяти; iframe получает только service access. Все refresh-запросы идут в ядро. Авторизация refresh — possession JWT из тела и живая запись в БД, отдельный access не нужен.

Каждый refresh атомарно потребляет текущий `jti` и выпускает следующую пару в той же семье; абсолютный срок семьи не продлевается. В БД хранится SHA-256 полного refresh и история использованных `jti` до конца семьи + skew. Повтор использованного корректно подписанного refresh отзывает семью; core reuse отзывает также все её service sessions. Service reuse отзывает только соответствующую дочернюю сессию. Повреждённый JWT не должен отзывать сессию по неподтверждённому `sid`.

Нет grace-периода или повторной выдачи сохранённого plaintext refresh. Shell сериализует refresh одной семьи; при потере ответа не повторяет старый токен, а выполняет новый login или создание дочерней сессии. Механизм обнаружения повторного использования соответствует принципу rotation из [RFC 9700, §4.14](https://www.rfc-editor.org/rfc/rfc9700.html#section-4.14).

`POST /auth/logout` принимает core refresh, отзывает всю core session с потомками и возвращает `204` также для уже отозванного/истёкшего/неизвестного токена; формат оболочки всё равно валидируется. Не отзывает другие login-сессии пользователя. После отзыва core access немедленно не принимается ядром, поскольку ядро проверяет `sid` в БД. При истёкшем core access logout всё ещё возможен.

Удаление membership, снятие профиля и отключение экземпляра отзывают затронутые service sessions в той же транзакции. Снятие/изменение роли сразу влияет на новую выдачу, private API и introspection. Уже выданный JWT при offline-проверке может сохранять прежние права до 300 секунд + skew: мгновенного отзыва одной подписью не получить. Для чувствительных операций сервис обязан использовать online introspection без кэша и fail closed при недоступности ядра. Срок действия offline JWT — допустимое окно для остальных операций.

## 5. Аутентификация backend сервисов

Для локального экземпляра администратор с `credentials.manage` вызывает private `POST .../services/{id}/credentials`. Возвращаются `credential_id`, `client_id` и `client_secret` **один раз**. Секрет — минимум 32 случайных байта в base64url, хранится в секретном хранилище backend сервиса, не в браузере/репозитории; в БД ядра — hash. Потерянный ответ не восстанавливается GET: создать новый credential и отозвать неизвестный по списку.

Облачные credentials создаёт оператор платформы и инжектирует непосредственно в deployment; даже owner вуза не получает machine secret облачного сервиса. Для общей cloud программы настраивается несколько отдельных bindings, без глобального JWT «доступ ко всем вузам».

`POST /api/v1/internal/auth/token`: HTTP Basic `client_id:client_secret`, JSON `{"grant_type":"client_credentials"}`. Ядро проверяет состояние credential, вуза и экземпляра, выдаёт machine access без refresh. Scopes не запрашиваются клиентом. Стандартный набор: `manifest:write`, `roles:read`, `roles:write`, `assignments:read`, `assignments:write`, `profiles:read`, `tokens:introspect`. Для administration публичные write-scopes ролей/назначений исключаются; дополнительно ему выдан `institution:manage`. Точные scopes возвращаются в ответе.

Максимум два активных credentials на экземпляр: выдать новый, настроить backend, отозвать старый. `DELETE credential` сразу блокирует обмен и все machine JWT с этим `credential_id` за счёт проверки БД. Секреты не ротируются через публичный API сервиса. Это не отзывает пользовательские сессии: при компрометации самого сервиса дополнительно отключить экземпляр. Все credential операции аудируются без секрета.

`GET /api/v1/internal/auth/jwks` публичен и содержит только публичные access-ключи RSA (`kty`, `use`, `alg`, `kid`, `n`, `e`), без `d`, `p`, `q` и refresh-ключей. Возвращает `Cache-Control: public, max-age=300`. При плановой ротации новый ключ публикуется минимум за 300 секунд до подписания им; старый остаётся ещё минимум 930 секунд после последнего выпуска access (600 TTL + 300 cache + 30 skew). Неизвестный `kid` вызывает одно ограниченное по частоте обновление JWKS, затем отказ. Аварийная компрометация ключа требует отдельного оперативного отзыва; offline-кэш не даёт мгновенной гарантии.

`POST /api/v1/internal/auth/introspect` принимает только service access. Вызвать может machine token **его экземпляра**. Для неверного/истёкшего/отозванного токена, чужой audience или потерянного доступа ответ `200 {"active":false}` без дополнительных сведений. `active:true` возвращает актуальные roles/permissions из БД, `sub`, оба session ID, срок и контекст. Это не introspection произвольных core/machine/refresh JWT.

## 6. Клиентский сценарий и профиль

1. `GET /institution` отдаёт публичную HTML-оболочку без персональных данных. Shell получает initData из MAX, выполняет login и `GET /auth/me`.
2. `GET /api/v1/institution` получает свои вузы. Если нет — пустое состояние; если ровно один — shell заменяет URL на `/institution/{id}`; если несколько — выбор. Редирект делается клиентом, потому что initial HTML navigation не содержит bearer из памяти. Сервер не должен ожидать JWT в URL.
3. `GET /api/v1/institution/{id}` и `/profiles` проверяют членство. Если профилей несколько, выбирает человек; если один — shell. Нельзя автоматически предпочесть `admin`.
4. `GET .../service?profile=student&locale=ru` возвращает только включённые экземпляры с доступными этому профилю меню. Карточка содержит только отфильтрованные меню. Прямой GET скрытого экземпляра возвращает `404`, если он не поддерживает профиль; отсутствие требуемого профиля у самого пользователя даёт `403`.
5. `POST .../service/{id}/session` с `profile` создаёт дочернюю пару после проверки членства, состояния и поддерживаемого профиля. Доступность хотя бы одного меню не обязательна для сессии: UI может быть headless, но API всё равно проверяет profile/RBAC.
6. Shell загружает URL выбранного меню, составленный из утверждённого `client_base_url` и `entrypoint_path`. Клиент сервиса — отдельный origin/iframe. Shell сверяет точный origin, `event.source` и контекст iframe перед передачей service access через `postMessage`; JWT не передаются в URL, referrer, shared localStorage или исходный HTML. Протокол сообщений SDK здесь не определяется.
7. При переключении профиля shell закрывает старый iframe, по возможности отзывает его service session через DELETE, загружает новый список и выдаёт новую пару. Глобального `active_profile` в аккаунте/БД/core JWT нет. Две вкладки могут одновременно работать в разных профилях.

Одна service session навсегда связана с одним пользователем, вузом, экземпляром и профилем. Refresh не меняет эти поля. Меню — средство навигации, а не авторизация API; наличие или скрытие пункта не заменяет проверки backend. HTML `/institution/{id}` может отдать оболочку для синтаксически корректного UUID без проверки членства; все данные загружаются только через защищённый JSON API. Для некорректного UUID HTML-маршрута — `404`.

Service client нельзя исполнять в JS-контексте shell или размещать на origin ядра. В MVP каждый тип cloud client получает отдельный origin, local — утверждённый origin вуза. Изоляция iframe и CSP shell допускают только зарегистрированные client origins; непроверенный HTML сервиса не вставляется в DOM ядра. Браузерные JSON-запросы shell к ядру same-origin, cross-origin CORS к core API по умолчанию закрыт. Private API не вызывается браузером; CORS не является его средством защиты. Доступ MAX к embedding HTML настраивается отдельно от CORS JSON API. Это требования границы доверия, а не контракт HTTP других компонентов.

## 7. Регистрация сервисов и метаданных

Оператор вручную создаёт active вуз, первого owner и работающий administration instance с утверждённым manifest. Private каталог позволяет выбрать остальные типы. Cloud URLs и manifest берутся из конфигурации платформы, произвольные URLs для cloud через private API запрещены. Для local установка требует `api_base_url` и `client_base_url`; экземпляр создаётся выключенным с пустым manifest, затем выдаются credentials, backend публикует manifest, администратор включает его. Machine API работает для disabled экземпляра, чтобы он мог зарегистрироваться; блокируются пользовательские сессии, а не onboarding. Для pending/suspended вуза machine exchange и internal API блокируются.

`PUT /api/v1/internal/service/{id}/manifest` заменяет имя/меню с `If-Match`; GET возвращает текущий manifest и ETag даже при пустом первоначальном состоянии. Не меняет URLs, тип, вуз, supported profiles или статус. Ссылки меню — абсолютные пути внутри зарегистрированного client origin: нельзя query, fragment, `..`, backslash, percent-encoded обходы и protocol-relative `//host`. Относительный путь присоединяется к **origin**, не к директории `client_base_url`; поэтому base URL хранится origin-only. `api_base_url` может иметь path-prefix.

Permissions меню входят в словарь типа; профили меню/ролей — подмножество `supported_profiles`. Manifest не регистрирует новые permission codes. Включение local с пустым manifest запрещено (`409 MANIFEST_REQUIRED`). В MVP хотя бы одно меню необходимо каждому включённому экземпляру; отдельная headless-сессия разрешена, даже когда у выбранного профиля нет видимых меню.

Локальные URLs допускаются только HTTPS без userinfo, query и fragment, с DNS hostname, одобренным оператором платформы для данного вуза. Администратор может выбрать лишь адрес из этой allowlist. IP-literal, localhost, link-local, инфраструктурные домены и небезопасные redirects отклоняются. Ядро не делает fetch по переданным URLs, поэтому регистрация не становится SSRF-proxy. До включения оператор подтверждает контроль вуза над origin вне API; автоматический challenge-протокол вне MVP.

Изменение local URL отключает экземпляр и отзывает все его service sessions; повторное включение явное. Public instance view всегда без secrets. Удаление экземпляра — логическое: он перестаёт выдаваться, credentials и сессии отзываются, связанные определения/назначения ролей деактивируются, аудит сохраняется. Данные курсовых/расписания удалением реестровой записи не уничтожаются. UUID никогда не переиспользуется; слот типа освобождается для новой установки с новым UUID.

Роль нельзя удалить, пока есть назначения (`409 ROLE_IN_USE`); сначала снять их. Изменение permissions немедленно меняет актуальную авторизацию в ядре, но offline-токен остаётся снимком. Сужение `allowed_profiles` при несовместимых назначениях — `409 ROLE_IN_USE`. Назначение неизвестной роли, роли другого экземпляра или несовместимой с профилем — `422 INVALID_ROLE_ASSIGNMENT`; оно не создаёт профиль автоматически.

### 7.1. Учебные группы (дополнение реализации)

Группа — сущность ядра: `(institution_id, id, name)`, состав — студенты вуза, максимум одна группа на студента. Управление — private API администрирования (`/groups`, `/groups/{id}/members`, `PUT /members/{user_id}/group`), право `groups.manage`. Чтение для сервисов — scope `groups:read` в стандартном наборе: `GET /api/v1/internal/service/{id}/groups`, `GET .../groups/{group_id}/members`; introspection дополнительно возвращает `group_ids`, ответ профилей участника — `groups`. Оболочке: `GET /api/v1/institution/{id}/groups?profile=` (студенту — своя группа, остальным — все с составом). Удалить можно только пустую группу; ссылки сервисов на группы ядро не отслеживает. В OpenAPI операции помечены `x-extension: study-groups`.

## 8. Облачное размещение

Ядро хранит отдельный instance на вуз, но URL облачного типа может быть одинаковым для всех. Общий процесс получает tenant только из проверенного service access либо из собственного machine binding. Каждая операция с данными требует обе координаты `(institution_id, service_id)`, включая фоновые задания, кэш и файловые ключи. Идентификатор из request body не заменяет token context. Список допустимых bindings задаётся платформой; клиент не может включить новый tenant самообъявлением.

В ядре права хранятся централизованно. Доменные данные принадлежат соответствующим сервисам; прямой доступ сервисов к таблицам core запрещён. Схемы их БД, provisioning-протоколы и HTTP endpoint сервисов здесь не задаются.

## 9. Хранение, атомарность и аудит

Рекомендуемая для MVP БД — PostgreSQL. Таблицы/связи:

| Группа | Основные ограничения |
| --- | --- |
| users | UUID PK, UNIQUE max_user_id, технические timestamps |
| institutions | UUID PK, status, translations, default_locale, revision |
| memberships / membership_profiles | UNIQUE institution+user; профиль из enum; FK на membership |
| service_types | код типа, deployment, supported_profiles, разрешённые permission codes; seed/config платформы |
| service_instances / manifests | FK institution/type, UNIQUE активный institution+type, URLs, enabled, tombstone, revision |
| roles / role_assignments | составные FK гарантируют тот же service и существующий membership profile; отдельная revision aggregate назначений |
| credentials | credential UUID, UNIQUE client_id, service FK, hash секрета, created/revoked timestamps |
| sessions / refresh_uses | core/service family, parent_sid, профиль/tenant, абсолютный expiry, revoked_at, хеши и UNIQUE jti |
| idempotency_records | ключ, actor, scope, request hash, результат создания без секретов, expiry |
| audit_events | UTC, request_id, machine credential, actor UUID, target, action, outcome; без токенов и анкет |

Одна транзакция нужна для: get-or-create пользователя; выдачи service session с проверкой membership/instance; refresh rotation/reuse; profile removal + assignments + sessions; instance disable/delete + sessions/credentials; защиты последнего owner; создания instance + запись idempotency. Выдача и отзыв сериализуются блокировками соответствующих записей; нельзя выдать новую сессию на основании членства, удалённого между проверкой и записью. Результат не публикуется до commit. При ошибке хранилища — `503`, а не успех с несогласованными правами. Credentials, ревокации и sessions не хранятся только в памяти workers.

PostgreSQL достаточно и для rate-limit/idempotency MVP. Redis можно добавить позднее, не делая его вторым источником истины. Для блокировок/отзыва в ядре не используется положительный кэш, который мог бы принять уже отозванную сессию. Кэш offline JWT у сервисов имеет ограничение из §4.3.

Технические retention: idempotency 24 ч; история refresh до абсолютного конца семьи + 30 с, затем очистка; rate-limit buckets до конца окна. Это технические пределы, не сроки хранения учебных документов или юридического аудита. Сроки audit, membership history, backups и удаления аккаунтов определяются оператором до реального пилота, фиксируются конфигурацией и процессом обработки обращений. Решения по персональным данным и незакрытые юридические вопросы приведены в отчёте.

## 10. Проверяемые сценарии для будущей реализации

Это критерии приёмки, тестовый код сейчас не добавляется.

1. Новый валидный MAX login создаёт ровно одного пользователя при гонке; без членства возвращается пустой список вузов. Поддельная подпись, дублирующий ключ, signed malformed user и недопустимый auth_date дают контролируемый `401`.
2. Пользователь A не читает вуз B; machine instance A не читает/меняет роли B. Вуз и service ID в URL обязаны соответствовать контексту.
3. Один пользователь с `student` и `teacher` получает разные сессии; refresh студента нельзя превратить в преподавателя. Public service API не создаёт профиль.
4. Public ingress даёт `404` на все private методы даже с валидными токенами. Private listener проверяет machine instance, actor audience, профиль и актуальный permission.
5. Потерявший owner или membership actor немедленно теряет private доступ. Два параллельных удаления owners не оставляют вуз без владельца.
6. Повтор refresh отзывает соответствующую семью; expired access не мешает валидному refresh/logout. Logout блокирует core/online service доступ; offline окно измеримо и не превышает TTL + skew.
7. Локальный disabled instance может получить machine JWT и опубликовать manifest, но не user session. Секрет облачного экземпляра через private API вуза получить нельзя.
8. Ротация credential допускает два секрета, отзыв старого немедленно отклоняет и обмен, и его ранее выданный machine JWT. GET никогда не раскрывает секрет.
9. Administration нельзя удалить/отключить. Профиль/роль не назначается через другой service_id. Role update с устаревшим ETag даёт `412`, отсутствие `If-Match` — `428`.
10. Повтор установки с тем же idempotency key возвращает тот же instance; иной body — `409`. Cursor из другого actor/profile/locale отклоняется.
11. В русском fallback меню остаётся доступным; два меню user-profile имеют разные стабильные ID. Злонамеренные client paths/URLs не превращаются в cross-origin загрузку или fetch из ядра.
12. Смена ключа JWKS сохраняет работу ещё действительных access; неизвестный `kid` не вызывает бесконечные сетевые запросы. Core/refresh/machine JWT не проходят как service access.

При проверке документации требуется отдельная валидация OpenAPI 3.1, всех `$ref`, operationId, path-параметров, примеров и AND-комбинации MachineBearer + ActorToken на private операциях. Успешная проверка документа не доказывает, что сервер уже реализует этот контракт.
